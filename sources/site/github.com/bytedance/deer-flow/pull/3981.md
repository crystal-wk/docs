## Summary

- Show an explicit `/skill` activation as a compact **inline chip** in both the composer and the chat transcript, instead of raw slash text. The chip sits inline with the input text so it reads naturally and stays aligned.
- In the composer, selecting a skill suggestion stores it as a removable chip; the `/skill` prefix is only re-attached at submit time, so the **backend activation protocol is unchanged**. Backspace on an empty input (or the chip close button) clears it, and prompt-history navigation is suppressed while a chip is active.
- Human messages in the transcript that begin with `/skill` now render the skill as a read-only chip followed by the task text.
- Add a shared `core/skills/slash.ts` (`parseSlashSkillReference` + `resolveSlashSkillDisplay`) that mirrors the backend `slash.py` gate, so the transcript only renders a chip when the skill **actually exists and is enabled** — plain `/word` text and disabled/removed skills fall back to plain text. This also removes a duplicated regex/reserved-name list, keeping display semantics consistent with backend activation.

## Notes

- Multi-skill activation is intentionally **not** introduced here: the backend only resolves a single leading `/skill`, so the UI keeps single-skill semantics rather than faking multi-select.

`resolveSlashSkillDisplay` only checks `skill.enabled && name === reference.name`, but the backend resolver also enforces a per-agent allowlist (`available_skills`), which is a strict subset for any custom agent that declares a `skills: [...]` list (and for bootstrap agents). The frontend reads only the global skills catalog and has no way to learn that allowlist.

Effect: on a custom-agent thread whose allowlist omits a globally-enabled skill, the composer still suggests it as a chip and the transcript renders it as an activation, but the backend rejects it and replies "Skill /X is not available for this agent." — the chip misrepresents what actually ran. It's not silent (the user sees the error reply), but worth either filtering suggestions by the active agent's allowlist or exposing the allowlist via the skills endpoint.

`[7000572](https://github.com/bytedance/deer-flow/pull/3981/commits/7000572ea792013be7b1a24812d210f2606582c8)`

```
The inline slash-skill editor wrapped with `break-words`
(overflow-wrap: break-word), which only moves an over-long token to the
next line before breaking it. A long unbroken string therefore started
on the line below the chip, and when the string contained a break
opportunity such as a hyphen the browser wrapped there and pushed the
remaining run to the next line, leaving a wide gap on the right.

Switch to `break-all` (word-break: break-all) so the text fills each
line from the chip and packs tightly regardless of hyphens or CJK.
```
