## Why

Follow-up to [#4501](https://github.com/bytedance/deer-flow/pull/4501) (Pattern B broker) and [#3971](https://github.com/bytedance/deer-flow/pull/3971) (Pattern A init container), closing [#4532](https://github.com/bytedance/deer-flow/issues/4532).

Both Lark sandbox runtime images (`docker/lark-cli-init/`, `docker/lark-cli-broker/`) shipped only their build definitions — neither was published by CI. They are opt-in and referenced through the empty-default `LARK_CLI_INIT_IMAGE` / `LARK_CLI_BROKER_IMAGE`, so operators had to build and push them by hand. [@zhfeng](https://github.com/zhfeng) asked on [#4501](https://github.com/bytedance/deer-flow/pull/4501) whether we can provide the `lark-cli-broker` image officially.

## What

New `.github/workflows/lark-cli-images.yaml` that builds and pushes both images to GHCR. It tracks the upstream `larksuite/cli` version rather than the DeerFlow `v*` release, so it's intentionally **decoupled** from `container.yaml` and the `verify-versions` gate:

- **Trigger:** `workflow_dispatch` with a `lark_cli_version` input (e.g. `v1.0.65`), or a `lark-cli-v*` tag (version read from after the prefix).
- **Multi-arch:** `linux/amd64,linux/arm64` via QEMU + Buildx — the images stage a real arch-dispatched `lark-cli` binary.
- **Per-component build context:** `lark-cli-init` builds from its own dir (relative `COPY`); `lark-cli-broker` builds from the repo root (it copies the shared `build-runtime.sh` and the harness `lark_broker.py`).
- **Tags:** by lark-cli version, no `latest`, gated on `github.repository == 'bytedance/deer-flow'`. Pinned action SHAs match the rest of the repo; new QEMU/Buildx SHAs verified against their tags.

Published names: `ghcr.io/<owner>/deer-flow-lark-cli-init` and `-lark-cli-broker`, tagged `:<lark-cli-version>`.

### Docs

- `RELEASING.md`: new "lark-cli sandbox images" section documenting the independent publishing.
- `docker/lark-cli-init/README.md` + `docker/lark-cli-broker/README.md`: document the CI publish path; replaced the "publishing is a fast-follow" notes with opt-in notes.

## Rollout / compatibility

- No behavior change: both features stay opt-in behind the empty-default env vars until an operator points them at a published tag.
- No change to the images themselves, the provisioner, or the runtime — this only adds a publish path + docs.

## Test plan

- [x] `python3 -c "import yaml; yaml.safe_load(...)"` — workflow YAML parses.
- [x] New action SHAs (`setup-qemu-action@v3.6.0`, `setup-buildx-action@v3.11.1`) verified against their tags.
- [ ] Maintainer dispatches the workflow (or pushes a `lark-cli-v*` tag) to confirm the multi-arch push to GHCR.

Closes [#4532](https://github.com/bytedance/deer-flow/issues/4532)

**Defensive-hardening suggestion:** `${{ inputs.lark_cli_version }}` is interpolated directly into the shell `run:`, which is the classic GitHub Actions expression-injection pattern. The job is gated on `github.repository == 'bytedance/deer-flow'` and only maintainers can dispatch, so the practical risk is low today — but if that gate ever widens (or a future contributor copies this pattern elsewhere), a dispatcher could submit a value like `v1.0.65"; curl evil; #` and have it execute in the runner. The defensive form passes the input through an env var instead:

```yaml
env:
  LARK_CLI_VERSION_INPUT: ${{ inputs.lark_cli_version }}
run: |
  if [ -n "$LARK_CLI_VERSION_INPUT" ]; then
    version="$LARK_CLI_VERSION_INPUT"
  else
    version="${GITHUB_REF_NAME#lark-cli-}"
  fi
  echo "value=${version}" >> "$GITHUB_OUTPUT"
```

Same caveat applies to line 54 (`version="${{ inputs.lark_cli_version }}"`). Not a blocker given the repo gate, just belt-and-braces.

* ci(lark): publish lark-cli-init/broker images (bytedance#4532)

Add .github/workflows/lark-cli-images.yaml to build and push the two
optional Lark sandbox runtime images (Pattern A init container and
Pattern B broker sidecar) to GHCR.

These track the upstream larksuite/cli version, not the DeerFlow v*
release, so the workflow is decoupled from container.yaml / the
verify-versions gate:

- Trigger via workflow_dispatch (lark_cli_version input) or a lark-cli-v*
  tag (version read from after the prefix).
- Multi-arch linux/amd64,linux/arm64 (the images stage a real
  arch-dispatched lark-cli binary), via QEMU + Buildx.
- Per-component build context: lark-cli-init builds from its own dir
  (relative COPY), lark-cli-broker from the repo root (it copies the
  shared build-runtime.sh + the harness lark_broker.py).
- Tagged by lark-cli version; no latest; gated on the upstream repo.

Docs: document the independent publishing in RELEASING.md and both image
READMEs, replacing the "publishing is a fast-follow" notes.

Closes bytedance#4532

* fix(ci): scope broker build context past root .dockerignore

The repo-root .dockerignore excludes the whole `docker/` tree, but the
lark-cli-broker image builds from a repo-root context and must COPY
`docker/lark-cli-init/build-runtime.sh` and
`docker/lark-cli-broker/entrypoint.sh` (plus the harness lark_broker.py).
Under root .dockerignore those COPYs fail (excluded from context).

per-Dockerfile ignore-file instead of the root one for `-f
docker/lark-cli-broker/Dockerfile` builds, keeping `docker/` and
`backend/` in context while still dropping .git/venv/frontend/docs noise.

var instead of interpolating ${{ inputs.lark_cli_version }} directly into

comment verb (stage -> ships).
