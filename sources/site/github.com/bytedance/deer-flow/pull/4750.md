## Why

`TaskSnapshot.poll_after_seconds` only rejected values `<= 0`. `float("nan")` slips past that comparison because every comparison with NaN is false, and `float("inf")` is genuinely greater than zero, so both were accepted as valid polling intervals.

The failure then surfaces one layer away from its cause. `McpTaskService._next_poll_at` turns the interval into a `timedelta`, which raises `ValueError: cannot convert float NaN to integer` for NaN and `OverflowError: cannot convert float infinity to integer` for infinity. A driver can therefore return a perfectly good remote task status and still have the snapshot fail to schedule and persist — the poll succeeded, but the task's next poll is lost.

## What changed

`TaskSnapshot` now rejects `poll_after_seconds` unless it is both finite and strictly positive, raising `ValueError("poll_after_seconds must be a finite positive number")`. Valid positive intervals behave exactly as before, and `None` still means "use the service's default interval".

The invariant lives at the protocol-neutral `TaskSnapshot` boundary rather than in any one driver, so every current and future `McpTaskDriver` is held to it, and a bad interval is reported at the boundary that produced it instead of crashing the consumer that converts it to a `timedelta`.

The `<= 0` cases (`0`, `-1`, `-inf`) were already rejected and still are; they now share the single unified error message.

## Surface area

- [x] **Docs / tests / CI only** — no runtime behavior change

(Strictly speaking this is a one-line validation tightening in the harness MCP task layer plus its tests and the matching `backend/AGENTS.md` contract note. It changes no endpoint, no agent wiring, and no default; the only behavior difference is that two inputs which previously crashed downstream are now refused at the boundary.)
