Fixes [#4656](https://github.com/bytedance/deer-flow/issues/4656) (bug 2 of the two reported there).

## Why

A run that externalizes an oversized tool result (over `tool_output.externalize_min_chars`, default 12000 chars) terminated as an error with "Artifact delivery incomplete: no produced output artifact was presented", even when the model answered correctly. The persisted `outputs/.tool-results/*.log` files are process feedback the model reads back with `read_file`, never deliverables, yet they were counted as produced artifacts.

## What changed

Run delivery verification no longer counts files under `outputs/.tool-results/` as produced output. Runs that externalize tool outputs now pass verification when the model presents nothing, and genuinely produced files still need `present_files` as before.

`ToolOutputConfig()` here instantiates with field defaults, so `storage_subdir` is always `.tool-results`. That field is user-configurable via `AppConfig.tool_output` (`app_config.py:224`), and `ToolOutputBudgetMiddleware.from_app_config` honors a custom subdir — so if a deployment overrides `tool_output.storage_subdir` in their `config.yaml`, the middleware writes externalized results under that custom dir while this filter still only excludes `.tool-results/`. Net effect: the delivery-incomplete bug this PR fixes would keep reproducing for anyone who customizes that field.

The call site (around line 974) already has `ctx.app_config` in scope — it's passed to other helpers at lines 760, 852, and 930. Threading `app_config` (or just `app_config.tool_output.storage_subdir`) into `_produced_output_paths` would keep the prefix in lockstep with the middleware. Minor in practice (the default covers the common case), but worth a follow-up so this filter can't silently drift from the writer.
