Fixes [#4757](https://github.com/bytedance/deer-flow/issues/4757)

## Why

Provider-generated tool call IDs are not globally unique across parent runs. The background subagent registry used those IDs as process-wide ownership keys, so concurrent runs with the same ID could overwrite, poll, cancel, or clean up each others execution state.

## What changed

- Generate a full server-side execution UUID for every background subagent run.
- Keep provider `tool_call_id` values only for ToolMessage, SSE, persistence, and frontend correlation.
- Use the internal execution ID for registry lookup, polling, cancellation, timeout handling, and cleanup.
- Let each scheduler closure retain its own `SubagentResult` instead of resolving ownership again through the mutable global registry.
- Add regression coverage for duplicate provider IDs and for the internal/external ID boundary.

## Pull request overview

This PR fixes a concurrency bug in the backend subagent background-task registry by separating **provider tool-call correlation IDs** from a **server-generated execution ID** used for process-wide task ownership (polling, cancellation, timeouts, cleanup). This prevents concurrent parent runs that reuse a provider `tool_call_id` from overwriting or controlling each other’s background subagent state.

**Changes:**

- `SubagentExecutor.execute_async()` now always generates a unique `execution_id` and uses it as the registry key; scheduler closures retain their own `SubagentResult`.
- `task_tool` keeps emitting/persisting `task_*` events keyed by the provider `tool_call_id`, while backend control paths use the internal `execution_id`.
- Adds/updates regression tests to validate the internal/external ID boundary and duplicate provider-ID isolation.
