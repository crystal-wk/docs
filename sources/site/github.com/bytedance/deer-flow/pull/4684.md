## Split plan

- [x] **1/3 — middleware foundation** ([feat(extensions): add middleware plugin foundation #4636](https://github.com/bytedance/deer-flow/pull/4636), merged)
- [x] **2/3 — task lifecycle and system-model observers** (this PR)
- [ ] **3/3 — extension services, contributed routers, and the reference extension**

## Why

[#4636](https://github.com/bytedance/deer-flow/pull/4636) gave extensions a middleware chain, and a middleware only sees what passes through the agent graph. Two runtime surfaces stay invisible to it:

- **Task boundaries** — an extension cannot tell when a lead run or a subagent begins and ends, so it has nothing to hang per-task setup, teardown, or accounting on.
- **Model calls made outside the graph** — goal evaluation, memory extraction, title generation, and summarization all invoke a model without passing through the middleware model-call wrappers, so an observability or governance extension silently under-reports the deployment's real model usage.

This PR closes both. It adds no Gateway API surface; services, routers, and the reference extension remain in PR 3.

## What changed

**Contract package `0.1.0` → `0.1.1`.** The registry gains two registration methods alongside `middlewares()`:

- `task_lifecycle(contributor)` — `on_task_start` / `on_task_stop`, receiving a `TaskInfo` (task/run/thread ids, `lead` or `subagent` kind, `parent_task_id`) and a conservative `TaskOutcome` of `completed` / `aborted` / `failed`.
- `system_model_observer(observer)` — `on_system_model_call`, receiving a `SystemOperationKind` (`goal`, `memory`, `title`, `summarization`), a `SystemModelRequest` snapshot, and a `SystemModelResult` carrying either the response or the provider exception plus a duration.

Both new Protocols keep default implementations and every new dataclass field has a default, so the additions stay additive for already-released extensions. `SystemModelRequest.messages` normalizes to a tuple at construction: goal and memory pass a message list while title and summarization pass one prompt string, and a bare `str` already satisfies `Sequence`, so without normalization an observer iterating it would walk characters.

**Task lifecycle.** The lead worker notifies start after the run has started and stop after completion persistence and the completion hook, but before clearing the finalizing barrier and publishing the stream end — holding the barrier across stop is what keeps a same-thread replacement run from overlapping this task's lifecycle. Cancellation raised out of the stop notification is deferred rather than propagated in place, so a cancelled run still clears the barrier and emits its end frame. A subagent with a parent `run_id` wraps its execution in the same pair and reports `parent_task_id` so a delegation tree is reconstructable; a subagent without one (embedded client, standalone LangGraph Server) logs and skips rather than inventing a parent. Contributors run in registration order inside one shared budget, and every failure is logged and failed open. Fail-open is decided by the origin of a failure rather than its base class: only a genuine cancellation of the host task increments `asyncio.Task.cancelling()`, so notification propagates on that and contains everything else — a contributor that lets a `CancelledError` escape must not skip its successors, nor reach the deferred-interrupt path above and end an otherwise successful run as cancelled. `KeyboardInterrupt` / `SystemExit` still propagate.

**System model calls.** All four kinds report every terminal path without changing the exception the host observes, short-circuit on `has_system_model_observers`, and pass the live task store when the runtime has one (detached system work gets an isolated store). Success and failure are awaited inline. Cancellation is a terminal path too — interrupt/rollback admission and shutdown both cancel the run task, so a user sending a follow-up mid-run routinely ends a goal or summarization call there, with the provider tokens already spent — but awaiting observers inside the cancelled task is unreliable, because a repeated cancel interrupts that await before any of them runs; it is therefore submitted to the notify loop instead, the same non-blocking path the memory bridge uses, and then propagated untouched. The DeerMem backend must stay vendorable and cannot import the extension API, so it reports through a new `MemoryCallbacks.on_memory_llm_result` host hook that the DeerFlow-side callbacks translate into an observation.

**Notification loop.** Extension resources must be touched on the loop that created them, but subagents can execute on isolated loops and DeerMem runs on a worker thread. The Gateway registers its serving loop before any runtime dependency starts and resets it last through the exit stack, which covers every startup-failure and cancellation path. Awaited hooks raised on another loop are dispatched across and awaited under the same budget; synchronous sites submit fire-and-forget work. Shutdown stops accepting detached observations before the memory flush — that flush runs on a worker thread and can emit memory observations — while keeping the loop alive for awaited task hooks until run and subagent drain completes.

**Registry.** Marks and rollbacks become per-bucket and positional, so an `install()` that fails after registering two different contribution kinds cannot leave one behind. `needs_task_store` now covers all three kinds, so a deployment registering only lifecycle hooks still gets a task store.

## Deliberately out of scope

- Extension services and contributed Gateway routers (PR 3)
- The standalone reference extension (PR 3)
- Standalone `DeerFlowClient` / TUI plugin loading
- The synchronous summarization half. It and its only host caller are the sync side of an async-only runtime — the agent runs through `abefore_model` and `runtime/context_compaction.py` calls `acompact_state` — so notifying there would block a thread for a call site the host never reaches. The reason is recorded at the call site.

## Impact

Deployments without `plugins:` are unchanged: every new hook site short-circuits on a precomputed flag, and the zero-extension path allocates nothing. Operators that opt in can now observe task boundaries and the model calls DeerFlow makes on its own behalf, without patching the runtime.

## Pull request overview

This PR is part 2/3 of the extensions implementation plan: it expands the `deerflow-extension-api` contract and the DeerFlow host runtime so extensions can observe (1) lead/subagent task lifecycle boundaries and (2) “system-owned” model calls made outside the agent graph (goal evaluation, memory extraction, title generation, summarization), while keeping the zero-plugin path allocation-free.

**Changes:**

- Bump the contract package to `deerflow-extension-api==0.1.1` and add additive public protocols/dataclasses for task lifecycle and system model call observation.
- Wire lifecycle + system-model observer notifications into the lead worker, subagent executor, goal evaluation, title middleware, summarization middleware, and DeerMem’s host callback bridge.
- Introduce a canonical “extension notify loop” registered by the Gateway runtime and add tests/docs covering ordering, fail-open behavior, time budgets, loop dispatching, and shutdown ordering.
