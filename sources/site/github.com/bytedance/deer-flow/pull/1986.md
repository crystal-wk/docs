# 修复 HTML 文件预览异常

## 变更说明

- 修复 Artifact 面板中 `.html` 文件的预览异常
- 不再使用 `iframe.srcDoc` 渲染 HTML 预览
- 改为直接加载原始 artifact URL，保留 HTML 文件自身的文档 URL 与浏览器行为
- 去掉 HTML 预览 iframe 的 `sandbox`，避免依赖 `cookie`、存储能力或页面上下文的 HTML 在预览中变成白屏或异常页

## 问题原因

之前 Deer Flow 对 `.html` artifact 的预览路径和其他文件不同：

- 先把 HTML 文件内容拉成文本
- 再塞进 `iframe.srcDoc`
- 同时给 iframe 加了 sandbox 环境

这样会改变 HTML 文件的实际运行环境，导致一部分本来可以正常打开的 HTML 文件，在 Deer Flow 预览面板里出现白屏、空白或明显渲染异常。

## 用户影响

修复后，用户在 Artifact 面板中预览这类 HTML 文件时，不再容易出现白屏或异常渲染，行为会更接近“直接打开该 HTML 文件”。

## 验证方式

- `cmd /c pnpm typecheck`
- `cmd /c pnpm lint -- src/components/workspace/artifacts/artifact-file-detail.tsx`
- 使用清华大学主页的本地 HTML 副本复现旧逻辑下的问题：旧的 `srcDoc + sandbox` 预览路径会出现异常渲染
- 验证修复后的预览路径可以正常显示清华大学主页

This PR aims to fix abnormal `.html` artifact preview behavior in the Artifact panel by changing the preview strategy to load the artifact URL directly (instead of rendering fetched HTML via `iframe.srcDoc` with a sandbox), to better match “open the HTML file directly” browser behavior.

- Adjust `ArtifactFilePreview` props to derive preview URL from `filepath/threadId/isMock` instead of a pre-fetched `url`

1. Backend returns HTML as Content-Disposition: attachment — iframe src may not render

<br>The backend artifacts endpoint (artifacts.py:172-173) explicitly serves text/html as a download attachment:

```
if mime_type in ACTIVE_CONTENT_MIME_TYPES:
    return FileResponse(..., headers=_build_attachment_headers(actual_path.name))
```

<br>An iframe loading a URL that returns Content-Disposition: attachment will not render in most browsers — it triggers a download instead. The PR screenshots suggest it works, but this is likely browser-specific<br>behavior (Chrome sometimes ignores attachment headers in iframes). This is unreliable and should be validated across browsers.<br>The correct fix likely requires either:

- A backend change to serve HTML inline when accessed from the preview iframe (e.g., a ?inline=true query param that skips the attachment header), or
- Keep using srcDoc but remove the restrictive sandbox attribute

2. Write-file HTML preview is broken

<br>The old code had isWriteFile ? { srcDoc: content } : url ? { src: url } : {}. For write-file: paths, the content comes from the tool call in memory (via loadArtifactContentFromToolCall), and the artifact may<br>not yet exist on disk. The PR removes this branch entirely — all HTML now loads via urlOfArtifact(...), which will 404 for write-file artifacts that haven't been persisted yet.<br>Copilot flagged this correctly. This is a regression.

3. Removing sandbox is a security concern

<br>The old sandbox="allow-scripts allow-forms" at least restricted the iframe's capabilities. The PR removes sandbox entirely, meaning the HTML artifact runs with full privileges in the app's origin. This allows:

- Access to the parent page's DOM (window.parent)
- Cookie/localStorage access from the app origin
- Potential for clickjacking or XSS via crafted artifact content

<br>If the goal was to fix storage/cookie issues, a better approach would be sandbox="allow-scripts allow-forms allow-same-origin" or using srcDoc without sandbox restrictions but on a blob URL. |
