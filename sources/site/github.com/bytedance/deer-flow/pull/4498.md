This form-seeding `useEffect` depends on the `task` object, which wipes in-progress edits on background refetches.

The parent passes `task={formDialogMode === "edit" ? (selectedTask ?? null) : null}` (page.tsx ~line 425), and `selectedTask` is a `useMemo` derived from the react-query `allTasks` array. react-query returns new object references on every background refetch (`refetchOnWindowFocus`, `refetchOnReconnect`, mutation invalidation), so `task` becomes a new reference even when the task content is unchanged. That re-triggers this effect and `setTitle` / `setPrompt` / `setSchedule` overwrite whatever the user is mid-editing - e.g. switch tabs away and back while editing, and your unsaved title/prompt/schedule are gone.

The old page-level code this replaces guarded against exactly this - it depended on `selectedTask?.id` (a stable string) with `eslint-disable-next-line react-hooks/exhaustive-deps` and the comment: "Depend on id only so a background refetch (same task, new object reference) does not wipe edits in progress." That safeguard was lost in the extraction.

For contrast, `AgentFormDialog` in `agents/agents.tsx` doesn't have this problem because the parent passes `editingAgent` (captured `useState`, stable across refetches) rather than a live query-derived value.

Suggested fix: depend on `task?.id` instead of `task` (with `eslint-disable-next-line react-hooks/exhaustive-deps` for the `task.*` reads inside the effect), matching the original pattern.

The edit branch sets `schedule` here but, unlike the create branch (which bumps `createNonce` on line 113), doesn't bump a key. `<ScheduledTaskScheduleInput>` is rendered inside the radix `DialogPortal`, so it only enters the tree when `open` becomes true — in the _same render_ that schedules this effect. Its `useState` initializers (`preset`, `parts`, `runAtLocal`, `timezone`) read `initial = schedule` at mount, which is still the default `{ cron: "0 9 * * *" }` (or `scheduleFromTask(prevTask)` from the previous edit). By the time this effect fires and updates `schedule`, the input has already locked its internal state and never re-syncs from `initial` — the input is uncontrolled, and only a `key` change forces a re-init.

Result: opening the edit dialog shows the wrong schedule (default `daily 9:00` on first open, previous task's schedule on subsequent opens), regardless of the task's actual cron. The input's mount effect also re-emits its internal state via `onChange`, which races with this `setSchedule` and can overwrite the parent's `schedule` state — saving then persists the wrong schedule.

This is a regression from the inline form this replaces: the old `useEffect` (`deps: [selectedTask?.id]`) ran on page mount and whenever `selectedTask` changed, _before_ the user opened the edit form, so `editSchedule` was already correct when the inline schedule-input mounted.

Fix: mirror the create branch — bump a nonce here and fold it into the schedule-input's `key` so it remounts in the re-render that follows this `setSchedule`. Reusing `createNonce` works:

```js
setTitle(task.title);
setPrompt(task.prompt);
setSchedule(scheduleFromTask(task));
setCreateNonce((n) => n + 1);
```

with `key={isCreate ? createNonce : \`${task?.id}-${createNonce}\`}`(or a single shared`formNonce\`).

Follow-up on thread 3658232339: the new `key={isCreate ? createNonce : task?.id}` (line 338) doesn't actually fix the edit-branch race.

`task?.id` is stable across reopens of the same task, so the key never changes between successive edit opens of one task. More fundamentally, the radix `DialogPortal` mounts `<ScheduledTaskScheduleInput>` in the _same render_ that flips `open` to true — i.e., **before** this `useEffect` fires. Its `useState` initializers (`preset`, `parts`, `runAtLocal`, `timezone`) read `initial = schedule` at mount time, which is still the parent's stale `schedule` (default `{cron:"0 9 * * *"}` on first open; the previous task's schedule on subsequent opens of a different task). The `setSchedule(scheduleFromTask(task))` here runs only after commit, so it cannot influence values the input has already locked in. The remount-on-dialog-open behavior of the radix portal doesn't help either, because that remount happens with the stale `initial` too (parent state hasn't been updated yet at that moment).

Repro (cold page load): click edit on a task whose cron isn't `0 9 * * *` (e.g. a weekly task) — the schedule section shows "daily 09:00" instead of the task's real schedule. The parent's `schedule` state does get corrected by this effect after mount, so a no-op save may happen to persist the right value, but the displayed schedule is misleading and any edit the user makes starts from the wrong baseline.

Fix: bump the nonce in the edit branch too, and fold it into the key so the input remounts in the re-render that follows `setSchedule`:

```js
setTitle(task.title);
setPrompt(task.prompt);
setSchedule(scheduleFromTask(task));
setCreateNonce((n) => n + 1);
```

with `key={isCreate ? createNonce : \`${task?.id}-${createNonce}\`}`(or a single shared`formNonce\`).
