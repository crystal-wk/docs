## Why

`csrf_middleware.py` trusted `Forwarded` / `X-Forwarded-*` on direct requests, so a client could spoof the browser-facing scheme/origin used by auth same-origin checks and OIDC fallback `redirect_uri` construction.

## What changed

- `Forwarded` / `X-Forwarded-*` are only honored when the TCP peer matches `AUTH_TRUSTED_PROXIES`.
- Direct requests now resolve scheme/origin from the real request scheme and `Host`.
- OIDC fallback `redirect_uri` continues to use the shared origin resolver.
- README, backend agent docs, `.env.example`, and `config.example.yaml` now describe the trusted-proxy boundary and HTTPS migration.

With `AUTH_TRUSTED_PROXIES` defaulting to unset, the bundled docker setup (`docker/docker-compose.yaml`) terminates TLS at nginx and proxies to the gateway over plain HTTP on the `deer-flow` docker network — so the gateway's TCP peer is the nginx container's dynamic IP, which matches no trusted network. After this change, `is_secure_request()` returns `False` for those requests even when the browser connection is HTTPS, which silently downgrades the CSRF cookie `secure` flag and disables `remember_me` persistence for any existing HTTPS deployment that hasn't opted in.

Worth spelling out here (and in `.env.example` / `config.example.yaml`, which currently don't mention this variable at all): (a) the default is unset/empty = no trust; (b) the value format is comma-separated CIDRs/IPs; (c) bundled-docker HTTPS users need to set it (e.g. to the docker network CIDR like `172.16.0.0/12`) to preserve pre-PR behavior. Otherwise this `risk:high` default-behavior change will catch operators upgrading from the previous release.
