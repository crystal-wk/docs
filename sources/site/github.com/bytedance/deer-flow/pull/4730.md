Closes [#4731](https://github.com/bytedance/deer-flow/issues/4731).

## Why

RFC [#1898](https://github.com/bytedance/deer-flow/issues/1898) concludes DeerFlow should keep a unified memory contract with pluggable providers, and lists **Honcho** as the user-dimension option (user profiling and long-term preference modeling). This PR adds that provider behind the existing `MemoryManager` contract, as a `backends/` drop-in with no core changes — the same shape as the OpenViking backend took ([#4509](https://github.com/bytedance/deer-flow/pull/4509) → [#4707](https://github.com/bytedance/deer-flow/pull/4707)).

## What changed

- New `backends/honcho/` (config + minimal httpx client + manager). **No new dependencies** (httpx is already a core harness dep) and **no local LLM calls** — Honcho's server-side deriver performs extraction/consolidation asynchronously, so `add()` is a cheap message write.
- **Multi-user isolation by construction (default derivation):** one Honcho workspace per `user_id`. The default derivation is collision-resistant (`sanitize[:48]-sha256[:8]` — lossy sanitization alone would let e.g. `user.name@example.com` and `user-name@example.com` merge into one workspace). `workspace_overrides` / `user_peer_overrides` let deployments map specific users to shared or custom workspaces; a workspace deliberately shared across users shares its **search index** (Honcho's `/search` is workspace-scoped, no peer filter), while `get_context` / `get_memory` stay peer-scoped. A missing/empty `user_id` fails closed (no memory for that call), never a shared fallback workspace.
- `get_context` returns the user's working representation (self-truncated via `max_injection_chars`); `search` implements tool-mode semantic search (`supports_search = True`); `get_memory` returns a minimal DeerMem-shape view. Recall failures follow `failure_policy.read` (default log-and-empty; `fail_closed` rethrows `MemoryManagerError`).
- `requires_passive_writes_in_tool_mode = True` (mem0's pattern): honcho's only write path is passive `add()` ingestion — fact CRUD is intentionally unsupported — so tool mode retains `MemoryMiddleware` instead of silently freezing writes.
- **Exception containment:** the client wraps non-JSON 200 responses (misconfigured proxies, maintenance pages) into `HonchoRequestError`, and the manager's boundaries catch broadly (openviking's precedent) so no backend exception can escape into `MemoryMiddleware.after_agent` and break an agent turn.
- Async entrypoints (`aadd`/`aget_context`/`asearch`) offload sync HTTP via `asyncio.to_thread`; a `tests/blocking_io/` anchor pins it.
- `api_key` over plain http requires `allow_insecure_http: true` (mem0's posture); auth-less self-hosted http needs no opt-in.
- Docs: backends README row + section, `config.example.yaml` commented block, `backend/AGENTS.md` bullet.

Follow-up (out of scope): moving onto an official Honcho SDK adapter, mirroring the OpenViking custom-HTTP → maintained-adapter arc ([#4707](https://github.com/bytedance/deer-flow/pull/4707)).

- Full offline suite: **11106 passed, 70 skipped** with this branch; `make test-blocking-io`: **71 passed** including the new honcho anchor.
- New `tests/test_honcho_memory_backend.py` (38 tests): config parsing, workspace resolution incl. override / fail-closed / sanitize-collision paths, message mapping + truncation, read policies (fail-open and fail-closed, incl. non-`HonchoRequestError` exceptions), search mapping, DeerMem-shape `get_memory`, passive-writes flag, factory drop-in discovery.
- `ruff format --check` + `ruff check` clean; `uv lock --check` unchanged (no new deps).

## Reviewer expectations, stated up front

- **Why a thin custom HTTP client instead of the `honcho-ai` SDK:** zero new dependencies (httpx is already a core harness dep) and a minimal surface for this first backend, mirroring the accepted OpenViking arc (custom HTTP in [feat(memory): add OpenViking HTTP backend #4509](https://github.com/bytedance/deer-flow/pull/4509) → official adapter in [refactor(memory): use official OpenViking adapter #4707](https://github.com/bytedance/deer-flow/pull/4707)). Adopting an official Honcho adapter is the natural follow-up PR.
- **No fact CRUD by design:** Honcho's server-side deriver owns the representation; `create_fact`/`update_fact`/`delete_fact` inherit the base `NotImplementedError` (frontend fact buttons report "not supported", per this backends README's own gotcha [无法正常运行呢？ #3](https://github.com/bytedance/deer-flow/issues/3)), and `get_memory` returns `facts: []` with the representation as the work-context summary. `requires_passive_writes_in_tool_mode = True` keeps tool mode writing.
- The v3 endpoints used (`/peers/{id}/representation`, workspace `/search`) are validated against a live self-hosted v3 instance; under the default fail-open read policy any future drift degrades to logged empty recalls, never a broken agent turn.
