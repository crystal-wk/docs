Manual triggers bypassed the `max_concurrent_runs` global cap enforced by the poller, allowing manual reservations to push the active run count above the configured limit.

## Why

`run_once` gates scheduled dispatches behind a `count_active_runs()` budget check before `claim_due_tasks(limit=budget)`. The manual trigger path called `dispatch_task` directly, skipping that check entirely — with `max_concurrent_runs=1`, a manual trigger could still launch while a scheduled run was active, and two concurrent manual triggers for different tasks could both launch.

## What changed

- `dispatch_task` now performs the same `count_active_runs()` budget check for `trigger == "manual"` (skipped when `max_concurrent_runs == 0`, i.e. uncapped). When `active >= max_concurrent_runs`, it returns a `"conflict"` outcome, which the router maps to HTTP 409 — consistent with the existing per-task active-run conflict response.

```python
if trigger == "manual" and self._max_concurrent_runs > 0:
    active = await self._task_run_repo.count_active_runs()
    if active >= self._max_concurrent_runs:
        return {
            "outcome": "conflict",
            ...
            "error": "global concurrent-run limit reached",
        }
```
