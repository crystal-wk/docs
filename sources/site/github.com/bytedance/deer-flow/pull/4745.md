## Why

PR [#4707](https://github.com/bytedance/deer-flow/pull/4707) established OpenViking as DeerFlow's automatic memory backend, while OpenViking's official `/mcp` endpoint provides richer operations that the model can choose explicitly. This PR documents and tests that complementary MCP path through DeerFlow's existing generic HTTP MCP infrastructure.

The responsibilities remain separate and compatible:

1. `MemoryManager` + `langchain-openviking` handle automatic turn recall and capture.
2. OpenViking `/mcp` provides explicit model-selected tools.

Related baseline: [#4707](https://github.com/bytedance/deer-flow/pull/4707). This PR does not depend on or duplicate the query-aware recall work in [#4732](https://github.com/bytedance/deer-flow/pull/4732).

## What changed

- Added a disabled-by-default `openviking` Streamable HTTP server example to `extensions_config.example.json`.
 - Authentication uses `X-API-Key: $OPENVIKING_API_KEY` with a normal owner-bound USER API key.
 - No credential is committed.
 - No OpenViking account, user, actor-peer, trusted-mode, root, or admin identity headers are added.
- Documented USER-key setup, first-run authentication/cache recovery, Docker addressing, default tool-name prefixing, and coexistence with the automatic memory backend.
- Exposed OpenViking's native tool set through DeerFlow's existing generic discovery path for capability parity, including `forget`.
 - `forget` permanently deletes a `viking://` URI and should be called only after explicit user confirmation.
 - DeerFlow does not enforce that confirmation.
- Added focused coverage using a deterministic localhost Streamable HTTP MCP fixture for config resolution, secret masking, identity-header absence, initialization, discovery, prefixing, and real `tools/call` routing.
- Added the required changelog entry.

### Responsibility boundaries

DeerFlow remains a generic MCP client. It uses the existing HTTP transport, standard `initialize` / `notifications/initialized` handshake, `tools/list`, MCP-to-agent-tool conversion, `<server>_` name prefixing, and `tools/call` routing. OpenViking remains the owner of its tool schemas and behavior.

No OpenViking-specific MCP client, protocol implementation, tool wrapper, registry, interceptor, memory abstraction, or shared policy framework is added. The final effective diff contains no shared MCP production-code changes.

### Security model

- Personal/single-owner mode uses a normal owner-bound OpenViking USER API key only.
- The checked-in example references `$OPENVIKING_API_KEY`; it contains no literal credential.
- DeerFlow sends no `X-OpenViking-Account`, `X-OpenViking-User`, or `X-OpenViking-Actor-Peer` headers in this path.
- Existing Gateway config masking keeps header values out of management responses.
- OpenViking's native `forget` capability is exposed for parity. Because deletion is irreversible, callers should obtain explicit user confirmation before invoking it; this PR does not claim or add enforcement.

## Scope

Included:

- official OpenViking `/mcp` registration through generic MCP configuration
- USER-key authentication through existing environment expansion
- native OpenViking tool discovery, prefixing, and invocation through existing MCP routing
- operator documentation, example configuration, changelog, and focused regression coverage

Not included:

- query-aware turn recall ([feat(memory): add query-aware turn recall #4732](https://github.com/bytedance/deer-flow/pull/4732))
- changes to automatic memory capture/recall ([refactor(memory): use official OpenViking adapter #4707](https://github.com/bytedance/deer-flow/pull/4707))
- memory lifecycle, compaction, shutdown, thread, or deletion signals
- hosted multi-user credential provisioning, trusted mode, root/admin data access, or impersonation
- setup wizard/UI changes
- new MCP protocol/client code, filtering policy, or broad authorization/config refactors

## Isolated live verification

The original isolated verification used OpenViking `upstream/main` at `3087f943a2dd41f6d0bde4742832d368d021f47b`, unique temporary config/data directories, and unused localhost ports.

- Started a real isolated OpenViking server and used its real `/mcp` endpoint.
- Provisioned a normal USER key through the root-only Admin API, then omitted the root credential from all DeerFlow MCP traffic.
- Used a deterministic localhost OpenAI-compatible embedding fixture only to make isolated OpenViking initialization independent of external embedding availability; OpenViking auth, MCP transport, handshake, discovery, and tool execution were not mocked.
- DeerFlow's real MCP client completed `initialize`, `notifications/initialized`, and `tools/list`; OpenViking reported 13 native tools.
- Structured calls to `openviking_health`, `openviking_list`, and `openviking_find` succeeded through the discovered DeerFlow tools.
- Captured requests contained the USER API key and no account/user/actor-peer identity headers.
- Automatic OpenViking memory configuration and the MCP server configuration loaded simultaneously without conflict.
- The redacted verification output contained no credential.
- All spawned services, listeners, temporary files, and isolated state were removed after the run.

The final removal of DeerFlow-side filtering is additionally pinned by the deterministic integration test, which discovers both `openviking_find` and `openviking_forget` while invoking only the non-destructive `find` fixture. A model-driven provider turn was not required for this deterministic check; the real discovered DeerFlow tool object was invoked and its structured MCP `tools/call` result was verified directly.
