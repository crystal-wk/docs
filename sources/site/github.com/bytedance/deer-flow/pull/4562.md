## Why

DeerFlow uses several independent backend execution domains, including the 
asyncio default executor, dedicated thread pools, AnyIO worker threads, and 
additional event loops.

The existing detector did not reliably cover executor aliases, helper 
wrappers, LangChain tool fallbacks, model fallbacks, or dynamically configured 
components. This made it difficult to build an accurate baseline for future 
thread-starvation tests.

## What changed

- Classify backend execution boundaries as:
 - asyncio default executor
 - dedicated executor
 - AnyIO worker thread
 - direct event-loop blocking
 - separate event loop
 - unresolved dynamic boundary
- Detect:
 - `asyncio.to_thread()`
 - `run_in_executor(None, ...)`
 - imported aliases and same-module helper wrappers
 - `set_default_executor()`
 - `ThreadPoolExecutor` construction and submission
 - additional event-loop creation
 - synchronous LangChain tools without native async implementations
 - `BaseChatModel` async executor fallbacks
- Add runtime inspection for configured tools and model classes without 
 invoking tools, constructing models, or contacting external services.
- Produce a concise summary and versioned machine-readable JSON inventory.
- Update `make detect-thread-boundaries` to run with the backend `uv` 
 environment and write: 
 `.deer-flow/thread-boundary-inventory.json`
- Add focused detector and runtime-inspection tests.
- Preserve existing executor sizing, routing, and production behavior.

The current source inventory independently verified:

- 200 explicit `asyncio.to_thread()` calls
- 2 default `run_in_executor(None, ...)` calls
- 10 explicit `ThreadPoolExecutor` constructions
