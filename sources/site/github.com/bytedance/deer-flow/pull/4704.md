## Summary

- publish uploads with atomic no-replace semantics and deterministic `_N` collision suffixes across Gateway, embedded client, generic IM, Feishu, DingTalk, and WeChat
- hold portable, cross-process generation leases through conversion, sandbox synchronization, response construction, deletion, rollback, and final release
- bind generated Markdown to the exact primary generation under `.upload-conversions/<actual-primary-filename>.md`, while preserving user-owned sibling Markdown
- make cancellation wait for in-flight publication, conversion, synchronization, rollback, and cleanup workers; once final lease release commits the result, late cancellation no longer turns success into an indeterminate failure
- protect active stages and deletion transactions from multi-worker startup cleanup with cross-process liveness locks
- synchronize exact remote copies for non-mounted providers and roll back every path completed before a later failure or cancellation
- reject unsafe or non-portable filename aliases before publication while retaining exact deletion support for legacy POSIX names
- document the ownership, sandbox visibility, recovery, and crash-consistency contracts and add regression coverage

## Root cause

Upload adapters selected names from an in-memory or on-disk snapshot and then wrote with truncating creation semantics. Independent requests and adapters could choose the same filename and overwrite one another. Generated Markdown also shared the primary upload namespace, so conversion and deletion could overwrite or remove user-owned content such as `report.md`.

The complete fix requires the filename lease to represent the entire generation, not just the final write. Conversion, sandbox synchronization, response construction, deletion, remote compensation, and cancellation cleanup now operate on the exact published identity while that lease is held.

## Deletion durability and recovery

- primary and exact conversion are moved into an inode-and-intent-tagged transaction before remote side effects
- transaction-root creation and every rename are persisted destination-first and source-second
- commit/restore markers are persisted as files and then in the transaction directory; retries reopen the same regular inode without following links and repeat that order
- a durable, provider-bound remote-deletion journal and finalization guard keep the basename reserved until the exact sandbox generation is deleted or confirmed absent
- commit cleanup persists tombstone removal before clearing commit intent; restore persists visible peers and hidden-alias removal before clearing restore intent
- unexpected-inode recovery removes a hidden hard-link alias only when the original target name itself is a verified same-inode visible peer; an unrelated hard-link peer or sole mismatched tombstone remains fail-closed
- guard-only and interrupted `nlink=2` states are idempotently repaired on startup or the next deletion preparation

## User and developer impact

Concurrent uploads preserve every completed payload as `name.ext`, `name_1.ext`, and so on. Responses and IM metadata expose the actual published name. Generated conversions have an explicit one-to-one path derived from that name and remain readable through the supported sandbox path.

Storage that cannot honor atomic no-replace publication fails explicitly. Remote deletion retries never reconnect to a replacement sandbox or infer ownership from a pathname alone, and cleanup never guesses or deletes a legacy/user-owned `uploads/<stem>.md` sibling.

I can see a reasonable argument for keeping the file across acquires for hot names (the path is deterministic per filename, so reuse amortizes creation cost when the same name is re-published). If the preservation is intentional, a periodic GC that drops lock files not attached to a current primary would close the gap; if not, mirroring `UploadStageLease.release` (unlink while the `flock` is still held, then unlock+close) would be the small fix.
