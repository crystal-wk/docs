## Why

DeerFlow has no mechanism for reviewing subagent results. The lead agent receives a free-text 
self-report (`"Task Succeeded. Result: ..."`) and its system prompt instructs it to "verify against 
primary evidence" — but no usable evidence exists: the child's intermediate `ToolMessage`s live on 
the other side of the subagent boundary, and verifying a claim costs roughly re-executing the 
action. A subagent that goes off the rails but returns `completed` has its conclusions adopted 
wholesale.

This is the trigger for the layered verification design in RFC [#4651](https://github.com/bytedance/deer-flow/issues/4651). This PR lands **Layer 1 
only**: deterministic **tool receipts** — an immutable, runtime-stamped execution fact per tool 
call — plus a model-visible receipt ledger that makes reports citable (`[rN]`). Parent-side 
citation verification, acceptance checklists, and the selective judge follow in later PRs (tracked 
in the RFC).

## What changed

- Every tool result now carries a `deerflow_tool_receipt` record in its metadata (tool name, 
 status, args/output fingerprints, byte count, timestamp) — stamped by the runtime, not the model, 
 so it cannot be forged by the LLM.
- Before each model call, the agent's context gains a hidden, ephemeral "Tool receipts" ledger 
 (`r1..rN`, status per call, bounded to ~2,000 chars with newest-first eviction). It is never 
 written back to state and never shown in the UI. The ledger header always states its evidence 
 boundary: _"Execution evidence only — … do not validate claim correctness or task acceptance."_
- New `verification` config section (`config.yaml`, config version 32 → 33): `receipts_enabled` 
 (default **on**), `judge_enabled` (default off, unused until the judge PR), `judge_model_name`.
- No behavior change to existing flows: receipts are additive metadata + bounded context 
 injection; stamping failures are logged and skipped, never blocking tool execution.
