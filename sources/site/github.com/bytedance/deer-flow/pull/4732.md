## Summary

Add the minimal backend-neutral backbone for query-aware memory recall on each real user turn, with OpenViking as the first backend opting into the capability.

This extracts the query-aware slice from the earlier broad design draft in [#4637](https://github.com/bytedance/deer-flow/pull/4637) without carrying over its lifecycle, startup, authentication, or failure-policy work. [#4726](https://github.com/bytedance/deer-flow/pull/4726) is not a prerequisite for this change.

## What changes

- Extend `MemoryManager.get_context()` and `aget_context()` with an optional plain-string `query`, guarded by a backend capability flag so existing and third-party managers remain compatible.
- Move generic memory loading, gating, failure handling, and `<memory>` formatting into the shared memory package.
- Add independent host controls for baseline session injection and query-aware turn injection while retaining `memory.injection_enabled` as the master gate.
- Add request-only turn recall in `DynamicContextMiddleware`:
 - selects the latest real user message using DeerFlow's existing conventions;
 - derives sanitized plain text from the original user content;
 - invokes the async manager path in Gateway execution;
 - inserts a hidden `HumanMessage` immediately before the current user message without mutating graph state;
 - caches the exact recalled text in run-local context once per user turn for tool-loop reuse.
- Redact the temporary recall cache from persisted or externalized run context.
- Opt OpenViking into query-aware context using request-local retriever copies and stable DeerFlow thread-to-OpenViking session mapping for per-turn queries.

## Behavior

Given:

```yaml
memory:
  injection_enabled: true
  session_injection_enabled: true
  turn_injection_enabled: true
```

Before this change, DeerFlow persisted one query-less baseline memory snapshot at the first turn and did not recall against subsequent user questions.

After this change, the existing baseline snapshot remains available, while an explicitly enabled turn path retrieves once against the latest real user question and makes that hidden user-role block visible only to model calls for the current run. Repeated tool-loop model calls reuse the same text. The recalled block is absent from returned state, checkpoints, history, and memory capture input.

With the generic defaults (`session_injection_enabled: true`, `turn_injection_enabled: false`), behavior remains the same as before.

## Compatibility

- Query-aware recall is opt-in per backend through `supports_query_aware_context`.
- Capability-off and older backends never receive the new `query` keyword.
- Query-less baseline calls do not receive `thread_id`, even when the backend supports query-aware context; `thread_id` travels only with a per-turn query.
- Capability-off baseline backends therefore retain their previous query-less scope.
- OpenViking per-turn recall receives the latest query and stable `thread_id` together; its shared retriever is not mutated because query, peer, and session configuration is request-local.
- No dependency or lockfile changes are included.

## Configuration

Generic host defaults remain unchanged:

```yaml
memory:
  injection_enabled: true          # master gate
  session_injection_enabled: true  # existing persisted baseline snapshot
  turn_injection_enabled: false    # request-only latest-query recall
```

When the master gate is enabled, at least one injection path must be enabled. Set `injection_enabled: false` to disable all automatic injection.

For OpenViking, the recommended configuration is:

```yaml
memory:
  injection_enabled: true
  session_injection_enabled: false
  turn_injection_enabled: true
  manager_class: openviking
```

OpenViking's session-start baseline runs the fixed `retrieval.injection_query` as a similarity search, so it can return an arbitrary top-N rather than directly reading an authoritative user profile. Per-turn query-aware recall supersedes that fixed-query baseline; directly loading authoritative profile, preference, or entity files remains future work.

## Scope

This PR intentionally does not change:

- generic memory defaults or baseline retrieval mechanics;
- memory read failure policy or error taxonomy from [fix(memory): enforce backend read failure policy #4726](https://github.com/bytedance/deer-flow/pull/4726);
- authentication or permission classification;
- Gateway startup validation or warmup;
- capture, commit, compaction, shutdown, or deletion lifecycle;
- query rewriting, summarization, enrichment, or query objects;
- direct profile, preference, or entity file loading;
- setup UI, provisioning, credential management, MCP tools, retries, or background writers.
