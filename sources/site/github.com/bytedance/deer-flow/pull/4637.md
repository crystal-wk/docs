## Why

DeerFlow already has an OpenViking memory backend, but it duplicates HTTP transport, message conversion, retry, and trusted-identity behavior that OpenViking now maintains in its LangChain integration.

This draft moves new OpenViking configurations onto that maintained adapter while keeping DeerFlow's existing `MemoryManager` seam as the owner of host lifecycle policy. It adds query-aware automatic recall and capture without changing DeerMem, Mem0, or third-party session-snapshot backends.

## What changed

- New configurations use `langchain-openviking==0.1.0` and `openviking-sdk>=0.1.6,<0.2`. DeerFlow does not install the OpenViking server package or maintain another SDK client.
- `DynamicContextMiddleware` supports both existing session-snapshot backends and per-turn backends. OpenViking recalls against the latest real user request before a model call, caches the result only for that run, and never checkpoints or captures the injected context.
- The Gateway resolves any enabled memory manager before reporting readiness. Invalid configuration, missing credentials, and backend construction failures abort startup with the original guidance instead of letting recall degrade and failing the completed run during capture. Disabled memory does not construct or validate its backend.
- Runtime recall failures still follow the configured read policy. Authorization and owner mismatches always fail closed.
- Automatic recall is request-scoped to the credential owner's self-memory and the current top-level agent peer. `search` mode also receives the stable OpenViking Session derived from the DeerFlow thread.
- Completed turns append only unseen messages. Token threshold, inactivity, and pre-compaction are commit boundaries. Commits create archives inside the same OpenViking Session rather than rotating it.
- Idle and failed-commit intent is stored in an atomic, bounded local cursor containing message hashes and lifecycle metadata, but no conversation content. Deadlines are restored after restart.
- Graceful shutdown stops new work, drains active operations, retries failed or already-due commits, and closes the shared recorder client. A deployment does not force every active conversation to commit early.
- The maintained path accepts an ordinary credential-bound OpenViking USER key and rejects a mismatched DeerFlow user before remote I/O. In OpenViking `api_key` mode, account/user identity comes from that credential and assertion headers are ignored. DeerFlow selects the actor peer inside a request-local scope for each recall, capture, and flush.
- Corrupt cursor state fails closed before transcript replay, avoiding duplicate remote writes. One bad lifecycle callback or shutdown candidate cannot stop cleanup for every other session.
- Explicit legacy-only configurations remain on the deprecated custom-HTTP implementation. An ambiguous configuration with shared URL/key fields but no `owner_user_id` now fails with migration guidance instead of silently selecting trusted mode. Removing the legacy implementation is intentionally left to a focused migration PR.

The lifecycle cursor is currently single-worker state, not a distributed outbox. Setup UX, hosted credential provisioning, and OpenViking MCP tools remain separate work.

## Pull request overview

This PR updates DeerFlow’s optional `openviking` memory backend to use OpenViking’s official LangChain recorder/retriever and `openviking-sdk` transport, while extending DeerFlow’s memory injection seam to support per-turn (query-aware) recall that is request-local and not persisted into checkpoints.

**Changes:**

- Added an official OpenViking backend implementation + config validator, plus a selector that keeps legacy trusted-mode configs on a deprecated compatibility path.
- Extended `DynamicContextMiddleware`/prompt utilities to support `context_refresh_policy="turn"` backends: recall uses the latest real user message and injects memory only into that model call, caching it only in redacted run context.
- Added comprehensive unit + blocking-IO tests for the official backend, plus doc/config updates describing the new ownership/security model.

- `asyncio.run(self._retriever.aclose())` will raise `RuntimeError` if `close()` is ever invoked from a thread that already has a running event loop (common during async app shutdown). This can make backend shutdown/cleanup fail unexpectedly.

        try:
