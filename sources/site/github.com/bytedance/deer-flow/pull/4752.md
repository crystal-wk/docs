## Why

Discord starts a periodic typing-indicator loop for accepted inbound messages. Previously, message handling queued `_start_typing()` as a detached task.

If the channel stopped before that queued starter ran, `stop()` could finish cancelling and clearing the currently registered typing tasks, after which the delayed starter could install a new infinite typing loop. This left background work active after the channel lifecycle had ended and could continue sending typing events.

## What changed

- Discord now refuses to start new typing work once the channel is no longer running.
- Inbound message handling registers the typing loop before continuing instead of leaving a detached starter queued.
- Normal cross-thread shutdown schedules typing-task cancellation, awaiting, and map cleanup on the dedicated Discord event loop with a bounded wait.
- The Discord worker drains typing tasks in `_run_client()`'s `finally` block while its event loop is still usable, covering disconnect and exception exits.
- `stop()` distinguishes no loop, the current loop, a running foreign loop, and an already-stopped foreign loop; it never awaits old-loop tasks from the main loop.
- Added deterministic regression coverage for same-loop registration, normal cross-thread shutdown, stopped-loop shutdown, and worker exception cleanup.
- Documented the Discord event-loop ownership and shutdown invariant. 
 The public API, configuration, and message format are unchanged.

## Bug fix verification

Test paths:

- `tests/test_channels.py::TestDiscordChannel::test_stop_prevents_queued_typing_starter_from_creating_task`
- `tests/test_channels.py::TestDiscordChannel::test_stop_serializes_typing_cleanup_with_discord_loop`
- `tests/test_channels.py::TestDiscordChannel::test_stop_does_not_await_typing_tasks_from_stopped_discord_loop`
- `tests/test_channels.py::TestDiscordChannel::test_run_client_drains_typing_tasks_before_worker_loop_exits`

The original queued-starter test went red on the base implementation and green after the initial fix.

The cross-thread test then went red on the previous PR revision (`d13c69e3`): after `stop()` returned, `_typing_tasks` still contained a pending task. It is green on `33d087b8`.

The cross-thread test uses separate main and Discord event loops plus explicit `threading.Event` synchronization. It pauses `_start_typing()` after observing `_running=True` but before registering its task, then starts `stop()` on the main loop. It uses no arbitrary sleeps and also verifies that the registered task is fully done before `stop()` returns.

The stopped-loop regression went red on `33d087b8` with `RuntimeError: ... got Future ... attached to a different loop`. It creates a typing task on a dedicated loop, stops that loop first, and then calls `stop()` from the main loop. It is green on `2e4f2185`.

The worker-exit regression simulates a client disconnect exception and verifies that `_run_client()` drains the typing task on its owning loop before closing the client and returning.

[@AoHanBei](https://github.com/AoHanBei) Thank you for working on this fix. The issue described in [#4751](https://github.com/bytedance/deer-flow/issues/4751) is valid, and I was able to reproduce it deterministically on the referenced base commit: after`stop()`returns, a tracked and pending typing task can still be created. 
The overall direction of this PR is good. Removing the unnecessary fire-and-forget wrapper around `_start_typing()` and adding the `_running` guard fixes the queued-starter ordering problem when everything runs on the same event loop. The added test and documentation are also clear.

However, there is still one blocking issue. In production, `_start_typing()` runs on the dedicated Discord event-loop thread, while `stop()` runs on the main event loop. The `_running` check, the `_typing_tasks` insertion, and the cleanup performed by `stop()` are not serialized across those threads. The following ordering is therefore still possible:

- \_start\_typing() observes \_running=True;
- stop() sets \_running=False and clears \_typing\_tasks;
- \_start\_typing() then creates and registers a new typing task;
- stop() returns while the mapping still contains a pending task.

I reproduced this deterministically on the current PR using two real event loops and explicit synchronization. The existing regression test runs both the starter and `stop()` on the same event loop, so it does not cover the production cross-thread lifecycle boundary.

I suggest moving typing-task cancellation, awaiting, and map cleanup onto \_discord\_loop, for example by scheduling a cleanup coroutine with asyncio.run\_coroutine\_threadsafe() and awaiting it before closing the Discord client. Please also add a deterministic regression test with separate main and Discord event loops.

[@AoHanBei](https://github.com/AoHanBei) Thank you for addressing the previous review. The original cross-thread registration race is now handled correctly: typing-task cleanup is scheduled onto \_discord\_loop, and the new two-event-loop test covers the normal shutdown ordering.

However, there is still one blocking issue. If the Discord worker loop has already exited because of a disconnect or an exception while \_typing\_tasks still contains tasks owned by that loop, stop() takes this fallback branch: 
`else: await self._cancel_typing_tasks()` 
In that case, \_cancel\_typing\_tasks() runs on the main event loop and uses asyncio.gather() to await tasks owned by the stopped Discord loop. This raises: 
`RuntimeError: ... got Future ... attached to a different loop`

I reproduced this deterministically with the following sequence:

- Create a typing task on a dedicated Discord event loop.
- Stop the Discord event loop first.
- Call channel.stop() from the main event loop.
- stop() fails inside \_cancel\_typing\_tasks() with the cross-loop error.

The exception also prevents the remaining client shutdown, thread join, and state cleanup from running. There is also a related race where the Discord loop can stop immediately after the is\_running() check, leaving the cleanup future unfinished without a timeout.

I suggest cancelling and awaiting typing tasks from \_run\_client()’s finally block while the Discord loop is still usable. stop() should also distinguish between no loop, the current loop, another running loop, and another already-stopped loop, rather than awaiting old-loop tasks from the main loop. Please add a bounded wait for cross-thread cleanup and a regression test where the Discord loop exits before stop() is called.
