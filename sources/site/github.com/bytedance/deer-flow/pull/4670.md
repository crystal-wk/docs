# PR [#1](https://github.com/bytedance/deer-flow/issues/1) 正文（fix/admin-init-race）— 按上游模板改写，中文

## Why

`POST /api/v1/auth/initialize` 的"先计数、后创建"之间没有加锁。两个并发请求（双击、双标签页、或客户端重试与设置页竞态）可能同时观察到"系统尚无 admin"，从而创建出**两个不同的 admin 账户**——邮箱唯一约束只能拦截同邮箱的竞争。

已在本机运行的完整栈上复现：无 admin 状态下并发发两个不同邮箱的 initialize 请求，均返回 201，数据库中创建了两个 admin（时间间隔 1.9ms）。

## What changed

- 新增模块级 `_INITIALIZE_ADMIN_GUARD = asyncio.Lock()`（与现有 `_SETUP_STATUS_INFLIGHT_GUARD` 同模式）
- `initialize_admin` 的 count-then-create 整体放入锁内：后到的请求会看到先到的 admin 已创建，返回 409
- 行为变化：并发初始化时第二个请求从"也成功"变为"409 System already initialized"

Heads up: this lock only serializes the count-then-create within a **single process**. `docker-compose.yaml` exposes `GATEWAY_WORKERS` (default 1, but overridable), and the `_login_attempts` table further down in this same file already documents the same caveat for multi-worker / `gunicorn -w N` deployments.

With `GATEWAY_WORKERS > 1`, two `/initialize` requests carrying **different** emails can land on different workers, both observe `count_admin_users() == 0`, both call `create_user` with distinct emails (so no email-collision `ValueError` is raised), and both return 201 — i.e. the exact TOCTOU this PR targets is still open across processes. There is no DB-level uniqueness on `system_role='admin'` to backstop it either; only `email` is unique (`backend/app/gateway/auth/repositories/sqlite.py`, `UserRow`).

To genuinely close the race, the robust fix is DB-side: a partial unique index on the admin role (e.g. `CREATE UNIQUE INDEX ... ON users(system_role) WHERE system_role = 'admin'`), or a `SELECT ... FOR UPDATE` inside a transaction bracketing the count + insert so the second writer blocks at the DB. Short of that, mirroring the `_login_attempts` caveat with a one-line comment here would at least make the residual gap explicit for future readers (and for anyone enabling `GATEWAY_WORKERS>1`).

Minor test-isolation note: `asyncio.Lock` binds itself to the running loop on the contended (slow) path of `acquire()` (it stores `events.get_running_loop()` the first time it has to wait). Inside this `asyncio.run(_scenario())` the lock is contended, so it binds to the loop that `asyncio.run` created — and that loop is torn down as soon as `_scenario` returns. Uncontended acquires in later tests take the fast path and skip the loop check, so this passes today, but any future test in this file that causes real contention on `_INITIALIZE_ADMIN_GUARD` from a different loop will get `RuntimeError: <Lock ...> is bound to a different event loop`.

Cheap to harden: reset the lock in the autouse `_persistence_engine` fixture alongside the existing `deps._cached_*` resets, e.g. `auth._INITIALIZE_ADMIN_GUARD = asyncio.Lock()`.

The partial unique index also fires on code paths beyond `/initialize`. `create_oauth_user` (used by OIDC auto-provisioning in `app/gateway/auth/user_provisioning.py`) and every `create_user(system_role="admin")` call funnel through `SQLiteUserRepository.create_user`, whose `IntegrityError` handler (`backend/app/gateway/auth/repositories/sqlite.py:104-106`) re-raises _every_ unique violation as `ValueError("Email already registered: ...")` regardless of which constraint fired.

Concrete regression on the OIDC path: if an admin already exists and a second user listed in `provider_config.admin_emails` signs in via OIDC for the first time, the insert hits `uq_users_admin_role` → `IntegrityError` → laundered into `ValueError("Email already registered")`. `get_or_provision_oidc_user`'s `except ValueError` block then re-looks-up by `(provider, subject)` (no prior account for a first-time signer, so `None`), and raises HTTP 409 "An account with this email already exists" — even though that email is _not_ in the DB. The admin-slot conflict is surfaced as an email collision, and that user can never sign in via OIDC. The existing `test_oidc_*` tests mock `local_provider`, so they don't exercise this path.

Options:

- Differentiate at the repo layer: catch `IntegrityError`, inspect `exc.orig.diag.constraint_name` (postgres) / match on the index name (sqlite), or re-check `count_admin_users()` and raise a distinct `AdminRoleTakenError`. Then `get_or_provision_oidc_user` can fall back to creating a regular user (or surface a clearer error).
- Or have `user_provisioning.py` itself detect admin-slot-conflict and demote to `system_role="user"`.

As-is, the lock-side recount in `auth.py` masks this for `/initialize` only; the OIDC path has no equivalent recovery.
