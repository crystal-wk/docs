## Summary

- enforce one deployment-wide E2B capacity limit when sandbox ownership uses Redis
- atomically reserve in-flight creates and track live remote sandboxes in a single Redis Hash
- reconcile Gateway crashes and E2B timeouts from sandbox metadata without overwriting concurrent ledger changes
- fail closed when Redis or the initial E2B inventory is unavailable
- keep memory ownership and the existing process-local behavior unchanged
- run the real Redis/Lua integration tier in backend CI

## Why

[#4391](https://github.com/bytedance/deer-flow/pull/4391) added process-local capacity accounting and the `wait`, `reject`, and bounded `burst` policies. The remaining gap in [#4339](https://github.com/bytedance/deer-flow/issues/4339) is that separate Gateway processes can still create beyond the intended deployment limit. This change shares admission state across Gateways and repairs it after crashes or remote sandbox expiry.

## Safety

- a Lua reservation prevents two Gateways from taking the final capacity slot
- warm and active VMs remain counted until destruction is confirmed
- incomplete E2B inventories never delete ledger entries
- successful but stale complete inventories grace missing sandboxes before releasing their slots
- revision-CAS reconciliation cannot erase a concurrent reserve, track, or release
- mismatched hard-limit configurations fail closed

## Tests

- real Redis capacity, provider, ownership, and reconciliation tests: `297 passed`
- stale-inventory regression: a just-tracked sandbox remains capacity-counted when omitted once
- `ruff format --check`: passed
- `ruff check`: passed

Fixes [#4339](https://github.com/bytedance/deer-flow/issues/4339)

| Thanks for tackling the deployment-wide capacity gap. I found one correctness concern around reconciliation before approval.<br>The current flow reads the Redis revision, fetches the E2B inventory, and then treats a successful, non-budget-exhausted inventory as authoritative. The Lua reconciliation deletes every `s:` entry missing from that inventory. If a sandbox has already completed `track()` before the revision read, but `Sandbox.list()` has not surfaced it yet, the revision still matches and reconciliation removes a live slot. A peer can then reserve another slot and exceed the advertised hard limit.<br>The revision CAS protects against concurrent Redis mutations, and `complete=False` protects explicit list/pagination failures, but neither protects a successful yet stale inventory response. I could not find a documented read-after-create/strong-consistency guarantee for E2B listing.<br>Could we keep missing `s:` entries for a grace period or consecutive complete inventories, or verify each missing sandbox directly before deleting it? A regression test should cover a just-tracked sandbox being omitted from one otherwise complete inventory and ensure its slot is not released immediately. |

Nit (maintainability): the live-entry count is derived as `HLEN(KEYS[1]) - 3`, where `3` is the number of meta fields (`meta:state`, `meta:hard_limit`, `meta:revision`). The coupling is implicit: if a future change adds another `meta:` field, this under-counts by one and silently allows `hard_limit + 1` concurrent sandboxes — a paid-resource over-allocation with no error. The existing tests assert correctness only for the current three meta fields, so that regression wouldn't be caught.

Consider counting `s:` + `r:` entries directly (iterate `HKEYS` and count prefixes — O(hard\_limit), negligible), or at least derive the offset from a named meta-count constant so the invariant is explicit. Flagging because the capacity ceiling is the whole point of this ledger.
