## Why

The retained `backend/langgraph.json` compatibility path could not be used with 
the standalone LangGraph Studio development server:

- LangGraph Server 0.10 resolves graph factories directly from a module's 
 dictionary, while `deerflow.agents:make_lead_agent` was exposed only through 
 `__getattr__`, causing graph loading to fail.
- Studio authenticates locally as `langgraph-studio-user`, but the ordinary 
 owner filter hid the server-registered `lead_agent` because system assistants 
 have `created_by=system` rather than per-user metadata.
- Studio's subgraph request invokes DeerFlow's synchronous graph/configuration 
 setup inside the development event loop, which BlockBuster rejects unless the 
 CLI explicitly allows blocking operations.
- `langgraph.json` looked for `backend/.env`, while the normal DeerFlow setup 
 writes the shared environment file at the repository root.

Together these failures prevented the optional Studio workflow from discovering 
and rendering DeerFlow's lead-agent graph.

## What changed

- Publish a concrete, thin `make_lead_agent` package entrypoint while preserving 
 lazy imports of the heavyweight lead-agent graph.
- Point the standalone LangGraph configuration at the repository-level `.env`.
- Allow Studio's synthetic local identity to read/search only 
 `created_by=system` assistants. User-owned assistants and all other resources 
 remain owner-scoped.
- Document the development-only 
 `uv run langgraph dev --allow-blocking` startup command and its production 
 limitations.
- Add regression coverage for the concrete graph entrypoint, root environment 
 path, Studio system-assistant discovery, and unchanged owner scoping.

IMPORTANT: This read filter is not a safe boundary for server-registered assistants.

I reproduced both cases with the locked `langgraph dev` runtime on a synthetic merge of current `upstream/main`:

1. Studio creates a normal assistant (`POST /assistants` returns 200 and stamps `user_id=langgraph-studio-user`), but an immediate GET returns 404 and search returns `[]`. Assistant writes remain enabled, but their results become unreadable because this branch accepts only `created_by=system`.
2. If the create request supplies `metadata.created_by=system`, LangGraph preserves it and the assistant becomes readable/searchable. The global handler below overwrites only `user_id`, and LangGraph also treats `created_by=system` as privileged when enforcing assistant ownership for run creation, so this caller-controlled field cannot prove server registration.

Please make `created_by` server-owned on external assistant create/update paths (and account for already persisted rows before trusting it), and identify Studio with `isinstance(ctx.user, Auth.types.StudioUser)` instead of a reusable identity string. Then either let Studio read both genuine system assistants and its own assistants, or explicitly reject Studio assistant writes. Please add route-level create -> get/search coverage for both the ordinary and forged-marker cases.
