## What

Moves the Tenki sandbox provider off the retired `tenki-sandbox` PyPI distribution onto `tenki>=0.5.4`, and drops `project_id`, which the SDK removed.

## Why

Two upstream changes landed after the provider was merged:

1. **The distribution was renamed.** `tenki-sandbox` is frozen at 0.4.0 on PyPI — it received no further releases. Everything from 0.5 ships as [`tenki`](https://pypi.org/project/tenki/) (currently 0.5.4). The existing `tenki = ["tenki-sandbox>=0.4.0"]` extra can therefore never resolve to a current SDK.
2. **Project scoping was removed from the sandbox API in 0.5.x.** `Client.create()` no longer accepts `project_id`, and `IdentityWorkspace.projects` / `IdentityProject` no longer exist, so `_resolve_scope()`'s project auto-selection cannot work against the current SDK.

## Changes

- `packages/harness/pyproject.toml`: `tenki` extra → `["tenki>=0.5.4"]`; `uv.lock` updated to match.
- `community/tenki/provider.py`:
 - Removed `_resolve_scope()` and `_require_single()`. `workspace_id` is now passed straight through from config; when unset the SDK infers scope from the API key's workspace. This also drops a `who_am_i()` control-plane round trip from every create.
 - Removed the `project_id` config key and create kwarg.
- `community/tenki/README.md`, `backend/AGENTS.md`, `community/tenki/sandbox.py`: refer to the `tenki` distribution.
- `tests/test_tenki_provider.py`: dropped the `_FakeProject`/`_FakeWorkspace`/`_FakeIdentity` fixtures and `who_am_i()` fake (the provider no longer calls it). The three project-scope tests are replaced by two workspace-scope ones, and the create test now asserts `project_id` is _not_ forwarded.

## Import paths intentionally unchanged

`from tenki_sandbox import Client` still works and is left as-is: the `tenki` distribution ships `tenki_sandbox` as the implementation package plus a thin `tenki` alias. The alias is `__init__`\-only, so submodule imports do **not** work through it — verified against the real 0.5.4 wheel:

```
OK    from tenki import Client
OK    from tenki_sandbox.fs import SandboxFS
FAIL  from tenki.fs import SandboxFS  -> ModuleNotFoundError: No module named 'tenki.fs'
```

Since `sandbox.py` needs `tenki_sandbox.fs.SandboxFS`, keeping every import on `tenki_sandbox` is both correct and consistent. Only the _distribution_ name had to change.

## Behaviour change worth flagging

`sandbox.project_id` in `config.yaml` is now unused. Previously the provider would auto-select a project, or raise telling the operator to set it; now scope comes from `workspace_id` (or is inferred). Anyone who set `project_id` can delete it — the key is simply ignored, since `SandboxConfig` is `extra="allow"`. Happy to add an explicit deprecation warning if you'd prefer that to silence.

## Verification

- `uv run pytest tests/test_tenki_provider.py`: **61 passed / 1 skipped on main → 60 passed / 1 skipped on this branch**. The −1 is the three project-scope tests becoming two; the skip is the opt-in live-integration test in both cases.
- `uv run ruff check` and `ruff format --check` on the changed files: clean.
- `uv lock --check`: lock resolves consistently with the updated `pyproject.toml`. The `uv.lock` diff is exactly the Tenki package rename — I hand-edited that entry rather than committing a full re-resolution, so no unrelated resolver drift is included.

Not run: the full backend suite, and any live-sandbox exercise against the Tenki API (the live test stays skipped without credentials).
