## Why

`wecom-aibot-python-sdk==1.0.2` does not keep `connect()` running for the full WebSocket lifecycle. `connect()` returns after the handshake and creates the SDK's internal receive task.

Its public `disconnect()` method then schedules `_async_disconnect()` with `ensure_future()` and discards the task handle. As a result, `WeComChannel.stop()` could return before the receive task and socket finished closing.

The previous revision also allowed a concurrent `start()` to install a new client while `stop()` awaited an old task, after which the old stop could clear the new lifecycle state.

## What changed

- Serialize each WeCom channel instance's `start()` and `stop()` transitions with a lifecycle lock.
- Cancel and drain an in-progress SDK connection attempt.
- Obtain and await the SDK's actual asynchronous receive-task/socket shutdown operation.
- Keep ownership of the shutdown task until cleanup completes.
- Prevent the public synchronous `disconnect()` from creating a duplicate, untracked shutdown task.
- Preserve caller cancellation: cancellation of `stop()` propagates only after owned cleanup finishes and lifecycle state is cleared.
- Clear lifecycle references using identity checks.
- Correct the documentation: the SDK `connect()` task covers setup, not the full connection lifecycle.

Configuration, message routing, streaming replies, reconnection behavior, dependencies, and public APIs are unchanged.

## Compatibility and risk

The installed SDK does not expose a public awaitable disconnect API, so the compatibility logic for its asynchronous shutdown is isolated in one helper and guarded by capability checks. DeerFlow already depends on the SDK's \_ws\_manager compatibility surface for WebSocket media uploads. 
The only runtime cost is during shutdown: stop() now waits for the old connection cleanup before returning or allowing a restart.

[@AoHanBei](https://github.com/AoHanBei) Thanks for the detailed report and deterministic test. I agree there is a real race while the initial connect() coroutine is still processing cancellation. However, I don't think this PR fully establishes the lifecycle contract it claims.

In the locked wecom-aibot-python-sdk==1.0.2, WSClient.connect() returns after the handshake and after scheduling the SDK's internal \_receive\_task. disconnect() then schedules \_async\_disconnect() with ensure\_future() and returns no awaitable. Therefore, in the normal connected state, \_ws\_task is already done: awaiting it does not wait for the receive task or socket close. stop() can still clear \_ws\_client and return while the previous SDK lifecycle is cleaning up, so an immediate restart can still overlap it. The new test uses a connect() coroutine that never returns and therefore does not model the installed SDK contract.

There is also a new start/stop race introduced by the added await. A concurrent start() can install a new client/task while stop() is awaiting the old task; when stop() resumes, it unconditionally clears the new \_ws\_task and \_ws\_client, leaving an active but untracked connection while \_running remains true.

Please obtain and await the actual SDK shutdown operation, serialize the channel lifecycle (or use generation/identity checks), and add tests where connect() returns before a blocked async disconnect cleanup plus a concurrent start during stop. The documentation should also avoid stating that the connect() task spans the full channel lifecycle.
