Fixes [#4694](https://github.com/bytedance/deer-flow/issues/4694)

## Why

Every Gateway process starts `ScheduledTaskService`. During startup, the scheduler treated every `queued` or `running` scheduled-task run in the shared database as a local leftover. In a multi-Pod deployment, a newly started Pod could therefore interrupt a live run owned by another Pod, release `uq_scheduled_task_run_active`, and allow the next scheduler tick to launch a duplicate execution.

This is especially harmful for `overlap_policy=skip`: a peer restart can defeat the single-active-run guarantee even though the original run is still executing.

## What changed

- The scheduler remains single-instance by default with `scheduler.multi_instance: false`.
- Operators can explicitly enable lease-aware scheduler recovery across Gateway instances with `scheduler.multi_instance: true`.
- Multi-instance scheduler startup fails fast unless the deployment uses shared Postgres, `run_ownership.heartbeat_enabled: true`, and `run_events.backend: db`.
- Startup and periodic reconciliation preserve scheduled rows backed by a live `pending`/`running` run lease and reclaim only terminated/recovered runs or expired leases through an atomic `claim_for_takeover()` update.
- Scheduled-run and parent-task association recovery uses metadata when post-launch bookkeeping missed both links, while stale parent `last_run_id` values are ignored.
- Queued pre-launch rows reuse the existing `scheduled_tasks.lease_owner` / `lease_expires_at` dispatch lease. Multi-instance manual triggers acquire the same short lease before creating a scheduled run row.
- `update_after_launch()` fences stale Pods by expected lease owner, so delayed writes cannot overwrite a newer Pod's status or lease.
- Multi-instance due-task claims use a short Postgres transaction advisory lock and count active scheduled rows plus valid dispatch reservations, making `max_concurrent_runs` a shared global cap.
- Existing Postgres `FOR UPDATE SKIP LOCKED` claims, the scheduled-run partial unique index, and run ownership leases remain the concurrency primitives; no leader-election service is introduced.
- Configuration version, reload-boundary descriptions, README, backend architecture, and Helm documentation are synchronized.

The lease design reads well and the earlier round looks fully addressed in [f408280](https://github.com/bytedance/deer-flow/commit/f4082800f538ae3e3f071f45f7c3e28b0ec2a2dc). Adding a few items from a downstream-fork / upgrade perspective — none block merge, but the first two should land in the PR description or docs before release.

**\[P2\] Undocumented breaking change: multi-worker + scheduler now refuses to start**

- Location: `backend/app/gateway/deps.py` (`_enforce_postgres_for_multi_worker`)
- Problem: on `main`, `GATEWAY_WORKERS>1` with `scheduler.enabled=true` starts silently (unsafely). After this PR it raises `SystemExit` unless `scheduler.multi_instance=true` plus Postgres / `run_events.backend=db` / `run_ownership.heartbeat_enabled=true`. Any existing deployment running that (mis)configuration will fail to boot after upgrade.
- Suggested fix: add an **Upgrade Notes** section to the PR description (and release notes) calling this out explicitly, so operators audit their config before rolling out.

**\[P2\] `max_concurrent_runs` semantics change from per-instance to global**

- Location: `backend/packages/harness/deerflow/persistence/scheduled_tasks/sql.py` (`claim_due_tasks` budget accounting under the advisory lock)
- Problem: in `multi_instance` mode the cap is now cluster-wide (including dispatch reservations), not per-Pod. Capacity planned as "cap × replicas" silently becomes "cap total". The Helm values comment mentions it, but `docs/CONFIGURATION.md` and the upgrade notes should state it plainly.
- Test/docs: a one-line note in the `scheduler.multi_instance` config docs suffices.

**\[P2\] `multi_instance` is startup-only; toggling it requires a coordinated restart**

- Location: `backend/packages/harness/deerflow/config/reload_boundary.py`
- The field is captured into the service instance and hot reload does not apply it; the boundary comment already says every Pod must restart together. Worth surfacing in the same Upgrade Notes — a config push without restart leaves operators believing multi-instance recovery is on when it is not.

**\[Suggestion, non-blocking\] Gate on capabilities rather than the backend name**

- Location: `deps.py`, the `backend != "postgres"` checks
- The real requirement is a set of primitives (row locks with `FOR UPDATE SKIP LOCKED`, a transaction-scoped named lock, shared durable storage), not the Postgres brand. Two follow-ups worth an issue:
 1. PG-compatible databases (GaussDB, CockroachDB, etc.) and transaction-mode poolers pass the name check but may not support `pg_advisory_xact_lock` — the gate would silently admit an unverified combination. A startup probe that acquires/releases the advisory lock and runs one `SELECT ... FOR UPDATE SKIP LOCKED` in a throwaway transaction would fail closed with an exact missing-primitive message.
 2. When a second shared-storage backend lands, the dialect-specific bits (`pg_advisory_xact_lock`, the `dialect.name == "postgresql"` branch) will need a small named-lock abstraction anyway; the probe defines its acceptance checklist.
- Fine as a follow-up issue, not this PR — postgres is the only shared backend today and the name check matches the supported matrix.

For context on the last point: we run a downstream fork on GaussDB and would be happy to validate the probe-based gate there and contribute it back.
