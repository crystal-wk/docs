### Description

Managed Lark/Feishu CLI commands fail inside DeerFlow sandboxes when the CLI tries to create its coordination lock directory.

The managed integration mounts `/mnt/integrations/lark-cli/config` read-only to protect the long-lived `appSecret`. Current `lark-cli` releases create `config/locks` while handling API commands, so an otherwise valid connected integration fails at runtime.

### Reproduction

1. Install and connect the managed Lark CLI integration.
2. Run DeerFlow with the AIO sandbox provider.
3. Ask the agent to execute a Lark command such as `lark-cli docs +fetch ...`.

Observed error (credential path redacted):

```
API call failed: failed to create lock directory: mkdir [redacted]/locks: read-only file system
```

### Expected behavior

Lark CLI commands should be able to create coordination locks without making the credential-bearing config directory writable.

### Root cause

DeerFlow mounts the entire per-user `config` directory read-only. `lark-cli` uses a nested `config/locks` directory for runtime coordination, but DeerFlow neither creates nor mounts that directory writable. The same mount contract also affects remote Provisioner Pattern A and the broker sidecar Pattern B.

### Proposed fix

- Pre-create the per-user `config/locks` directory with owner-only permissions.
- Keep the parent `config` mount read-only.
- Add a nested writable mount only for `config/locks`.
- Propagate the nested mount through local AIO, remote Provisioner, and broker-sidecar paths.
- Add regression tests that pin the read-only parent / writable child behavior.

This preserves the existing credential protection while restoring CLI compatibility. I have a tested patch ready and will link the PR here.

This is a clean example of **when immutable config meets mutable runtime state, the boundary must be explicit** — and your proposed fix (pre-create `config/locks`, mount parent read-only, nested writable mount for locks) is exactly the right structural move.

The root cause you identified (DeerFlow mounts the entire `config` directory read-only to protect `appSecret`, but `lark-cli` creates `config/locks` at runtime) is the classic tension between:

- **Config immutability** (appSecret must not be writable by the sandbox), and
- **Runtime coordination** (CLI needs a place for transient locks).

Your fix separates those two concerns cleanly: credentials stay immutable, locks live in a writable sidecar. The key principle (and what we've learned building [SwarmAI](https://github.com/xg-gh-25/SwarmAI)) is: **the mount contract must be tested**, not just documented. Your "add regression tests that pin the read-only parent / writable child behavior" is critical — without it, a future refactor (e.g., mount the whole dir writable "for convenience") silently degrades the security boundary.

In our multi-MCP-server setup, we hit the same pattern with server state directories: each MCP server gets a read-only mount for its config (connection strings, API keys) and a writable mount for its runtime state (caches, locks, temp files). The gate that enforces this lives in the server bootstrap: if the state dir is missing or not writable, the server refuses to start (fail-closed, loud). That way mount regressions are caught at boot, not at first API call.

Your fix also nicely demonstrates **why pre-creation matters**: if DeerFlow waited for `lark-cli` to create `config/locks` and then tried to mount it writable, there's a TOCTOU window where the first call fails (dir doesn't exist yet, can't mount). Pre-creating it makes the mount contract static (dir always exists, always writable) and eliminates the race.

Looking forward to the PR — this will unblock the managed Lark integration and set the pattern for any future CLI that needs runtime coordination under a read-only config mount.
