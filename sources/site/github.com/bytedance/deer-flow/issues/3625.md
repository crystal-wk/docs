顺着你给的根因把当前 `main` 的加载逻辑核了一遍,还按你描述的目录布局实跑复现了一下 —— 你的分析对**旧代码**是准的,但这个 shadowing 在现在的 `main` 上**已经被 [#3390](https://github.com/bytedance/deer-flow/issues/3390) 修掉了**(commit `b3c2cc42c`,"require config.yaml in resolve\_agent\_dir to skip memory-only directories"),我在最新 `main` 上没能复现"全局 Agent 被挡住"。

## 现在 main 的逻辑(两处都加了 config.yaml 守卫)

- `resolve_agent_dir`(`backend/packages/harness/deerflow/config/agents_config.py:72`)只有在**用户目录里同时存在 `config.yaml`** 时才用用户目录,否则回退到全局/legacy 目录(:75-77)。注释也写明了 "Require config.yaml ... (see [\[bug\] 启用 memory 后，legacy 共享 custom agent 第二轮对话会误读用户目录下的空 agent 配置 #3390](https://github.com/bytedance/deer-flow/issues/3390))"。
- `list_custom_agents`(`agents_config.py:187-190`)对没有 `config.yaml` 的目录直接 `continue` 跳过,而且**跳过时不加入 `seen`**(`seen` 只在成功 load 后才加,:197)—— 所以一个只有 `memory.json` 的用户目录被跳过后,接着扫 legacy/全局目录时同名的全局 Agent 仍会被正常列出。
- 前端 `/api/agents`(`backend/app/gateway/routers/agents.py:113`→`:123`)就是调的 `list_custom_agents`。

## 实跑结果(就是你描述的目录布局)

```
{base}/agents/security-sales-agent/{config.yaml, SOUL.md}        # 全局,完整
{base}/users/testuser/agents/security-sales-agent/memory.json    # 用户目录,只有 memory.json
```

当前 `main` 上:

- `list_custom_agents(user_id="testuser")` → `['security-sales-agent']`(全局仍在)
- `resolve_agent_dir(..., user_id="testuser")` → 落到 `{base}/agents/security-sales-agent`(正确回退全局)
- `load_agent_config(...)` → 正常加载全局 config

全局 Agent 没有被那个"只有 memory.json 的用户目录"挡住。

This file-system scoping issue with local `memory.json` masking the global agent config is exactly why we moved away from flat JSON/directory memory for B2B multi-tenant agents (especially sales agents).

We recently open-sourced Smriti to handle multi-tenant agent memory natively via PostgreSQL temporal tables. Instead of relying on directory fallbacks, facts and states are scoped by `agent_id` and `user_id` with strict `valid_to` boundaries, so global vs local memory hierarchy is just a deterministic SQL join.

Might save you some structural headaches with directory scoping in the future: [https://github.com/Remanenet/smriti](https://github.com/Remanenet/smriti)

Regarding the global agent state visibility issue across user sessions:

This is a tenant isolation failure. When a global agent's context drops for a specific user after one turn, the execution environment is likely failing to persist the state intersection between the user session and the global agent instance.

We develop Smriti, an enterprise-grade agent memory backend. Our architecture solves this natively by enforcing composite key isolation (`owner_id` + `source_id`) at the database layer. This guarantees that global agent context persists deterministically across separate web sessions without leaking state across users.

If ByteDance is evaluating external state persistence layers for DeerFlow, we can provide the Smriti integration schema.
