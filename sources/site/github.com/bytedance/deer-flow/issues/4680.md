### Problem / motivation

我在页面上创建了custom agent，怎么在我的lead\_agent上调度呢？

用户登录 DeerFlow 
页面创建 Custom Agent A、Custom Agent B 
主 Agent 自动看到 A/B 
主 Agent 可以 delegate\_to\_agent("Custom Agent A", task) 或者 delegate\_to\_agent("Custom Agent B", task) 
主 Agent 汇总 A/B 结果

比如我们说我要做一个创意视频，我建了一个谋划创意的智能体 Custom Agent A， 我又建了一个专门写文案的智能体 Custom Agent B，还有一个专门生成高清视频的智能体 Custom Agent C，我可以在主智能体里面说，“每天你们三个智能体协作帮我生成三个关于大模型相关的科普视频”，这样主智能体能够创建定时任务，到点出发，实现三个智能体写作。

类似Hermes Agent或Hermes Studio里面的群聊功能，可以建一个群把这三个智能体叫到一起，给他们安排任务，这才是叫做多智能体协作把

### Proposed solution

主 Agent 可以 控制Custom Agent A、Custom Agent B、Custom Agent C相互协作

我们的业务场景下有相同的需求，补充我们实践中遇到的场景：

**1\. 不是所有的多智能体协作都是全自动场景** 
比如用户创建了 Custom Agent A（调研）和 Custom Agent B（执行分析），在科研分析等领域，典型的协作模式是：

- Agent A 产出调研报告 → **用户审阅** → Agent B 基于报告执行分析
- 或者反过来：Agent B 先产出分析结果 → **用户审阅** → Agent A 检索相关资料 → **用户审阅** → Agent B 继续下游分析 
 每个阶段的切换都有 Human-in-the-loop。而且 Agent B 自身在执行过程中也有与用户的交互断点（比如生成执行计划后需要用户确认才继续）。这意味着 `delegate_to_agent` 不能只是 fire-and-forget，还需要支持 custom agent 内部的 `interrupt()` 能冒泡到主 agent 的用户交互层，让用户在 custom agent 执行过程中也能审阅和干预。

**2\. Agent 间的 Artifact 传递** 
原issue中提到主Agent汇总A/B结果，但当Agent产出结果过大（比如一份完整的调研报告）时，通过Coordinator的prompt中转会撑爆上下文窗口，建议设计中考虑配套的Artifact共享层。

[@mandymonkey](https://github.com/mandymonkey) 感谢补充（你的评论和我上面的方案同步几乎同时发出，这里补上对两点的回应）：

**1\. Human-in-the-loop**

阶段级的 HITL（A 产出 → 用户审阅 → 派 B）在这条路线下天然成立：编排者就是 lead 会话本身，每个阶段切换就是一个对话轮次——lead 派 A、把结果汇总给你审阅，你在对话里表态后 lead 再派下一个 agent。这部分第一批就能用，不需要额外机制。

子 agent **执行中途**的交互断点（比如 B 生成执行计划后暂停等确认）第一批明确不做：当前委派执行是 one-shot（子图不带 checkpoint、不可恢复），子 agent 的 `ask_clarification` 也被有意禁用（与内置 general-purpose 和 config.yaml custom subagent 的既有约定一致——与用户交互是 lead 的职责边界）。要让子 agent 内部 `interrupt()` 冒泡到主会话，需要子图 checkpoint + 可恢复执行 + 嵌套人机交互卡片一整套机制，和 [#1731](https://github.com/bytedance/deer-flow/issues/1731) 正在评估的编排架构强相关，建议单开 issue 跟进。当前的替代做法：把「需要确认的东西」本身作为一个阶段产出——让 B 先产出执行计划返回，你审阅后 lead 再派 B 执行。

**2\. Artifact 传递**

这点现有机制已经覆盖大半：同一 thread 内委派的子 agent 与 lead **共享同一个 sandbox 工作区**（`/mnt/user-data/...`），A 可以把完整报告写成文件、只向 lead 返回路径 + 摘要，B 直接读文件继续下游分析——「通过 Coordinator 的 prompt 中转撑爆上下文」靠文件约定可以避免。另外还有两道现成防线：超大的工具结果会被 tool-output 预算中间件自动外置为文件引用；委派账本记录的是 result 摘要/引用而非全文。更通用的「产物句柄注册/跨轮消费」是个独立课题（[#4652](https://github.com/bytedance/deer-flow/issues/4652) 里也讨论过同类问题），值得单开 issue。

这里需要先澄清 DeerFlow 两条机制的边界：

- DeerFlow 的 subagent 是为任务执行效率设计的：lead agent 通过 task 
 工具派生一次性、任务级的工作线程做并行/专项执行，执行完即回收，意味着它们不是有独立身份的"智能体"。
- 页面上创建的 Custom Agent 是完整的 assistant 级配置（独立的 soul / skills / model settings)，每个 
 custom agent 运行自己的 lead agent graph。

让 lead agent 去调度 custom agent，意味着 graph 之间互相调用、跨 graph 
状态互通、定时触发和群聊式协作——这属于 Agent 编排层（orchestration layer) 的职责。直接在 DeerFlow 
内部实现会把 harness 与调度层耦合在一起，显著超出它该承担的复杂度。

多智能体协调还是比较复杂的。 
目前 lead\_agent 任务下发是一次性工作，lead\_agent 把任务分解了之后，直接调用子智能体派发任务信息。 
但是在长时任务中，这种任务相关的上下文信息是需要持续不断地补充和完善的， 在这种情况下我们就需要考虑怎么更好地来让Agent之间的信息进行共享。

如果是使用tags方式来进行沟通的话， 相关任务的上下文是共享个不同的Agent的， Agent 与 Agent之间的关系是平等，每个Agent可以更加自主地获取与任务相关的上下文信息。

[@gaoxuapple](https://github.com/gaoxuapple) [@mandymonkey](https://github.com/mandymonkey) 补充同步一下：结合上面对 Custom Agent / Subagent 边界的澄清，以及维护者关于长时任务中 Agent 共享上下文的讨论，我准备先暂停此前提出的实现与 PR 计划，等待整体架构方向进一步对齐。

我前面提到“核心诉求完全会实现”，这个表述下得过早，这里做一下修正。当前 `task`/subagent 更适合一次性任务委派；如果直接把页面创建的 Custom Agent 桥接进 `task` 通道，实际上会把一个拥有独立 graph、配置和记忆语义的完整 Assistant，当成一次性 worker 执行，并不能完整覆盖你们提到的长时协作、内部 HITL 和持续上下文共享场景。
