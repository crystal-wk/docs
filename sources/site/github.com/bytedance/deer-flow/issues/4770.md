感谢反馈。我们核对了日志，有两个关键信息需要先确认：

1. `Worker stats` 中的 `max=32`、`available=31`、`active=1` 表明 `--n-jobs-per-worker` 已经生效，总容量是 32；因此当前现象并不是 worker 上限只有 1。
2. 复现命令仍然直接启动 `langgraph_cli dev`，日志版本是 `langgraph_api 0.7.65`。DeerFlow 最新 `main` 已通过 [feat(gateway): implement LangGraph Platform API in Gateway, replace langgraph-cli #1403](https://github.com/bytedance/deer-flow/pull/1403) 切换到 Gateway 内置运行时，当前 `make dev` 不再启动 2024 端口的独立 `langgraph dev`。因此这份日志目前还不能证明最新 `main` 上存在同样的问题。[\[Bug\] LangGraph 队列堵塞导致对话无响应 #1565](https://github.com/bytedance/deer-flow/issues/1565) 是相同旧运行时队列现象的历史记录。

请更新到最新 `main` 后直接使用 `make dev` 复测，并补充以下信息：

- `git rev-parse HEAD` 的输出；
- 5 个并发请求使用的是同一个还是不同的 `thread_id`；
- 使用的模型类和 provider（请隐藏密钥）；
- `make support-bundle` 的摘要，以及从第一个请求开始到队列堆积期间的完整 Gateway 日志。

同一个 `thread_id` 上的运行不会并行推进，会根据 multitask strategy 排队、拒绝或中断；如果最新 Gateway 运行时下，5 个不同 `thread_id` 仍然只能运行 1 个，我们会继续按当前并发问题排查。

如果暂时仍需使用旧的 `langgraph dev` 启动方式，也请去掉 `--allow-blocking` 再复现一次，以便同步阻塞 I/O 直接暴露 traceback。

感谢确认，这就解释了日志中的 `n_running=1, n_pending=4`：5 个请求共用同一个 `thread_id` 时，它们是在同一条对话状态/checkpoint 流上运行，不能作为 5 个独立任务并行修改；旧版 `langgraph dev` 会将后续请求排队。`--n-jobs-per-worker=32` 是 worker 对不同 thread 的总并发容量，不是单个 thread 内的并发数。

如果这 5 个请求是独立任务，请分别使用不同的 `thread_id`。如果它们是同一段对话中的连续输入，则需要按顺序处理，或在最新 Gateway 中选择适合的 multitask strategy（`reject` / `interrupt` / `rollback`）。

因此，从目前日志看，这不是系统级死锁，而是同一 thread 的预期排队行为。如果第一个 run 本身一直无法结束，请另行提供该 run 从开始到卡住的完整日志及模型/provider 信息，我们再排查首个 run 为什么没有完成。
