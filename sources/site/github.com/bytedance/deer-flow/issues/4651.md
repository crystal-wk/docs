# RFC: Deterministic Tool Receipts & Layered Subagent Result Verification

**Status:** Draft for feedback. **Revision 2** incorporates review by [@AnnaSuSu](https://github.com/AnnaSuSu) and [@willem-bd](https://github.com/willem-bd) (vocabulary layering + anti-automation-bias rendering rules; no-citation→UNVERIFIED heuristic; workspace-scoped file checks; split render flag; typed claim bindings; judge input scope). A pilot implementation of Layer 1 (tool receipts) is open as PR [#4659](https://github.com/bytedance/deer-flow/pull/4659) (branch `feat/tool-receipts` on a contributor fork, full backend suite green) and reflects this revision. 
**Affects:** `backend/packages/harness/deerflow/agents/middlewares/` (new), `backend/packages/harness/deerflow/subagents/`, `backend/packages/harness/deerflow/tools/builtins/task_tool.py`, `backend/packages/harness/deerflow/agents/thread_state.py`, `backend/packages/harness/deerflow/config/`, `config.example.yaml`.

---

## TL;DR

DeerFlow has **no mechanism for reviewing subagent results**. The lead agent receives a free-text self-report from each subagent ("Task Succeeded. Result: ...") and is instructed by prompt to "verify against primary evidence" — but no primary evidence exists in a form the verifier can use. A subagent that ran off the rails but returns `completed` has its conclusions adopted wholesale.

This RFC proposes a three-layer verification stack, ordered by cost, built on one shared primitive — the **tool receipt**, an immutable per-call execution fact stamped by the runtime (not the LLM):

1. **Receipts (zero LLM cost)** — every tool call gets a deterministic fact record (`tool_name`, `status`, `args_sha256`, `output_sha256`, `output_bytes`, `created_at`); subagent reports cite receipt ids `[rN]`; the parent **deterministically cross-checks citations against the execution record**. This kills the "false success" class — claims about actions that never happened or that failed.
2. **Acceptance checklist (zero~low cost)** — delegations carry `acceptance_criteria`; decidable leaves (`file:<path> exists|non-empty`) are checked in code; undecidable leaves are marked `UNVERIFIED`, never silently passed.
3. **Selective one-shot judge (one small-model call, opt-in, default off)** — fires at most once per delegation, only when unchecked leaves remain. One round, never retried automatically.

The design is the convergence point of current research and production practice: full-trajectory LLM judging of every subagent result has been falsified on both cost and quality grounds; what works is _deterministic checks as the base, LLM judgment spent only where undecidable_.

---

## 1\. Problem: subagent self-reports are adopted without verification

### 1.1 What happens today

The result flow (`tools/builtins/task_tool.py`, `subagents/status_contract.py`):

- A subagent's terminal result returns to the lead as a `ToolMessage`: `content = "Task Succeeded. Result: <free text>"`, with structured metadata (`subagent_status`, `stop_reason`, `result_brief + sha256`) in `additional_kwargs`.
- The **only** verification is a prompt instruction in the lead's system prompt: _"Verify and synthesize the returned result against primary evidence"_ (`agents/lead_agent/prompt.py`, delegation workflow step 6).
- The delegation ledger (`agents/middlewares/delegation_ledger.py`) renders status guidance ("may retry with a changed plan"), but this is text guidance — nothing programmatic.
- The 14-middleware chain (`agents/middlewares/tool_error_handling_middleware.py::_build_runtime_middlewares`) contains **no result-review stage**.

### 1.2 Why the prompt instruction is hollow

Verifying a claim like "wrote the analysis to /outputs/report.md" costs roughly **re-executing the action** (stat the file, re-fetch the URL) — and the child's intermediate `ToolMessage`s live on the other side of the subagent boundary, in the child's own checkpoint. The parent's context only sees the delegation call and the summary text. So "verify against primary evidence" asks the model to check against evidence it does not have, at a cost it will not pay.

### 1.3 Why existing records don't help

DeerFlow _does_ record execution: raw tool output in `ToolMessage.content` (checkpointed), sandbox audit logs, run journals, LangSmith traces. But none of these are _usable evidence for verification_:

| Record | Why it can't serve as evidence |
| --- | --- |
| `ToolMessage.content` | Unstructured free text; mutated by truncation/sanitization; removed by compaction; and crucially, **on the child's side of the boundary** |
| Sandbox audit / journal / traces | Built for ops observability — no code path in the agent loop consumes them for verification |

The gap is not recording; it is **facts a verifier can reach and compare without re-execution**.

---

## 2\. Prior art and why this shape

### 2.1 Research convergence (2025–2026)

- **Tool Receipts (NabaOS, arXiv 2603.10060)** — runtime-issued, HMAC-signed execution receipts per tool call; LLM replies are cross-checked against the receipt ledger deterministically. Detects fabricated tool references (94.2%), count distortions (87.6%), false negatives (91.3%) at **<15ms and ~zero token cost**. The strongest "good _and_ cheap" design point. Its boundary: verifies tool-call facts, not reasoning quality.
- **Mind2Web 2 (ICML'25)** — generation-verification asymmetry: verification is far easier than generation, so decompose judging into a tree of binary rubric leaves. Checklist decomposition _is_ the cost-reduction mechanism.
- **Agent-as-a-Judge (Meta)** — near-human alignment but up to tens of minutes of compute per task. The quality ceiling and the cost floor; not a production option for every delegation.
- **Production consensus (OpenHands, Claude Code, OpenAI Agents SDK, …)** — deterministic step-level verifiers first (<10% overhead), CRITIC-style grounding only at side-effect boundaries, Reflexion-style reflection at most one round on retryable tasks (each extra round ≈ 3× tokens with no gain).

**Conclusion drawn:** receipt-grade determinism as the base (free), checklist decomposition (cheap), selective judge only on the ~1% undecidable paths (expensive but rare).

### 2.2 Hermes Agent (closest shipped design)

Hermes (`NousResearch/hermes-agent`, v0.19.1) also has no code-level review, but ships two ideas worth borrowing explicitly:

- Its delegation tool description hard-codes: _"Subagent summaries are SELF-REPORTS, not verified facts… require the subagent to return a verifiable handle (URL, ID, absolute path, HTTP status) and verify it yourself."_ Instructions embedded in the tool schema are seen on every call, unlike a system-prompt paragraph.
- It hard-fails empty subagent summaries ("zero-content success").

DeerFlow already exceeds Hermes in one respect: the deterministic delegation ledger with `stop_reason` distinguishing budget-capped from genuinely failed runs. What Hermes has and DeerFlow lacks is the _verifiable handle_ discipline — receipts generalize it.

## 3\. Design

### 3.1 The receipt: an immutable execution fact, stamped at the one moment truth is whole

```
ToolReceipt = {
  tool_call_id, tool_name,        # linkage, self-contained for transport
  status,                         # reuses deerflow_tool_meta's 3-tier status
  args_sha256, output_sha256,     # input/output fingerprints (16 chars)
  output_bytes, created_at,       # scale + time anchors
}
```

**Stamping point: `wrap_tool_call` in a new `ToolReceiptMiddleware`.** This is the _only_ point in the system where all four conditions hold simultaneously:

1. Both inputs in scope (`request.tool_call` + raw result) — anywhere else, recovering args requires a fragile cross-message join that silently breaks after compaction.
2. Content not yet rewritten by sanitization/truncation — the receipt captures **execution truth** ("what the tool returned"), deliberately distinct from delivery truth ("what the model saw").
3. `deerflow_tool_meta` status already stamped (ordering guard-enforced at build time).
4. Shared by lead and subagent chains alike — one stamping site covers both, which is what makes parent-side harvesting possible without a second code path.

**Carrier: `ToolMessage.additional_kwargs["deerflow_tool_receipt"]`.** LangChain's official extension slot, already used by `deerflow_tool_meta`; serialized into checkpoints for free. Alternatives considered and rejected: lazy derivation (loses execution-truth semantics, fragile joins, no timestamp source), a dedicated state channel (redundant storage = drift risk; breaks the "model's view ≡ ledger's content" invariant under compaction), `artifact` field (a second convention beside `tool_meta`).

**Derived, not stored.** Receipts ride the message stream; the ledger is _re-derived_ on every model call via `extract_tool_receipts`, which assigns stable display ids `r1..rN` positionally over the append-only stream. The same function serves in-context rendering, executor harvesting, and tests. No dedicated channel, no consistency maintenance: compaction removes a message, its receipt vanishes with it — exactly what the model sees.

**Model-visible ledger.** On every model call, the middleware renders the receipt ledger (2,000-char budget, newest-first eviction) and injects it as an ephemeral hidden `HumanMessage` (`hide_from_ui`, never written back to state — the `DurableContextMiddleware` pattern, reusing `_insert_after_leading_system_messages`). The ledger header always carries its evidence boundary: _"Execution evidence only — receipts record that a call happened and its status; they do not validate claim correctness or task acceptance."_ This fixed limitation line is a hard requirement (anti-automation-bias, §3.4 rule 4).

**Rendering is split from stamping** (review feedback on the always-on token tax): `receipts_enabled` (stamping) stays on by default; rendering has its own mode. Subagent contexts always render — citations are produced there, and a subagent without the ledger reverts Layer 1 to inert. Lead contexts render only while processing subagent results (a delegation completion exists in the message stream), the one place the lead needs citation context. Bounded cost: ≤~500–600 tokens per model call when rendered, zero otherwise.

**Failure-isolated.** Stamping/injection exceptions are logged and swallowed; receipts can never break tool execution or result delivery.

### 3.2 Crossing the boundary (Layer 1 consumption)

```
child messages (stamped ToolMessages)
  → executor harvests at terminal status via extract_tool_receipts(final_state.messages)
  → SubagentResult.tool_receipts
  → status_contract: additional_kwargs["subagent_tool_receipts"]
  → parent-side receipt_verification.verify_receipt_citations(report_text, receipts)
  → verdict rendered into the delegation ledger line
```

`verify_receipt_citations` is pure code: extract `[rN]` citations from the subagent's report, classify each as `resolved` (exists, status=success) / `failed` (exists, status=error) / `unknown` (not in the execution record). The ledger line gains, e.g.: `receipts: 2 citations resolved, 1 unknown — execution evidence only, does not validate claim correctness`.

**Two hardening rules (review feedback):**

1. **No-citation claims are `UNVERIFIED`, not neutral.** A completed report containing action claims (file written, command run, upload done) with _zero_ citations is a weak-negative signal, not a clean bill — the classifier flags `no_citation_claims` and renders `UNVERIFIED — action claims without receipt citations`. Without this, the reports most worth suspecting would score the cleanest.
2. **Rich anchors `[r2 write_file]`.** Citations may carry the tool-name label; `verify_receipt_citations` then sanity-checks claim-evidence coherence (a file-write claim anchored to a `web_search` receipt gets flagged `failed` with a mismatch note).

**Verdict vocabulary convention** (aligning _structure_ with the run delivery receipt, §3.4 — but **not** vocabulary): `{source: "receipt_citations", requirement: "cited_ids_in_execution_record", citation_resolved: bool, cited/resolved/failed/unknown: [...]}`. The boolean is deliberately named `citation_resolved`, not `satisfied`: this layer is advisory execution evidence, and strong-positive words (`satisfied`/`verified`/`passed`) are reserved for the runtime hard gate, so the model never conflates the two.

### 3.3 Layers 2 & 3: checklist and selective judge

- **Checklist.** `task` tool gains `acceptance_criteria: list[str]`. Deterministic leaf families, checked in code:
 - `file:<path> exists|non-empty` — via `read_current_file_content` (the `ReadBeforeWriteMiddleware` precedent), **scoped to the shared thread workspace**: the path must resolve under the thread's `outputs_path`/`workspace_path` (which the executor propagates into the subagent). Paths outside the shared domain return `checked=False` (`UNVERIFIED`) rather than assuming cross-sandbox reachability — if a future isolated-sandbox provider breaks sharing, leaves degrade to UNVERIFIED instead of misjudging.
 - **Typed claim bindings** (review feedback): `file_written:<path>` (existence + read-back) and `tests_passed:<command>` (the claim must anchor to a _specific_ recorded execution — a matching bash receipt with status=success and a test-summary shape — not merely to some successful call). Full parent-side re-execution is deferred to the read-only verifier (§6 follow-ons). 
 Any other leaf returns `checked=False` and is rendered `UNVERIFIED` — never silently passed. Results travel in result metadata and a rendered text section.
- **Judge.** Config-gated (`verification.judge_enabled`, default **off**). Fires only when: status == completed ∧ unchecked leaves exist. One `create_chat_model(thinking_enabled=False)` call (the `TitleMiddleware` pattern), verdict `supported|not_supported|uncertain` (not `pass` — vocabulary layering, §3.4) + ≤200-char rationale, appended to metadata and result text. **Judge input is report + unchecked criteria only** — the receipt digest is deliberately withheld so the judge cannot read "citation resolved" as "claim verified" (automation-bias loop). Any failure → silent `None`, result flows back unjudged. **One round, no auto-retry**: the verdict is a signal in the ledger; re-delegation remains the lead model's decision. Full-trajectory judging, multi-round reflection, and multi-agent debate are explicit non-goals (3–6× token cost, no production justification).

### 3.4 Relationship to the existing run delivery receipt

DeerFlow already has one receipt concept — the **run delivery receipt** (`run.delivery` event, `runtime/journal.py`, `runtime/runs/worker.py`, [#4272](https://github.com/bytedance/deer-flow/issues/4272)/[#4365](https://github.com/bytedance/deer-flow/pull/4365)): one per run, event-store-persisted, singleton with crash-recovery semantics. The two are distinct layers and must stay unconfused:

| | tool receipt (this RFC) | run delivery receipt (existing) |
| --- | --- | --- |
| Layer | harness (middleware) | runtime (worker) |
| Granularity | per tool call | per run, terminal |
| Carrier | message `additional_kwargs` | event store (`put_if_absent`) |
| Consumer | subagent (citation), parent (verification) | gateway / clients / recovery |

Three design rules keep them coherent:

1. **Facts vs verdicts** — both layers follow the existing "fact record, not a verdict" philosophy (`get_delivery_content`): receipts are immutable facts; verdicts (`satisfied`, stage) are computed by consumers and never written back. This is what makes delivery-receipt orphan recovery safe, and what lets tool-receipt verdict rules evolve without re-execution.
2. **Verdict structure aligned, vocabulary layered** — verdicts keep the `{source, requirement, ...details}` structural convention (`_delivery_content_with_outputs`), but the strong-positive boolean `satisfied` is **exclusive to the runtime hard gate**. Advisory layers (citation check / checklist / judge) use neutral vocabulary (`citation_resolved`, `supported`, `uncertain`) and never `satisfied`/`verified`/`passed` — model-visible positive signals cause automation bias, and two layers sharing `satisfied` would invite the model to conflate advisory evidence with a hard delivery gate. Shape alignment serves human readers; vocabulary layering protects model judgment.
3. **Naming** — metadata keys use the `deerflow_tool_*` prefix; event types use `run.*`; "receipt" alone in docs means tool receipt, the other always spelled "run delivery receipt".
4. **Model-visible rendering always carries its limitation (anti-automation-bias)** — any receipt/verdict text entering model context must: use neutral wording (states execution evidence, never implies claim correctness), carry a fixed limitation line (_"Execution evidence only — does not validate claim correctness or task acceptance"_), and render anything not deterministically checked as `UNVERIFIED` with no positive default. Design invariant: **confidence must not grow faster than correctness.**

**Code distribution follows layer ownership, not concept grouping** (no cross-layer `receipts/` package — the layers' dependency directions are opposite, and the existing delivery code is entangled with crash recovery; zero moves):

```
agents/middlewares/  tool_receipt.py (facts) · tool_receipt_middleware.py (hooks) · receipt_verification.py (verdict)
subagents/           executor.py (harvest) · status_contract.py (transport) · acceptance_checks.py · result_judge.py
runtime/             journal.py · runs/worker.py          ← existing delivery receipt, untouched
config/              verification_config.py               ← the only new config section
```

```yaml
verification:
  receipts_enabled: true        # deterministic receipts (default on: additive metadata only)
  receipts_render_mode: "delegation_only"  # subagent contexts always render; lead renders only when processing subagent results

  judge_model_name: null        # falls back to the parent model
```

## 5\. Alternatives considered

| Alternative | Why rejected |
| --- | --- |
| Full Agent-as-a-Judge per delegation | Up to tens of minutes compute/task; research consensus is selective judging |
| Multi-round reflexion / multi-agent debate | 3–6× tokens; optimum is exactly one round |
| HMAC-signed receipts (NabaOS) | Their channel is untrusted; ours is runtime-written `additional_kwargs` the LLM cannot forge — plain sha256 suffices |
| Lazy derivation instead of stamping | Loses execution-truth semantics (post-truncation content), fragile AI↔ToolMessage joins after compaction, no timestamp source |
| Dedicated `tool_receipts` state channel | Redundant storage → drift; breaks "model's view ≡ ledger content" under compaction |
| Cross-layer `deerflow/receipts/` package | Second organizational convention; opposite dependency directions between harness and runtime layers |
| Hard-gating runs on citation verdicts | Citation verification is advisory by design; hard gates belong to the runtime delivery layer |

## 6\. Non-goals

- Verifying **reasoning quality** (receipts attest tool-call facts only; reasoning is for checklist/judge and the lead model)
- Any change to the existing `run.delivery` receipt structure, persistence, or recovery
- Automatic retry loops: all verdicts are signals; re-delegation decisions stay with the lead model
- Merging the two receipt layers' channels (a future "subagent receipt digest in run delivery facts" would be a separate proposal)

## 7\. Open questions for reviewers

1. **Receipt semantics at the sanitization seam** — settled: receipts capture execution truth (raw tool return, pre-truncation). Corollary (review framing, adopted): post-compaction, `output_sha256` is a **freshness stamp, not a re-checkable fingerprint**, since only sanitized `content` survives — stated in the module docstring.
2. **Token budget** — settled: stamping and rendering are separate flags; subagents always render, lead renders only when processing subagent results (§3.1, §3.5).
3. **Citation ergonomics** — settled: rich anchors `[r2 write_file]`; the label doubles as a claim-evidence coherence check in `verify_receipt_citations`.
4. **Judge input scope** — settled: report + unchecked criteria only; the receipt digest is withheld to avoid the judge reading "citation resolved" as "claim verified".
5. **Open: read-only verifier rollout** — the judge's evolution (tool access, reopening real files, rerunning key checks) is a follow-on; trigger data from PR5 will inform when to build it.

## TL;DR

DeerFlow 目前**没有任何子 agent 成果验收机制**。lead agent 收到的是子 agent 的自由文本自述("Task Succeeded. Result: ..."),prompt 里虽然写着"对照原始证据验证",但验证者手里**根本不存在可用的原始证据**。一个跑飞了的子 agent 只要返回 `completed`,它的结论就会被原样采信。

本 RFC 提出一个按成本排序的三层验证栈,建立在一个共享原语之上——**tool receipt(工具回执)**:由运行时(而非 LLM)在每次工具调用时打下的不可变执行事实。

1. **Receipt(零 LLM 成本)**——每次工具调用获得确定性事实记录(`tool_name`、`status`、`args_sha256`、`output_sha256`、`output_bytes`、`created_at`);子 agent 报告引用回执编号 `[rN]`;父侧**确定性地把引用与执行记录交叉比对**。这直接杀死"虚假成功"这一大类——声称做了根本没发生、或实际失败了的操作。
2. **验收 Checklist(零~极低成本)**——派单时可携带 `acceptance_criteria`;可代码判定的叶子(`file:<path> exists|non-empty`)由代码判定;无法判定的叶子标记 `UNVERIFIED`,绝不静默通过。
3. **选择性单轮 Judge(一次小模型调用,可选,默认关)**——仅当存在未判定叶子时触发,每次委托最多一次。一轮为限,不自动重试。

这个设计是当前研究与生产实践的收敛点:"对每个子 agent 结果做全量 LLM 评审"在成本与效果上均已被证伪;有效的是**确定性校验打底,LLM 判断只花在无法判定的刀刃上**。

## 1\. 问题:子 agent 的自述被无验证采信

### 1.1 现状

结果回流路径(`tools/builtins/task_tool.py`、`subagents/status_contract.py`):

- 子 agent 终态结果以 `ToolMessage` 回到 lead:`content = "Task Succeeded. Result: <自由文本>"`,结构化元数据(`subagent_status`、`stop_reason`、`result_brief + sha256`)放在 `additional_kwargs`。
- **唯一**的验收是 lead 系统 prompt 里的一句指令:"Verify and synthesize the returned result against primary evidence"(`agents/lead_agent/prompt.py`,委托工作流第 6 步)。
- 委托账本(`agents/middlewares/delegation_ledger.py`)会渲染状态引导("may retry with a changed plan"),但那是文本引导,没有任何程序化校验。
- 14 个中间件的链路(`agents/middlewares/tool_error_handling_middleware.py::_build_runtime_middlewares`)中**没有任何结果评审环节**。

### 1.2 为什么 prompt 指令是空话

验证"已把分析写入 /outputs/report.md"这类声称,成本约等于**重新执行该动作**(stat 文件、重新 fetch)——而子 agent 的中间 ToolMessage 在边界的另一侧(子 agent 自己的 checkpoint 里),父侧上下文只能看到委托调用和摘要文本。所以"对照原始证据验证"要求模型对照一份**它没有的证据**,支付它**不会支付的成本**。

### 1.3 为什么既有记录帮不上忙

DeerFlow 确实记录了执行过程:ToolMessage.content 里的原始输出(已 checkpoint)、沙箱审计日志、run journal、LangSmith trace。但都不是**验证可用的证据**:

| 记录 | 为什么不能当证据 |
| --- | --- |
| `ToolMessage.content` | 非结构化自由文本;会被截断/消毒改写;会被 compaction 删除;而且最关键——**在子 agent 边界的另一侧** |
| 沙箱审计 / journal / trace | 面向运维可观测性——agent 回路里没有任何代码路径消费它们做验证 |

缺的不是记录,是**验证者够得着、能直接比对、无需重新执行的事实**。

## 2\. 先行工作与选型依据

### 2.1 研究界收敛(2025–2026)

- **Tool Receipts(NabaOS,arXiv 2603.10060)**——运行时签发、HMAC 签名的逐次工具调用回执;把 LLM 回复与回执台账确定性交叉比对。检出编造工具引用 94.2%、数量失实 87.6%、假阴性 91.3%,**开销 <15ms、几乎零 token**。是"又好又便宜"的最优形态。边界:只能验证工具调用事实,验不了推理质量。
- **Mind2Web 2(ICML'25)**——生成-验证不对称性:验证远比生成容易,因此把评审拆成树状 rubric,每个叶子是一个二元判断。checklist 拆解本身就是降本手段。
- **Agent-as-a-Judge(Meta)**——与人类评审对齐度极高,但单任务最坏几十分钟计算。质量天花板、成本地板以下,不适合每次委托都用。
- **生产共识(OpenHands、Claude Code、OpenAI Agents SDK 等)**——步骤级确定性 verifier 先行(开销 <10%);CRITIC 式 grounding 只在副作用边界触发;Reflexion 式反思只在可重试任务上最多一轮(每多一轮 ≈ 3 倍 token 且无收益)。

**结论:** receipt 级确定性打底(免费)+ checklist 拆解(便宜)+ 只对约 1% 无法判定的路径启用 judge(贵但罕见)。

### 2.2 Hermes Agent(最接近的已落地设计)

Hermes(`NousResearch/hermes-agent`,v0.19.1)同样没有代码级验收,但有两个值得明确借鉴的点:

- 委托工具的描述里硬编码:"Subagent summaries are SELF-REPORTS, not verified facts… 要求子 agent 返回可验证句柄(URL、ID、绝对路径、HTTP status)并自行复核。"写在工具 schema 里的指令每次调用都可见,胜过系统 prompt 里的一段话。
- 空摘要硬判失败(防"零内容假成功")。

DeerFlow 有一点已超过 Hermes:确定性委托账本用 `stop_reason` 区分"预算耗尽"与"真失败"。Hermes 有而 DeerFlow 缺的是**可验证句柄**纪律——receipt 正是它的泛化。

## 3\. 设计

### 3.1 回执:在真相唯一完整的时刻打下的不可变事实

```
ToolReceipt = {
  tool_call_id, tool_name,        # 关联锚点,自含以便运输
  status,                         # 复用 deerflow_tool_meta 的三档状态
  args_sha256, output_sha256,     # 输入/输出指纹(16 字符)
  output_bytes, created_at,       # 规模与时序锚点
}
```

**打戳点:新 `ToolReceiptMiddleware` 的 `wrap_tool_call`。** 这是全系统**唯一**同时满足四个条件的点:

1. 两个输入都在场(`request.tool_call` + 原始返回)——其他任何位置想凑齐参数,都得做跨消息 join,而 join 在 compaction 后会静默断裂。
2. content 尚未被消毒/截断改写——receipt 捕获的是**执行真相**("工具返回了什么"),刻意区别于交付真相("模型看到了什么")。
3. `deerflow_tool_meta` 的 status 已打好(由构建期顺序守卫强制)。
4. lead 与 subagent 共用同一条链——一处打戳两边生效,这正是父侧收割不需要第二套代码的原因。

**载体:`ToolMessage.additional_kwargs["deerflow_tool_receipt"]`。** LangChain 官方扩展槽,已有 `deerflow_tool_meta` 同构先例;随 checkpoint 序列化零成本。已考虑并否决的替代:惰性派生(丢失执行真相语义、join 脆弱、无时间戳来源)、专用 state channel(冗余存储=漂移风险;破坏"模型所见≡台账所述"的 compaction 不变量)、`artifact` 字段(在 tool\_meta 旁制造第二套约定)。

**派生而非存储。** receipt 寄生在消息流上;台账在每次模型调用时由 `extract_tool_receipts` 现场派生,按只追加的消息序赋稳定编号 `r1..rN`。同一个函数同时服务于上下文渲染、executor 收割和测试。不开专用 channel、不做一致性维护:compaction 删掉消息,其 receipt 随之消失——与模型所见严格一致。

**模型可见台账。** 每次模型调用,中间件渲染台账(2000 字符预算,最新优先淘汰),以短暂隐藏 `HumanMessage` 注入(`hide_from_ui`,不写回 state——沿用 `DurableContextMiddleware` 模式,复用 `_insert_after_leading_system_messages`)。台账头部**永远携带证据边界声明**:"Execution evidence only — receipts record that a call happened and its status; they do not validate claim correctness or task acceptance." 该固定限制行为硬性要求(反自动化偏误,见 §3.4 规则 4)。

**渲染与打戳拆分**(review 反馈:常驻 token 税):`receipts_enabled`(打戳)默认常开;渲染有独立模式。子 agent 上下文**始终渲染**——引用在子侧产生,子侧没台账则 Layer 1 退回静默失效;lead 上下文**只在处理子 agent 结果的回合渲染**(消息流中存在委托完成记录时),这是 lead 唯一需要引用上下文的场景。成本有界:渲染时每次调用 ≤约 500–600 tokens,不渲染时为零。

**故障隔离。** 打戳/注入的任何异常仅记录日志并跳过;receipt 永远不能打断工具执行或结果回写。

### 3.2 跨越边界(第 1 层消费)

```
子 agent 消息流(带戳 ToolMessage)
  → executor 终态收割:extract_tool_receipts(final_state.messages)
  → SubagentResult.tool_receipts
  → status_contract:additional_kwargs["subagent_tool_receipts"]
  → 父侧 receipt_verification.verify_receipt_citations(报告文本, receipts)
  → 裁决渲染进委托账本行
```

`verify_receipt_citations` 是纯代码:从子 agent 报告中提取 `[rN]` 引用,逐条分类——`resolved`(存在且成功)/ `failed`(存在但失败)/ `unknown`(执行记录中不存在)。账本行尾新增形如:`receipts: 2 citations resolved, 1 unknown — execution evidence only, does not validate claim correctness`。

**两条强化规则(review 反馈):**

1. **零引用的动作声称判 `UNVERIFIED`,不是中性。** 完成报告含有动作声称(写了文件、跑了命令、完成上传)却零引用,是弱负向信号而非清白——分类器标记 `no_citation_claims` 并渲染 `UNVERIFIED — action claims without receipt citations`。没有这条,最值得怀疑的报告反而会得到最干净的结果。
2. **富锚点 `[r2 write_file]`。** 引用可携带工具名标签;`verify_receipt_citations` 随之做声称-证据一致性检查("写文件"声称锚定到 `web_search` 的 receipt → 标 `failed` 并注明不匹配)。

**裁决词汇约定**(与 run delivery receipt 对齐_结构_,见 §3.4——但**不对齐词汇**):`{source: "receipt_citations", requirement: "cited_ids_in_execution_record", citation_resolved: bool, cited/resolved/failed/unknown: [...]}`。布尔值刻意命名 `citation_resolved` 而非 `satisfied`:本层是建议性执行证据,强正向词汇(`satisfied`/`verified`/`passed`)由 runtime 硬门独占,模型不会混淆两者。

### 3.3 第 2、3 层:checklist 与选择性 judge

- **Checklist。** `task` 工具新增 `acceptance_criteria: list[str]`。确定性叶子族,代码判定:
 - `file:<path> exists|non-empty`——经 `read_current_file_content`(沿用 `ReadBeforeWriteMiddleware` 先例),**限定共享 thread 工作区**:路径必须落在 thread 的 `outputs_path`/`workspace_path` 之下(executor 会透传给子 agent)。共享域外的路径返回 `checked=False`(UNVERIFIED),不假设跨沙箱可达——未来隔离型 sandbox 破坏共享时,叶子退化为 UNVERIFIED 而非误判。
 - **类型化声明绑定**(review 反馈):`file_written:<path>`(存在性 + 回读)与 `tests_passed:<command>`(声称必须锚定到_具体一次_有记录的执行——匹配的 bash receipt 且 status=success、输出含测试摘要形态——而不是任意一次成功调用)。父侧完全重跑留给只读 verifier(§6 后续项)。 
 其余叶子返回 `checked=False`,渲染 `UNVERIFIED`,绝不静默通过。结果进结果 metadata 并渲染到文本尾部。
- **Judge。** 配置开关(`verification.judge_enabled`,默认**关**)。触发条件:status == completed ∧ 存在未判定叶子。一次 `create_chat_model(thinking_enabled=False)` 调用(沿用 `TitleMiddleware` 模式),输出 `supported|not_supported|uncertain`(不用 `pass`——词汇分层,§3.4)+ ≤200 字理由,附加到 metadata 与结果文本。**judge 输入仅含报告 + 未判定叶子**——刻意不給 receipt 摘要,防止 judge 把 "citation resolved" 读成 "claim verified"(自动化偏误回路)。任何失败→静默返回 `None`,结果照常回流。**一轮为限,不自动重试**:裁决只是账本里的信号,是否重派仍由 lead 模型决定。全轨迹评审、多轮反思、多 agent 辩论均为显式非目标(3–6 倍 token,无生产依据)。

### 3.4 与既有 run delivery receipt 的关系

DeerFlow 已存在一种 receipt——**run delivery receipt**(`run.delivery` 事件,`runtime/journal.py`、`runtime/runs/worker.py`,[#4272](https://github.com/bytedance/deer-flow/issues/4272)/[#4365](https://github.com/bytedance/deer-flow/pull/4365)):每 run 终态一次,事件库持久化,带崩溃恢复的单例语义。两者是不同分层,必须避免混淆:

| | tool receipt(本 RFC) | run delivery receipt(既有) |
| --- | --- | --- |
| 层 | harness(中间件) | runtime(worker) |
| 粒度 | 每次工具调用 | 每 run 终态一次 |
| 载体 | 消息 `additional_kwargs` | 事件库(`put_if_absent`) |
| 消费者 | 子 agent(引用)、父侧(校验) | gateway / 客户端 / 恢复流程 |

三条设计规则保证两者协调:

1. **事实与裁决分离**——两层都遵循既有"fact record, not a verdict"哲学(`get_delivery_content`):receipt 是不可变事实;裁决(`satisfied`、stage)由消费方计算,永不回写。这正是 delivery receipt 崩溃恢复安全成立的原因,也让 tool receipt 的裁决规则可以演进而不必重放执行。
2. **裁决结构对齐,词汇分层**——裁决沿用 `{source, requirement, ...details}` 的结构约定(`_delivery_content_with_outputs`),但强正向布尔词 `satisfied` **由 runtime 硬门独占**。建议性信号层(引用校验/checklist/judge)使用中性词汇(`citation_resolved`、`supported`、`uncertain`),禁用 `satisfied`/`verified`/`passed`——模型可见的正向信号导致自动化偏误,两层共用 `satisfied` 会让模型混淆建议性证据与硬交付门。结构对齐服务人类读者,词汇分层保护模型判断。
3. **命名**——metadata 键用 `deerflow_tool_*` 前缀;事件类型用 `run.*`;文档中单独出现"receipt"指 tool receipt,另一种必须写全"run delivery receipt"。
4. **模型可见渲染永远携带限制声明(反自动化偏误)**——任何进入模型上下文的 receipt/裁决文本必须:措辞中性(只述执行证据,不暗示结论可信);携带固定限制声明("Execution evidence only — does not validate claim correctness or task acceptance.");未经确定性验收的项永远渲染 `UNVERIFIED`,无正向默认。设计不变量:**信心增长速度不得超过正确性增长速度。**

**代码分布按层归属,不按概念收拢**(不建跨层 `receipts/` 包——两层依赖方向相反,且既有 delivery 代码与崩溃恢复深度纠缠;零挪动):

```
agents/middlewares/  tool_receipt.py(事实)· tool_receipt_middleware.py(hook)· receipt_verification.py(裁决)
subagents/           executor.py(收割)· status_contract.py(运输)· acceptance_checks.py · result_judge.py
runtime/             journal.py · runs/worker.py          ← 既有 delivery receipt,不动
config/              verification_config.py               ← 唯一新增配置节
```

## 5\. 已考虑并否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 每次委托跑完整 Agent-as-a-Judge | 单任务可达数十分钟;研究共识是选择性评审 |
| 多轮 reflexion / 多 agent 辩论 | 3–6 倍 token;最优点恰为一轮 |
| HMAC 签名 receipt(NabaOS) | 其场景通道不可信;我们的 `additional_kwargs` 由运行时写入、LLM 无法伪造,普通 sha256 足够 |
| 惰性派生代替打戳 | 丢失执行真相语义(只能读到截断后内容)、AI↔ToolMessage join 在 compaction 后脆弱、无时间戳来源 |
| 专用 `tool_receipts` state channel | 冗余存储→漂移;破坏 compaction 下"模型所见≡台账所述"不变量 |
| 跨层 `deerflow/receipts/` 包 | 制造第二套组织约定;harness 与 runtime 两层依赖方向相反 |
| 引用裁决硬门化(直接判 run 失败) | citation 校验设计上即建议性信号;硬门属于 runtime delivery 层 |

## 6\. 非目标

- 验证**推理质量**(receipt 只为工具调用事实作证;推理质量归 checklist/judge 与 lead 模型)
- 任何对既有 `run.delivery` receipt 结构、持久化与恢复流程的改动
- 自动重试闭环:一切裁决只是信号,重派决策留在 lead 模型
- 合并两层 receipt 的通道("子 agent receipt 摘要汇入 run delivery 事实"如需做,另行提案)

## 7\. 留给 reviewer 的开放问题

1. **消毒接缝处的 receipt 语义**——已定:receipt 捕获执行真相(原始返回,先于截断)。推论(采纳 review 表述):compaction 之后 `output_sha256` 是**新鲜度戳,不是可重验指纹**(只有消毒后的 content 存活)——写进模块 docstring。

Thanks for the detailed RFC. I agree that the current trust gap is real and that deterministic execution evidence can be useful. My main concern is that the proposal needs a much sharper boundary between **execution provenance** and **result verification**.

There are two different trust models worth separating:

1. **Receipt-centered verification**: the runtime proves that a tool call existed and records its status; the subagent cites `[rN]`; deterministic parent-side code checks that the citation resolves to a successful recorded call. The lead agent still has to decide whether that call actually supports the adjacent claim.
2. **Inspectable artifacts + independent re-verification**: workers leave findings, change logs, paths, commands, and other inspectable outputs in a shared artifact/workspace area; the lead reads and synthesizes those artifacts itself; a separate read-only, adversarial verifier reopens the real files and reruns the critical checks. This costs more, but it evaluates the task outcome rather than only the existence of a cited action.

A receipt is useful evidence, but it does not by itself make a subagent trustworthy. For example:

- “All tests passed \[r3\]” may cite an unrelated successful receipt.
- A write tool may have succeeded while writing the wrong file or wrong content.
- A shell command may have exited successfully while running only a partial test selection.
- The tool output may be genuine but interpreted incorrectly by the subagent.

Therefore:

> verified citation ≠ verified claim ≠ accepted task

This creates a downstream risk of **automation bias**. Model-visible signals such as `satisfied: true`, “cited ok”, or “verification passed” can cause the lead agent to treat a weak provenance check as an outcome-level guarantee. That can be more misleading than an explicit self-report. The lead may then skip independent checks, synthesize an incorrect conclusion, re-delegate based on a false premise, or propagate the result into later artifacts, memory, and user-facing answers. Reusing the same `satisfied` vocabulary as the hard `run.delivery` gate also increases the chance that the model conflates two very different semantics.

I think the RFC could be strengthened by considering the following:

- Treat receipts strictly as **execution evidence**, not verification verdicts. Prefer names such as `execution_observed` and `citation_resolved`; avoid `verified`, `passed`, or `satisfied`.
- Always render an explicit limitation: “This does not validate claim correctness or task acceptance.”
- Add typed claim-to-evidence bindings and outcome-specific checks. For example, `tests_passed` should bind to the exact command, exit code, and complete test summary; `file_written` should bind to the expected path plus read-back/content validation.
- Keep the task status `UNVERIFIED` unless a deterministic acceptance check or independent re-verification actually ran.
- For critical tasks, use a separate read-only verifier (or lead-agent re-execution) to inspect artifacts and rerun checks.
- Test adversarial cases explicitly: unrelated receipts, reused citations, successful tools with incorrect outputs, partial test runs, stale evidence, and compaction boundaries.

In particular, I would be cautious about landing a model-visible positive receipt ledger as a standalone first step before the end-to-end acceptance semantics exist. Otherwise the system may increase confidence faster than it increases correctness. Receipts can be a useful lower-level signal, but they should complement—not replace—inspectable artifacts and independent outcome verification.

感谢这份详细的 RFC。我同意当前确实存在子 Agent 成果可信度缺口，确定性的执行证据也有价值。我的主要担忧是：方案需要更严格地区分 **“执行来源可追溯”** 和 **“结果已经验证”**。

这里其实存在两种不同的信任模型：

1. **以 receipt 为中心的验证**：运行时证明某次工具调用确实存在并记录状态；子 Agent 引用 `[rN]`；父侧代码确定性地检查该引用是否对应一次成功的调用。至于这次调用是否真的支持旁边那句话，最终仍要由 lead Agent 判断。
2. **可检查产物 + 独立复验**：Worker 把调查结果、修改记录、路径、命令等写入共享的 artifact/workspace；lead Agent 自己读取并综合；再由一个独立、只读、对抗性的验证 Agent 重新打开真实文件并重跑关键检查。这种方式成本更高，但验证的是任务结果，而不只是某个动作是否发生。

Receipt 是有价值的证据，但它本身不能让子 Agent 变得可信。例如：

- “所有测试都通过了 \[r3\]”可能引用的是一次无关的成功调用；
- 写入工具成功，不代表写对了文件或内容；
- 命令退出码为 0，可能只是运行了不完整的测试集合；
- 工具输出是真实的，但子 Agent 可能理解错了。

因此：

> 引用已核验 ≠ 声明已核验 ≠ 任务已验收

这会带来明显的 **自动化偏误** 风险。模型看到 `satisfied: true`、`cited ok` 或 “verification passed” 这类强正向信号后，可能把很弱的来源检查理解为结果级保证，甚至比明确标注为“子 Agent 自述”更容易误导。随后可能出现：

- lead Agent 跳过独立检查；
- 基于错误结论继续综合或重新派单；
- 错误结果被写入后续 artifact、memory 或用户答案；
- 与 `run.delivery` 共用 `satisfied` 词汇后，模型混淆“建议性证据”和“硬交付门槛”。

建议考虑：

- Receipt 只称为 **执行证据**，不要称为验证结论；可使用 `execution_observed`、`citation_resolved`，避免 `verified`、`passed`、`satisfied`。
- 始终向模型明确展示：“该证据不验证声明正确性，也不代表任务已验收。”
- 建立声明类型与证据的绑定，并做针对结果的检查。例如 `tests_passed` 必须绑定具体命令、退出码和完整测试摘要；`file_written` 必须绑定目标路径，并进行回读或内容校验。
- 没有运行确定性验收或独立复验时，任务状态应保持 `UNVERIFIED`。
- 对关键任务使用独立的只读验证 Agent，或者由 lead Agent 重新执行关键检查。
- 增加对抗性用例：无关 receipt、重复引用、工具成功但结果错误、只跑部分测试、过期证据以及 compaction 边界。

尤其需要谨慎的是：如果先单独落地一个面向模型展示强正向信号的 receipt ledger，而完整的结果验收语义尚未建立，系统增加“信心”的速度可能会快于增加“正确性”的速度。Receipt 可以作为有价值的底层信号，但更适合补充可检查产物和独立结果复验，而不是替代它们。

**1\. Vocabulary: accepted, with one nuance.** We'll drop `satisfied`/`verified`/`passed` from the advisory layer entirely. Thanks for the detailed RFC - the cost-ordered layering and the stamping-point design are well-argued, and the response to [@AnnaSuSu](https://github.com/AnnaSuSu)'s review already improved the automation-bias framing. I did a pass focused on grounding the RFC's codebase claims against current `main` (which includes [#4365](https://github.com/bytedance/deer-flow/pull/4365) and the follow-up [#4494](https://github.com/bytedance/deer-flow/pull/4494)), and found a few citations that don't resolve, plus a couple of design gaps worth raising.

## 1\. §3.4 cites delivery-receipt symbols that don't match the merged code

§3.4 is the architectural keystone - it argues the tool receipt must stay a distinct layer from the "existing run delivery receipt." I checked its specific citations:

| RFC claim | Against current main |
| --- | --- |
| `run.delivery` event | No such event. `runtime/events/catalog.py` defines only `run.start` / `run.end` / `run.error` (+ `llm.*`, `subagent.*`, `context:memory`, workspace-changes). No inline `RunEventDefinition`s elsewhere. |
| `get_delivery_content` ("fact record, not a verdict" philosophy) | Not found in `packages/` or `app/`. |
| `_delivery_content_with_outputs` (verdict-shape convention to align with) | Not found. |
| "event-store-persisted, singleton with `put_if_absent` crash-recovery semantics" | `put_if_absent` doesn't exist - `events/store/base.py` exposes `put` / `put_batch` only. |

What [#4365](https://github.com/bytedance/deer-flow/pull/4365) + [#4494](https://github.com/bytedance/deer-flow/pull/4494) actually shipped is **workspace-snapshot capture/persist** (`capture_workspace_snapshot`, `pre_run_workspace_snapshot`, `_persist_snapshot_to_store` in `runs/manager.py` / `runs/worker.py`), and the only "receipt" in `worker.py` is `_has_durable_goal_turn_receipt` - a checkpoint-derived end-of-turn marker, not an event-store singleton.

Why this matters: the RFC's three design rules (facts-vs-verdicts, verdict-shape alignment, naming) are all framed against this existing layer. If that layer doesn't carry a `{source, requirement, satisfied, ...}` verdict shape or `put_if_absent` semantics, "shape-aligned, semantics-layered" is aligning with something that isn't there. Could you reconcile §3.4 against what [#4365](https://github.com/bytedance/deer-flow/pull/4365)/[#4494](https://github.com/bytedance/deer-flow/pull/4494) actually shipped? (Possible this is a planned rename or an earlier draft - either way, as written it won't survive a maintainer cross-check.)

## 2\. §1.1/§1.2 quote a lead-prompt instruction that isn't there

The RFC states: _"The only verification is a prompt instruction in the lead's system prompt: 'Verify and synthesize the returned result against primary evidence' (`agents/lead_agent/prompt.py`, delegation workflow step 6)."_

That string doesn't exist in `lead_agent/prompt.py` (or anywhere in `agents/` / `subagents/`). The actual delegation "CRITICAL WORKFLOW" is COUNT -> PLAN BATCHES -> EXECUTE -> REPEAT -> **SYNTHESIZE** -> "Cannot decompose -> Execute directly." Step 5 is "SYNTHESIZE: After ALL batches are done, synthesize all results." There's no "verify against primary evidence" instruction.

The real situation is actually stronger than the RFC's framing - there isn't even a hollow verify instruction, just "synthesize" - so fixing/dropping the citation makes the argument more convincing, not less.

(Minor: "14-middleware chain" is ~13 by my count of `_build_runtime_middlewares` + `TitleMiddleware`; the "no result-review stage" claim is correct. Config version: RFC says 32->33 but `config.example.yaml` is at `config_version: 29` - worth re-checking against current main.)

## 3\. Design strengths

- **Stamping at `wrap_tool_call`, execution truth (pre-truncation)** - the four-conditions argument is the strongest part. Cross-message arg-join after compaction _would_ be fragile.
- **"Derived, not stored"** - receipts ride `additional_kwargs`, ledger re-derived positionally, compaction removes message + receipt together. Preserves "model's view ≡ ledger content" with zero consistency maintenance.
- Carrier reuse (`deerflow_tool_receipt` beside `deerflow_tool_meta`), failure-isolated stamping, and the 5-PR decomposition with keyword-only-param conflict mitigation are all right.

## 4\. Gaps the discussion hasn't surfaced

**a. Layer 1 is inert when the subagent doesn't cite - and nothing forces it to.** "False success becomes detectable" depends on the subagent putting `[rN]` in its report. A hallucinating/lazy subagent writing `"Task Succeeded. Result: done."` with zero citations yields `0 cited, 0 unknown` - a _neutral_ ledger line, not a suspicious one. The adversarial test list accepted from [@AnnaSuSu](https://github.com/AnnaSuSu) covers unrelated/reused citations but not the no-citation case. PR3 (prompt-layer citation requirement) is therefore load-bearing, not "small diff, fast review" - if the subagent ignores it, Layer 1 is a no-op. Consider treating a citation-less success claim as `UNVERIFIED` rather than neutral, plus a "claim made, no receipts cited" weak signal.

**b. Cross-boundary file checks assume a shared workspace.** PR4's deterministic leaves (`file:<path> exists|non-empty`) use `read_current_file_content` (the `ReadBeforeWriteMiddleware` precedent), but that precedent runs _within one agent's sandbox_. A subagent writes to _its_ sandbox; the parent's `read_current_file_content` won't find `/outputs/report.md` unless there's a shared artifact/workspace contract. This is exactly [@AnnaSuSu](https://github.com/AnnaSuSu)'s "inspectable artifacts" point. PR4 should either scope file leaves to a documented shared workspace, or sequence after that shared-artifact layer.

**c. Always-on ~500-600 token/model-call tax.** The ledger renders on _every_ model call for the thread's lifetime. "Zero when no receipts exist" holds early, but in a 50-tool-call run the 2000-char budget (newest-first) stays near-full - ~600 tokens x every subsequent call, easily 30K+ extra over a long task, injected even when the current decision doesn't touch receipts. My take on open-question [#2](https://github.com/bytedance/deer-flow/pull/2): split the flag - keep `receipts_enabled` (stamping) on by default, but default _rendering_ off and render only when a subagent result is being processed (the one place citations matter).

**d. Layers 2-3 are dormant by default.** `acceptance_criteria` is optional and requires the lead to specify upfront. In practice most delegations won't carry it, so Layer 2 won't run and Layer 3 (gated on unchecked leaves) won't trigger - leaving Layer 1 (citations) as the only active layer, which (per _a_) is itself inert without citations. The RFC needs an adoption story: templates/defaults that pre-populate `acceptance_criteria` for common delegation types, or a lead-prompt nudge.

## 5\. Open questions - my takes

1. **Execution truth vs delivered truth** - agree, keep execution truth. Nuance: post-compaction `output_sha256` is unverifiable against anything (raw return isn't checkpointed, only sanitized `content`), so it's a freshness stamp, not a re-checkable fingerprint - worth stating explicitly.
2. **Token budget** - split the flag; render only at subagent-result processing (see _c_).
3. **Citation format** - lean toward richer anchors (`[r2 write_file]`). The classifier can strip the label, and the tool name lets `verify_receipt_citations` sanity-check ("file-write claim cites a `web_search` receipt" -> flag).
4. **Judge input scope** - start with report + unchecked criteria only (option A). Don't include the receipt digest from day one - that risks the judge treating "citation resolved" as "claim verified," which is precisely the automation bias [@AnnaSuSu](https://github.com/AnnaSuSu) flagged.

## Bottom line

Direction is right; cost-layering and stamping-point design are sound, and the author has been responsive to review. The blocker is §3.4: the central alignment argument rests on symbols/semantics (`run.delivery`, `get_delivery_content`, `_delivery_content_with_outputs`, `put_if_absent`) that don't exist in the merged delivery-receipt code, so it needs rewriting against what [#4365](https://github.com/bytedance/deer-flow/pull/4365)/[#4494](https://github.com/bytedance/deer-flow/pull/4494) actually shipped. Fix the §1.1 citation (the real situation is stronger anyway), and address the citation-adoption gap (a) + cross-boundary file-check assumption (b) before PR2/PR4 land. The rendering tax (c) and default-dormant upper layers (d) are tuning issues, not blockers.
