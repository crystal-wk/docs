### Problem summary

SqlAgentStore cache signatures can remain unchanged after a persisted agent update made within the same system clock tick.

### Affected area(s)

Agents / LangGraph (graph, prompts, langgraph.json)

### What happened?

`SqlAgentStore.signature()` currently uses `(MAX(updated_at), COUNT(*))` 
as the change token for the GitHub agent-registry cache.

When an agent is created and updated within the same system clock tick, the 
persisted configuration changes but `updated_at` can remain equal. The returned 
signature therefore remains unchanged.

I first observed this through the existing 
`test_signature_changes_on_mutation` regression test. In five isolated runs, 
the test failed once.

I then reproduced the underlying condition deterministically by making the 
create and update operations use the same timestamp:

```
before = ('2026-01-01 00:00:00', 1)
after  = ('2026-01-01 00:00:00', 1)
stale_signature = True
stored_description = changed
```

The agent configuration was successfully updated, but the cache signature did 
not reflect the mutation.

### Expected behavior

```md
Every persisted mutation that changes the effective agent definition should
produce a different `AgentStore.signature()` value.

After updating an agent's configuration or SOUL, the next call to
`build_github_agent_registry()` should detect the changed store signature and
rebuild the cached GitHub webhook routing registry.

The result should not depend on the operating system's clock resolution or on
whether two writes receive the same `updated_at` value.

### Additional context

The affected cache consumer is 
`app/gateway/github/registry.py::build_github_agent_registry()`.

It returns the cached registry when the current `AgentStore.signature()` equals 
the previous token. A same-tick update can therefore leave GitHub webhook 
routing on the previous agent configuration until another mutation or process 
restart invalidates the cache.

The DB-backed custom-agent store was introduced in [#4359](https://github.com/bytedance/deer-flow/pull/4359). I searched current 
issues and pull requests for `SqlAgentStore`, `agent store signature`, and 
`test_signature_changes_on_mutation` and did not find an existing report or 
implementation for this collision.

A possible fix is to derive the DB signature from a deterministic digest of the 
effective agent definitions — for example normalized `(user_id, name, config, soul)` rows — instead of depending only on timestamp and row count.

I would be happy to submit a focused PR with:

1. a deterministic regression test;
2. a content-sensitive DB signature;
3. no database migration or public API change;
4. updated cache-invalidation documentation.
