## Motivation

DeerFlow supports multiple model providers, but it is currently hard to quickly verify whether a configured model works with the core runtime contract: streaming, tool calling, artifact writing, multi-tool flows, and recovery after tool errors.

I would like to propose an opt-in live smoke test that is not part of the default pytest or CI suite. It would call real model APIs only when a developer explicitly runs it with their own configured model names.

## Proposed Smoke Cases

- basic chat response
- streaming health and first-content latency
- write\_file tool execution
- write\_file followed by read\_file
- recovery after a tool error

## Example

python backend/tests/model\_compat/run\_smoke.py --models deepseek-reasoner,volc-kimi-coding

## Initial Local Result

I tested two native provider configurations locally:

- deepseek-reasoner: 5/5 passed
- volc-kimi-coding: 5/5 passed

This is intentionally small and extensible. It can later be used to validate additional official providers without relying on third-party OpenAI-compatible gateways.

If this direction sounds acceptable, I can open a PR with the initial smoke runner and README.

Hi [@tomsen02](https://github.com/tomsen02) and maintainers,

I noticed that the earlier implementation PR [#3185](https://github.com/bytedance/deer-flow/pull/3185) was closed without being merged, while this issue remains open and currently has no assignee.

I'd like to pick this up if nobody is actively working on it. Since [#3185](https://github.com/bytedance/deer-flow/pull/3185) was opened, [#4482](https://github.com/bytedance/deer-flow/pull/4482) has merged an explicit opt-in policy for live LLM integration tests. I plan to build on that mechanism and keep the compatibility smoke runner strictly opt-in:

- it will not be collected or executed by the default pytest suite or CI;
- automated coverage for argument parsing, model selection, summaries, error categories, and exit codes will use offline fakes/stubs;
- no real model API calls will run in automated tests;
- smoke runs will use isolated thread/workspace identifiers and avoid polluting existing user data;
- failures will distinguish configuration errors, model incompatibility, tool failures, and runner errors.

The intended live cases remain the five proposed here: basic chat, streaming health with first-content latency, `write_file`, `write_file` followed by `read_file`, and recovery after a tool error.

If you're planning to resume [#3185](https://github.com/bytedance/deer-flow/pull/3185), or if maintainers would prefer that PR to be reopened instead of a new implementation, please let me know so we can coordinate.
