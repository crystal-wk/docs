## Problem

When a GitHub webhook arrives for a `(repo, number, agent)` thread that already has an active run, the run is rejected and the triggering comment is **silently dropped** - the human sees no reaction, no comment, no acknowledgement, and reasonably concludes the bot ignored them.

## Current behavior

The GitHub chat path is `fire_and_forget` with `multitask_strategy: "reject"` (`app/gateway/github/run_policy.py`, `app/channels/manager.py`):

1. First comment -> `client.runs.create(thread_id, …)` succeeds -> autonomous run starts (legitimately long: clone, edit, test, push, comment).
2. A second comment arrives on the same thread while the first run is still active -> `runs.create` raises `ConflictError`.
3. The manager catches it (`_is_thread_busy_error`) and calls `_send_error(msg, THREAD_BUSY_MESSAGE)`.
4. `GitHubChannel.send` is **log-only by design** (agents post via `gh` themselves), so `THREAD_BUSY_MESSAGE` goes nowhere visible.
5. **Net: the second comment is silently dropped.** No reaction, no comment, no queue signal.

This collision window is ~6 minutes per typical coding run, wide enough to fire routinely:

- Human realizes 30s after their initial comment that they need to clarify.
- Multiple reviewers comment at once on a PR the bot is still working on.
- A bot reviewer (Copilot, CodeRabbit) submits a `pull_request_review` while our coder bot is mid-PR.

[#4003](https://github.com/bytedance/deer-flow/pull/4003) (merged) made the "one active run per thread" invariant DB-enforced via the `uq_runs_thread_active` partial unique index, so the `ConflictError` is now deterministic and cross-pod-safe (good - no more two-concurrent-runs race). But it does nothing about the silent drop itself - the second comment still vanishes.

## Proposed direction

A per-thread follow-up buffer + watcher, layered on the existing `StreamBridge.END_SENTINEL` completion signal:

- **On `ConflictError`**: append the comment to a per-`(thread_id)` buffer (dedup by `comment_id`), react `eyes` on the comment via the installation token ("queued; will pick up after the current run"). Hard cap (e.g. 20); overflow reacts `confused` + WARNING log as a visible overload signal.
- **Watcher**: on the happy path, capture `run_id` and `async for entry in bridge.subscribe(run_id)` until `END_SENTINEL` (zero-overhead push, no `runs.get` polling). Subscribe through the `StreamBridge` abstraction so it works under `GATEWAY_WORKERS=1` (memory bridge) and `>1` (Redis bridge).
- **Drain**: on run completion, drain the buffer FIFO (batch ~10), coalesce into a single `<followups-while-busy>` input block, and `runs.create` the next run. Naturally chains for >10 buffered.
- **Reaction semantics**: `+1` = "working on this now" (existing agent SOUL.md flow); `eyes` = "saw it, queued for next run" (manager); `confused` = "saw it, can't queue" (manager overflow). Each comment gets some reaction within ~1s.
- **Fanout filter (independent, ship first)**: suppress `pull_request_review_comment` events that carry a `pull_request_review_id` (and no `in_reply_to_id`) - the parent `pull_request_review` event already covers them and the agent fetches inline comments itself via `gh api`. This eliminates the 20-30 comment "CodeRabbit storm" as a buffer concern before the buffer is even built.

A full design (option matrix, walkthrough, edge cases, numbers, implementation order) is written up and can be turned into a PR / design doc on request.

## Multi-worker caveat

The buffer is in-memory per gateway _process_. Under `GATEWAY_WORKERS>1` each uvicorn worker has its own `MessageBus` + `ChannelManager` + buffer (`app/channels/service.py` - `_channel_service` is a per-process singleton); under multi-pod, each pod does too. A follow-up comment may land on a different process than the one holding the in-flight run + buffer. [#4003](https://github.com/bytedance/deer-flow/pull/4003) keeps the _run_ layer safe (the second process's `runs.create` hits the DB index -> `ConflictError`), but the _buffer_ and `eyes` reaction are per-process - the second process doesn't know the comment was already queued/acknowledged. Resolving this needs either IM leader election (the "parallel surface" [#4003](https://github.com/bytedance/deer-flow/pull/4003) explicitly deferred) or a shared buffer store (Redis) - the same shape as the [#4120](https://github.com/bytedance/deer-flow/issues/4120) fix. The watcher's END-signal is **not** the blocker (the Redis `StreamBridge` forwards it cross-process); buffer-state ownership is. For `GATEWAY_WORKERS=1` / single-pod (the current safe default), the design works as-is.

## Scope

Two independently-shippable slices:

1. **Fanout filter** for review inline comments (smaller, useful on its own - shrinks the buffer's job before it exists).
2. **Buffer + watcher + reactions**.

Both are currently unimplemented.

Thanks for the detailed write-up, zhfeng — I'd like to take this on. Planning to split it into two separately-shippable PRs matching the issue's own scoping:

1. **Fanout filter first** (the smaller slice) — suppresses redundant `pull_request_review_comment` events that carry a `pull_request_review_id` with no `in_reply_to_id`, since the parent `pull_request_review` event already covers them. This alone doesn't fix the silent-drop problem this issue describes, just shrinks the noise the buffer would otherwise have to deal with (the CodeRabbit-storm case) — will reference this issue for context but won't claim to close it.

2. **Buffer + drain + watcher** — the actual fix for the silent-drop problem: queue the comment on `ConflictError`, watch the active run via `StreamBridge.subscribe(run_id)` until completion, then drain into the next run. One plumbing note from reading the code: `ChannelManager`/`ChannelService` currently has no reference to the FastAPI `app` (it's constructed from a config snapshot in the lifespan, unlike request-scoped consumers that get the bridge via `app.state`), so this needs threading `app`/the stream bridge through `start_channel_service()` similarly to how `ScheduledTaskService` already gets `app` via a closure over `launch_run`. Planning to hold off on the reaction semantics (`eyes`/`confused`) for a follow-up after this lands — GitHub's reaction API has no existing integration in this codebase (all current GitHub writes go through the agent's own `gh` CLI), and it needs its own design pass (endpoint differs for issue vs. review comments, plus token/rate-limit error handling), so I'd rather not bundle a rushed version of it into the core fix.

Let me know if that split or any of the above doesn't match what you had in mind before I start.

Correction to my message above, before you spend time on it: I described the scope as "just the two reactions on the existing queue and overflow paths, with no change to the buffer semantics". Having gone through the code, that is wrong, and the difference is big enough that it changes who should decide what.

What it actually needs:

1. **A reaction capability that does not exist yet.** `Channel` (`app/channels/base.py`) has `send` / `send_file` / `receive_file` but nothing for acknowledgements. Slack, Discord and Feishu each react internally, but there is no shared entry point, and `ChannelManager` is channel-agnostic — it buffers by `thread_id` and never learns which provider it is talking to. So either `Channel` grows an optional `react()` that GitHub implements and the others no-op, or the manager gains provider-specific knowledge. The first looks right to me, but that is an ABC change and your call.

2. **The comment id is not in the message.** The dispatcher puts `repo`, `number`, `event`, `delivery_id`, `installation_id`, `recursion_limit`, `thread_id` into `metadata["github"]` — no comment id. Every reactions endpoint needs one, so `fanout_event` would have to start carrying it.

3. **`_FollowupEntry` cannot address its own comment.** It deliberately stores only `dedupe_key` and `text`, because routing identity comes from the carrier message. Reacting on _overflow drop_ means the entry has to carry enough to identify the comment it came from, so that structure grows too.

4. Only then the two call sites in `_buffer_followup` / `_enforce_followup_cap`, plus tests.

There is also a wrinkle worth deciding before any code: **not every buffered follow-up has something to react to.** The bindings fan out `issue_comment`, `pull_request_review_comment`, `pull_request_review`, `issues` and `pull_request`. The first two are comments and take reactions, but on _different_ endpoints (`/issues/comments/{id}/reactions` vs `/pulls/comments/{id}/reactions`). `pull_request_review` has no reactions endpoint at all, and for `issues` / `pull_request` the trigger is the body rather than a comment. So the feature is inherently partial — some queued follow-ups would stay silent, which is arguably worse than uniformly silent because the signal becomes unreliable.

So this is a change across the gateway and channel layers including an ABC addition, not the small thing I implied. I have not written any of it. Options as I see them:

- Add `react()` to `Channel` and plumb the comment id through, accepting that only the two comment events get a reaction.
- Skip reactions and make the acknowledgement channel-native some other way.
- Leave it, and close this issue as covered by [fix(channels): buffer and drain GitHub comments queued during a busy run #4133](https://github.com/bytedance/deer-flow/pull/4133).

Happy to implement whichever you prefer, or to leave it entirely — I would rather ask than hand you a five-file diff built on my own guess about the design.
