### Problem / motivation

DeerFlow allows a Custom Agent to be configured with the browser tool group. From a user’s perspective, this implies that browser work can be performed within that Custom Agent conversation. 
However, Custom Agent chats do not expose the Browser Live entry point or live-session panel that is available in normal workspace chats. When browser output appears, the user can view a screenshot/artifact but cannot inspect the live browser session, enter a URL, or take over an interaction in the same session. 
This is especially limiting for browser workflows that require a human step, such as signing in, completing a CAPTCHA, or checking an intermediate page before the agent continues. 
I searched existing issues and pull requests using BrowserViewProvider, BrowserTrigger, and Custom Agent/Browser Live combinations, and did not find a directly matching request or patch.

### Proposed solution

When browser control is enabled and a Custom Agent is configured with tool\_groups: \[browser\], expose Browser Live in that Custom Agent’s chat using the same feature flag and thread-ownership rules as normal workspace chats.

From a user’s perspective:

I configure a Custom Agent with browser tools.

I open a conversation with that agent.

I can open Browser Live, see the live browser session, navigate to a URL, and perform a necessary human interaction.

The agent and I continue using that same per-conversation browser session.

If Custom Agents are intentionally intended to be agent-only for browser operation, please document that restriction clearly instead.

### Affected area(s)

Frontend (UI / Next.js)

### Alternatives considered

Keep the current static screenshot/artifact preview.

This is useful for viewing output, but it cannot replace Browser Live because it is not connected to the active browser session and does not allow human navigation or takeover.

Document Custom Agents as browser-agent-only.

This is a valid alternative if it is intentional. However, the current configuration allows the browser tool group, while the README describes browser control as a per-conversation Browser Live capability without documenting a Custom Agent exclusion.

Remove browser tools from Custom Agents.

This would make the restriction explicit, but would reduce useful Custom Agent configurations. Supporting the same Browser Live UI appears more consistent with the existing tool wiring and backend browser endpoint.

### Additional context

Normal workspace chat renders BrowserTrigger and uses useBrowserControlEnabled:frontend/src/app/workspace/chats/\[thread\_id\]/page.tsx

Normal chat mounts BrowserViewProvider:frontend/src/components/workspace/chats/chat-providers.tsx

Custom Agent chat route/layout do not include those Browser Live integrations:frontend/src/app/workspace/agents/\[agent\_name\]/chats/\[thread\_id\]/{page,layout}.tsx

Custom Agent tool loading passes custom tool\_groups to the available-tool loader:backend/packages/harness/deerflow/agents/lead\_agent/agent.py

The browser navigation endpoint is scoped by thread ownership and the global browser-feature setting, without a Custom Agent exclusion:backend/app/gateway/routers/browser.py

Implemented in [#4719](https://github.com/bytedance/deer-flow/pull/4719).

Custom Agent chats now expose Browser Live for existing threads when browser control is available and the agent's `tool_groups` are unrestricted or include `browser`. Explicit non-browser allowlists, unavailable browser control, mock chats, and not-yet-created threads keep the control hidden.

The PR includes production-build E2E coverage for the enabled, unrestricted, disabled, and new-thread boundaries.
