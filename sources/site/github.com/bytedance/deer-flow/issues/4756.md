用deepseek分析了一下：

### 核心原因：事件循环被同步阻塞（Event Loop Blocking）

当一个 agent 通过 bash 工具运行脚本时，\*\*`LocalSandbox.execute_command()` → `_run_posix_command()`` 内部使用同步的` subprocess.run(...)`阻塞等待**。如果这个调用发生在 asyncio 事件循环线程上（没有被`asyncio.to\_thread`/`run\_in\_executor\` 卸载到线程池），那么：

- 该脚本运行的整个期间，**整个 ASGI 事件循环被冻结**
- 所有其他对话/线程的 HTTP 请求（包括查询、新消息、轮询）全部排队
- 积压的请求超出超时/连接限制后即返回 **500 服务器正忙**
- 直到脚本运行结束、事件循环恢复，其他对话才恢复可用

这与 AGENTS.md 中反复强调的架构约束完全吻合——本项目专门有 `tests/blocking_io/` 运行时门禁（Blockbuster），**任何在事件循环上执行的同步阻塞 IO 都会抛出 `BlockingError`**。这证明该代码库对"事件循环阻塞"这一类 bug 高度敏感，而 bash 脚本执行正是最典型的触发点。

### 支持的证据链（来自 AGENTS.md）

1. **`LocalSandbox`** 使用同步 `subprocess.run(env=...)` 执行命令（本地沙箱实现）。
2. **`bash_tool`** 是同步 LangChain 工具，若被同步地挂在图节点上就可能直接跑在事件循环线程。
3. 文档明确要求：`SandboxMiddleware` 的异步 acquire / `SandboxProvider.acquire_async` 等必须保持 off-loop，说明沙箱生命周期本身已是异步边界，但**脚本的实际执行路径**仍可能是同步阻塞点。
4. 每线程沙箱 LRU 缓存虽用 `threading.Lock`，但那是字典级短锁，不是 500 的根源；真正根源是脚本执行阻塞了共享事件循环。

### 修复方案（按优先级）

**方案 A（推荐，最小改动）：bash 工具执行卸载到线程池**

- 在 `bash_tool` 的执行路径中，把 `sandbox.execute_command(...)` 的调用用 `asyncio.to_thread(...)` 或 `run_in_executor(...)` 包起来，确保 `subprocess.run` 的阻塞等待发生在事件循环之外。
- 这样每个脚本在各自的工作线程中运行，互不阻塞，其他对话的事件循环保持响应。
- 相应地补一个 `tests/blocking_io/` 锚点测试，锁定"bash 执行 off-loop"，防止回归（与现有 `test_skills_load.py`、`test_sqlite_lifespan.py` 等锚点模式一致）。

**方案 B（加固）：SandboxMiddleware 生命周期统一 off-loop**

- 确保 `SandboxMiddleware` 的 sandbox acquire/release 与脚本执行都走异步/线程池路径，杜绝任何同步阻塞入口。

感谢补充分析。我按照当前 `main` 做了一轮双用户并发实测，目前暂未复现该问题：

- 使用 SQLite，开启认证并创建真实的用户 A、B；
- A 的长任务持续运行约 2.5 分钟；
- A 运行期间，B 的新对话正常返回 HTTP 200，并在 A 仍处于 `running` 时完成；
- B 连续访问模型/会话接口以及创建 20 个新会话，均未出现 500 或 `database is locked`；
- 同一会话重复启动任务则按预期返回 409，说明当前限制是单会话级，而不是全局互斥。

我也检查了“bash 阻塞事件循环”的假设。Windows 下 `LocalSandbox.execute_command()` 确实使用同步 `subprocess.run()`，但当前 Gateway 的 Agent 运行路径使用 `agent.astream()`；`bash_tool` 已注册异步 coroutine，并通过 `asyncio.to_thread()` 执行同步工具体。Sandbox 的 acquire/release 也已有异步卸载。因此暂时没有证据表明 bash 的 `subprocess.run()` 会直接阻塞 ASGI 事件循环，建议的线程池方案在当前代码中实际上已经存在。

不过我的测试环境不是 Windows，执行的也不是完全相同的 Deep Research 工具链，因此先保持 Issue 开放。为了继续定位，麻烦补充：

1. 用户 B 失败请求的具体 URL、HTTP 方法和完整响应体；
2. 同一时间点的 Gateway traceback；
3. 当前 Git commit 或 support bundle；
4. `database.backend`、`sandbox.allow_host_bash` 配置；
5. 问题发生时 A 是否实际调用了 bash，以及对应命令和持续时间。

如果当时确实调用了 bash，也可以先做一个最小对照：让 A 固定执行一个 30 秒的 sleep 命令，同时让 B 请求 `/api/models` 或创建新会话。这样可以直接验证是否为事件循环阻塞。

感谢补充，这次按你给出的启动命令复现出来了，也更正一下我上面“暂未复现”的结论。

根因不是 bash 阻塞 asyncio 事件循环，而是直接使用 `uvicorn --reload` 时，Uvicorn 会监听整个 `backend/`，其中包括运行时目录 `backend/.deer-flow`。Agent 在任务中生成/写入 Python 文件后会触发 Gateway reload；reload 期间另一用户的 `/api/v1/auth/me` 正好遇到连接重置或 5 秒超时，因此前端表现为 `AbortError` / `ECONNRESET`。任务停止后不再写运行时文件，所以看起来又恢复正常。

我做的对照实测：

- 未排除运行时目录：写入 `.deer-flow/*.py` 后 Gateway 进程被替换，B 的连续 auth 请求中有 4 次超时；
- 使用绝对路径排除运行时目录后：同样写入文件，Gateway 进程不变，100/100 次 auth 请求返回 HTTP 200；
- 回归测试已经覆盖 backend dev launcher 的绝对路径排除和目录预创建规则。

修复已提交：[#4759](https://github.com/bytedance/deer-flow/pull/4759)

合并后，推荐从 `backend/` 使用 `make dev`。如果仍要手动执行你贴出的 Uvicorn 命令，需要预先创建运行目录，并给 `--reload-exclude` 传入 `backend/.deer-flow` 和 `backend/sandbox` 的**绝对路径**；仅写相对路径在 Uvicorn 的 reload 匹配中并不可靠。

谢谢你补充完整的错误和启动方式，这两项信息直接定位到了 reload 边界。
