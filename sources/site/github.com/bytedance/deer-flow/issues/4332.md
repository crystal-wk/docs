真名是 **Ports & Adapters**（Cockburn, 2005）。"六边形"只是画图的偶然——作者需要一个能摆脱"上/下"方位暗示的形状，六条边没有任何含义。

它的全部内容是一个观念转变加一条规则：

> **应用只有"内外"之分，没有"上下"之分。** 数据库和浏览器没有本质区别——它们都是站在边界外、想与业务核心对话的外部世界。传统分层图把数据库画成业务的"地基"，这是错觉；六边形把它掰起来，与 UI 摆在同一圈上，降格为业务的一个"插件"。

**唯一规则**：依赖箭头永远从外指向内。核心声明接口（port），外部世界各自带转换头（adapter）来插——调用可以由内向外发起（业务调仓储），但依赖方向始终向内（仓储实现的是业务声明的接口）。调用方向与依赖方向解耦，这就是"依赖反转"的准确含义，也是它与分层架构唯一的真正区别。

**唯一检验**：业务逻辑能否在没有 HTTP、没有数据库的测试里（全部换成 fake）完整运行。能，就实现了；不能，无论目录叫什么名字都没实现。

## 二、能给 DeerFlow 带来什么：四个受众视角

先说病根：现状的根本问题不是某个具体 bug，而是**没有一套被执法的设计规范**——8 个仓储 4 种形态（无接口 / ABC 但吞裸 dict / app 侧领域对象各行其是）、同一份配置文件三套读缓存、领域规则散落在 router、SQL 文件与运行时三层。每个新增代码都在"参考现有代码"，而现有代码给出的答案是随机的。六边形重构的本质是立一套**有明确规则、可机器执法**的规范。它对四类人产生价值：

**1\. 对学习和了解 DeerFlow 的人：目录即文档，降低学习曲线。** 现状回答"Feedback 的合法状态是什么"要横跨 router 与 sql.py 两处，回答"任务何时算结束"要去 SQL 文件里找模块常量。重构后 `domain/` 目录就是系统的业务说明书——每个模块读 model.py 即知全部规则与合法状态，读 ports.py 即知它需要什么、提供什么；六个限界上下文给新人一张系统地图。规范统一后，**读懂一个模块 = 读懂所有模块**。

**2\. 对维护者与二开用户：变更局部化，高内聚低耦合。** 明确的规约让"改这里会不会影响别处"有确定答案——每类变更有明确的落点：

| 变更类型 | 动哪里 |
| --- | --- |
| 改业务**规则**（允许 rating=0、评论限长） | **只动 model.py**——现状同样的改动要碰 sql.py 两处 if，漏一处即数据不一致 |
| 改用例**编排**（评价后通知、删除加校验） | **只动 service.py**（必要时新增窄 output port） |
| 加业务**字段**（feedback 加 tags） | **五层全动**：model → port → adapter → ORM+迁移 → DTO，最不利场景 |
| 加**新用例** | service + port + router 照 Feedback 模板复制 |

对"加业务字段"要诚实：五层传导的点数不比现状少，甚至多一层——但性质完全不同。现状的每一处都是**独立决策**（校验放哪、dict 键叫什么、谁负责序列化），且漏改静默无声（dict 多键少键无人报错，直到前端渲染出 undefined）；重构后是 **1 次决策（model 定形状）+ N 次有红灯指路的机械对齐**——类型检查红 = 签名没跟上，契约测试红 = 映射漏了，域测试红 = 规则错。

一个更尖锐的场景：新增的是**隐私字段**——比如 feedback 加内部审核备注 `review_note`，闭环分析需要它，但绝不该展示给前端。现状 `_row_to_dict` 用反射把 ORM 的**全部列**自动拍进 dict，dict 直通 API 响应——**新列默认暴露**，不泄漏反而需要有人记得在某处手动剔除，漏了就是一次静默的隐私泄漏事故（比 undefined 严重得多，且同样无人报错）。重构后领域对象与响应 DTO 都是显式映射——**字段不写就不出去，暴露必须是一个显式决定**。默认方向的反转，把"记得删"变成"需要加"，隐私保护从依赖人的记性变成结构的性质。

多付出的这一点结构成本，买的是系统的**高适应性与长期稳健性**：适应性——存储、入口、业务规则各自独立演进，互不牵连；稳健性——变更的影响半径有边界、遗漏有红灯，系统不随修改次数累积腐化。二开用户则拿到清晰的扩展点：实现 port 即可接入自己的存储或入口，不需要读懂整个系统。

**3\. 对 AI 编码工具：明确规约是 AI 的护栏，终结"参考出来的乱"。** 本仓库近 90 天 750 commits、124 位贡献者，大量 AI 辅助编码。AI 写代码靠模仿仓库既有模式——现状 4 种仓储形态并存，AI 每次模仿到哪种是随机的，**乱会自我复制、加速扩散**。重构给 AI 三样东西：一句话圈层规则（写哪、怎么写无歧义）、Feedback 复制模板（生成有唯一正确样板）、AST 执法测试进 CI（越界代码被机器拦截，不靠 reviewer 肉眼）。纯文字规约 AI 会漂移；结构 + CI 执法不会。规约不是限制 AI，是让 AI 的产出可预测。

**4\. 对测试：成本结构改变。** 现状无接口 seam，53 个测试文件必须起真 SQLite 临时库；重构后域与服务层零 IO 单测（注入 fake），真库只留给 adapter 契约测试。测试更快，失败定位也更清晰：域测试红 = 规则错，契约测试红 = 存储实现错。

且以上不以风险为代价：8 个小 PR 渐进交付、行为等价、beta 通道用户可控、存量部署"升级即换代码"（零 schema/数据/配置格式变更）。

## 三、Feedback 的业务设计

**现状与建模**：数据模型是"每用户对每次回答（run）至多一份评价"（唯一约束 thread+run+user）。现有 6 个 API 端点中 4 个无前端消费者，评审已裁剪投机 API——per-run 统计（FeedbackStats）因"统计恒为 0/1 且零消费"从领域契约移除；前端 UI 数据链路当前未接通，随 PR1-fe 接通，beta 通道首发即带用户可见的功能增量。

**业务意义——一份评价，两个去向**：feedback 是用户对一次回答的 👍👎+评论。今天它是低频小功能，但这份数据有两条明确的消费路径：

- **为这个用户（个性化）**：带评论的点踩（如"太啰嗦了"）提炼成该用户的偏好记忆，下次回答更合口味。完全复用现有 memory 抽取管线（评价作为附加信号喂给同一个提炼流程），零新机制；无评论的裸点赞点踩信号太弱，不进记忆。
- **为所有用户（产品改进）**：被点踩的对话连同完整执行轨迹归档为"差案例"，积累成回归评估集——调优提示词/技能后重放案例验证效果。诚实的定位：自部署场景评价量少，**做不了统计报表，做得了案例库**——这是自演进闭环（采集→评估→迭代）现实可行的起点。

**路径一细节（个性化记忆）**：

- **触发时机**：评价发生在回答结束**之后**（用户看完才点），因此它是记忆管线的第二个入队触发点——评价提交后，将"用户对这条回复点了踩 + 评论原文 + 回复摘要"作为附加信号送入现有的记忆提炼流程（防抖队列、后台 LLM 提炼、原子写入，全部现成，零新机制）。
- **入选规则**：仅**带评论**的评价触发提炼——裸 👎 不知道踩的是什么，噪声大于信号；提炼出的偏好条目标注来源（source=feedback），可审计可回溯。
- **治理复用**：去重、过期审查、合并、注入预算全部沿用现有 memory 机制，不新增治理逻辑。

**路径二细节（闭环优化）**——归因是核心难题，三个难点及对策：

1. **多轮累积**：点踩可能针对整段会话的方向而非单条回复——归档时连同该回答之前的轨迹窗口一起记录，分析按会话（thread）聚合而非只看单次回答；
2. **子代理归因**：被踩的回答可能大部分工作由子代理完成——需关联执行轨迹中的委托记录，才能分解"主 agent 决策问题（该不该委托、如何合成）vs 子代理执行问题"；
3. **场景标签**：回答本身没有"场景"字段——以激活的技能、工具组合作为场景代理变量（"某技能的差案例率"直接可算，价值最高）。

闭环按四层推进：**信号层**（评价关联执行轨迹）→ **案例层**（好/差案例自动归档，轨迹以引用+关键摘要记录）→ **评估层**（案例集成为回归评估基准，调优后重放验证）→ **调优层**（改提示词/技能/参数）。数据量的诚实定位：自部署单实例评价量少，**做不了统计报表，做得了案例库**；跨实例统计需团队形态部署或 opt-in 遥测（隐私敏感，远期另议）。

### 4.1 Feedback 领域化（本次重构范围）

```python
# ── 内圈（harness domain/feedback/，零基础设施依赖，CI 执法）──

# model.py —— 聚合：规则的唯一宿主
VALID_RATINGS = (1, -1)

class InvalidRatingError(FeedbackError): ...
class DuplicateFeedbackError(FeedbackError): ...   # 唯一约束的领域表达 → 409
class RunNotFoundError(FeedbackError): ...

@dataclass(frozen=True)
class Feedback:
    """每用户对每次回答（run）至多一份评价。"""
    feedback_id: str
    run_id: str
    thread_id: str
    rating: int                                    # 不变量 ∈ {+1, -1}
    user_id: str | None = None
    comment: str | None = None
    created_at: datetime = field(default_factory=lambda: datetime.now(UTC))

    def __post_init__(self):                       # 创建即一致：构造期爆炸
        if self.rating not in VALID_RATINGS:
            raise InvalidRatingError(self.rating)

    @classmethod
    def create(cls, *, run_id, thread_id, rating, user_id=None, comment=None):
        return cls(feedback_id=str(uuid.uuid4()), run_id=run_id,
                   thread_id=thread_id, rating=rating,
                   user_id=user_id, comment=comment)

# ports.py —— output ports：技术中立，无 SQL/文件/哨兵词汇
#（评审裁剪后 7 方法；FeedbackStats/stats_for_run 已因无业务价值移除）
@runtime_checkable
class FeedbackRepository(Protocol):
    async def add(self, feedback: Feedback) -> Feedback: ...       # 已存在 → Duplicate
    async def save(self, feedback: Feedback) -> Feedback: ...      # 按聚合身份幂等覆盖
    async def find_for_run(self, thread_id, run_id, *, user_id) -> list[Feedback]: ...
    async def latest_per_run_in_thread(self, thread_id, *, user_id) -> dict[str, Feedback]: ...
    async def remove_for_run(self, thread_id, run_id, *, user_id) -> bool: ...

class RunLookup(Protocol):
    """窄 port：只问 run 归属哪个 thread。"""
    async def thread_of(self, run_id: str) -> str | None: ...

# service.py —— input port：用例编排，user_id 显式传参
class FeedbackService:
    def __init__(self, repository: FeedbackRepository, runs: RunLookup):
        self._repo, self._runs = repository, runs

    async def rate_run(self, thread_id, run_id, *, rating, comment, user_id):
        if await self._runs.thread_of(run_id) != thread_id:
            raise RunNotFoundError(run_id)         # 原 router 手工校验收编
        return await self._repo.save(Feedback.create(
            run_id=run_id, thread_id=thread_id, rating=rating,
            user_id=user_id, comment=comment))

            return self._to_domain(row)            # row → 领域对象，tzinfo 归一化于此

class RunStoreRunLookup:
    """RunLookup 的 adapter：3 行包装既有 RunStore（宽接口→窄接口），
    复用既有查询、不写新 SQL。用途：run 归属校验（防跨 thread 越权写评价）。"""
    def __init__(self, run_store): self._rs = run_store
    async def thread_of(self, run_id: str) -> str | None:
        run = await self._rs.get(run_id)
        return run.get("thread_id") if run else None

# app/gateway/deps.py —— 组合根：唯一装配点
app.state.feedback_service = FeedbackService(
    repository=SqlFeedbackRepository(sf),
    runs=RunStoreRunLookup(app.state.run_store))

# routers/beta/feedback.py —— 纯协议转换
@router.put("/{thread_id}/runs/{run_id}/feedback")
async def upsert_feedback(thread_id, run_id, body, request,
                          svc=Depends(get_feedback_service)):
    user_id = await get_current_user(request)
    try:
        fb = await svc.rate_run(thread_id, run_id, rating=body.rating,
                                comment=body.comment, user_id=user_id)
    except InvalidRatingError:  raise HTTPException(400)
    except RunNotFoundError:    raise HTTPException(404)
    return _to_response(fb)
# POST 额外捕获 DuplicateFeedbackError → 409（原 500，唯一行为差异）
```

```python
        ...

    async def rate_run(self, thread_id, run_id, *, rating, comment, user_id):
        fb = await self._repo.save(Feedback.create(...))
        if self._signals and fb.comment and fb.user_id:          # 带评论才投递

                    user_id=fb.user_id, thread_id=fb.thread_id,
                    run_id=fb.run_id, rating=fb.rating, comment=fb.comment))
        return fb

    async def submit(self, s: FeedbackSignal) -> None:
        self._q.enqueue(user_id=s.user_id, thread_id=s.thread_id,
            extra_note=f"用户对该会话中一条回复评价 {s.rating:+d}，评论：{s.comment}")
        # updater 的提炼 prompt 携带此附注 → LLM 抽出 preference 条目
        # （source=feedback，confidence/去重/过期/合并沿用现有治理）

# 组合根：memory.enabled 时装配，否则 None（信号静默关闭）
```

### QA

#### Exception为什么放在dmian/model中？

1. 领域错误是领域语言的一部分。"同一用户对同一次回答重复评价"是一个业务事实，不是技术故障——谁拥有这个概念，谁就定义它。domain 声明"什么是合法状态"（VALID\_RATINGS），也就同时声明"什么算业务上的失败"（DuplicateFeedbackError）。错误类型就是错误的统一语言。
2. 依赖方向决定它别无去处。这些异常被三方使用：聚合在 **post\_init** 里抛 InvalidRatingError；adapter 在 commit 处把 IntegrityError 翻译成 DuplicateFeedbackError 抛出（这个翻译目标写在 port 契约注释里——"add 撞重复 → raise DuplicateFeedbackError"，所以异常类型是 port 契约的一部分）；router 捕获它们映射 HTTP 码（409/404/400）。adapter 和 router 都在 app 侧、都要 import 这些类，而 harness 禁止 import app——共享词汇只能放在依赖箭头的终点，即内圈。
3. 不违反 domain 纯度。class FeedbackError(Exception) 只依赖 builtins——Exception 是 Python 语言设施，不是基础设施，test\_harness\_domain\_purity 不拦也不该拦。
