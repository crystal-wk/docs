### Problem summary

A queued Discord typing-task starter can run after DiscordChannel.stop() has completed, creating an active background typing loop that is no longer tracked or cancelled by the stopped channel.

### Affected area(s)

Backend API (gateway / endpoints / SSE)

### What happened?

DiscordChannel.\_on\_message() schedules \_start\_typing() through asyncio.create\_task().

\_start\_typing() does not begin immediately. If DiscordChannel.stop() runs first, it clears the current \_typing\_tasks mapping and marks the channel stopped. The previously queued starter can then resume and create a new infinite \_typing\_loop after that cleanup boundary.

The resulting task remains active in \_typing\_tasks even though channel.is\_running is False. Because stop() has already returned, the task is no longer covered by that shutdown and may continue retaining Discord/channel objects and attempting typing notifications.

This is a task-ordering race, not a timing-dependent network reproduction: explicitly scheduling the starter, stopping the channel before yielding to it, and then allowing it to run reproduces the leaked task deterministically.

### Expected behavior

Once DiscordChannel.stop() returns, no queued typing starter should be able to create a new typing loop. The channel should have no active or tracked typing tasks after shutdown.

### Steps to reproduce

1. Check out latest main at [17531d7](https://github.com/bytedance/deer-flow/commit/17531d7c118d6111b863f945ff910a7889a235b0).
2. From backend/ in PowerShell, run:

@' 
import asyncio 
from app.channels.discord import DiscordChannel 
from app.channels.message\_bus import MessageBus

class Target: 
async def trigger\_typing(self): 
pass

async def main(): 
channel = DiscordChannel(MessageBus(), {}) 
channel.\_running = True

```
starter = asyncio.create_task(
    channel._start_typing(Target(), "chat-1")
)

await channel.stop()
await starter

leaked = channel._typing_tasks["chat-1"]
print("channel running after stop:", channel.is_running)
print(
    "typing task created after stop:",
    "chat-1" in channel._typing_tasks,
)
print("typing task still active:", not leaked.done())

leaked.cancel()
await asyncio.gather(leaked, return_exceptions=True)
```

asyncio.run(main()) 
'@ | uv run python -

3. Observe that the channel is stopped but a new active typing task exists.

### Additional context

The intended scope is limited to the Discord typing lifecycle:

- prevent a queued typing starter from crossing the stopped-channel boundary;
- avoid the unnecessary fire-and-forget wrapper around typing-task registration where possible;
- add a deterministic regression test that controls task ordering without arbitrary sleep;
- update the required backend lifecycle documentation.

Normal Discord message routing, active-channel typing behavior, configuration, persistence, and public APIs should remain unchanged.

I checked the originating typing-indicator PR [#2842](https://github.com/bytedance/deer-flow/pull/2842) and the current open Discord-related PRs. PR [#3140](https://github.com/bytedance/deer-flow/pull/3140) touches discord.py only for thread-mapping persistence and does not modify \_start\_typing, \_typing\_tasks, or their shutdown behavior.
