### Problem / motivation

MCP 协议工具不仅可能返回长时间运行任务的 task\_id/job\_id，也可能在服务内部生成文件、目录或其他后续工具需要消费的产物。 
目前这些信息主要通过工具返回消息进入 Agent 上下文。当会话经过多轮对话并触发上下文压缩后，相关信息可能被截断、摘要或丢失，导致：

- Agent 无法找回之前生成的 task\_id/job\_id；
- Agent 猜测或编造文件路径；
- 多次调用同一个工具时混淆不同任务及其产物；
- 下游 MCP 工具无法准确使用上游工具生成的文件；

依赖 middleware 在压缩后重新注入信息，但会占用上下文空间，并且仍要求模型复制完整路径或任务 ID。似乎是一个更通用的“外部工具句柄和产物引用进入模型上下文后失效”的问题。

### Proposed solution

增加一个与具体 MCP 协议和工具实现解耦的持久化 Task/Artifact Registry。 
工具调用返回结构化结果后，由运行时识别其中的任务句柄和产物引用，并保存：

- 本地任务 ID；
- 远端 task\_id/job\_id；
- 工具名称；
- tool\_call\_id 和调用序号；
- 任务状态；
- 文件路径或其他产物信息；
- 任务与产物之间的关联；
- 用户和 thread 的归属关系。

模型上下文中不直接保存或依赖真实路径和远程任务 ID，而只提供稳定的本地短引用。 
当 Agent 后续调用工具时，运行时在工具调用边界将短引用确定性解析为真实的 task\_id 或文件路径，并进行 thread/session 所有权校验后再传递给 MCP 服务。

### Affected area(s)

MCP

### Alternatives considered

尝试增加一个middleware层拦截产物的返回，并在压缩后注入。 
似乎不是一个通用的解决方案

[@AnnaSuSu](https://github.com/AnnaSuSu) 感谢关注。这里可能产生了一点范围上的误解。

[#4652](https://github.com/bytedance/deer-flow/issues/4652) 主要解决的是长周期异步 MCP 任务的生命周期管理，包括：

- 远端 task\_id/job\_id 持久化；
- 后台轮询；
- 重启恢复；
- 任务取消；
- Agent 唤醒。

而目前关注的是更一般的工具产物引用问题，并不要求产物一定来自长周期任务，也不要求启动后台轮询。

例如：

1. MCP协议工具 A 同步执行完成并生成一个文件；
2. 工具 A 返回文件路径；
3. 会话经过多轮对话并发生上下文压缩；
4. 后续同一个 MCP 工具服务中 B 需要消费这个文件。

此时即使没有 task\_id、没有后台任务、没有轮询，文件路径仍然可能丢失或被模型幻觉。

关注的是：

- 工具输出产物的通用登记；
- 产物与 tool\_call\_id/call\_index/job\_id 的关联；
- 生成稳定的 artifact handle；
- 后续工具调用边界将 artifact handle 确定性解析为真实路径或其他句柄；
- 支持多个工具、多次调用和跨轮次消费。
- 支持同一个工具多次调用产生多份不同文件。以及后续消费选择准确性。

[#4665](https://github.com/bytedance/deer-flow/pull/4665) 中的 result\_artifact 可以作为远程工具产物的一种来源，但不能覆盖所有同步 MCP 工具产生的文件或其他外部产物。

我们希望 讨论的是通用 Artifact/Handle Registry，以及它与 [#4652](https://github.com/bytedance/deer-flow/issues/4652) 中Task Runtime 的衔接，而不是重复实现长任务轮询。
