## Summary

The README [Improper Deployment May Introduce Security Risks](https://github.com/bytedance/deer-flow#improper-deployment-may-introduce-security-risks) section states DeerFlow is _"designed by default to be deployed in a local trusted environment (accessible only via the 127.0.0.1 loopback interface)"_. However, the actual defaults bind the gateway to `0.0.0.0`:

- `scripts/serve.sh:257` — local dev entrypoint runs `uvicorn ... --host 0.0.0.0`
- `backend/app/gateway/config.py:9,22` — `GatewayConfig.host` default and `GATEWAY_HOST` fallback are `0.0.0.0`
- `backend/Dockerfile` / `docker-compose.yaml` — `--host 0.0.0.0` (needed inside the container network; the risk there depends on port publishing)

A user following the documented trust model ("loopback only by default") would assume the gateway is not reachable beyond the local machine, but a plain `make dev` / `scripts/serve.sh` actually listens on all interfaces.

## Why it matters

The gateway exposes endpoints that are intentionally public by design (`/api/v1/auth/register` auto-login, `/api/runs/stream|wait` run agent with file/web tools). On a LAN or cloud host, an attacker that can reach the port can register an account and drive the agent without any prior credential — consuming LLM quota and reading/writing the sandbox workspace. This is exactly the "Unauthorized illegal invocation" scenario the README warns about, but the default bind makes it the _default_ outcome rather than an opt-in risk.

## Proposed fix

- Default local dev and config to `127.0.0.1`, with an explicit env opt-in (`GATEWAY_BIND_HOST=0.0.0.0`) for intentional exposure
- Keep Docker bindings as-is (`0.0.0.0` inside the container is required by the container network) but document that publishing ports exposes the gateway
- Update the README security note to state the actual default bind per deployment mode

A PR implementing this is open: [#4697](https://github.com/bytedance/deer-flow/pull/4697)

## Severity

This is a defense-in-depth / documentation-mismatch issue rather than a code-level vulnerability — the README already warns against untrusted deployment. The value of the fix is making the documented trust model match reality by default.

Update: this is now **resolved on main** — the README has a "Deployment Defaults" section stating the Docker stack publishes its entry port on `127.0.0.1` only (with `BIND_HOST=0.0.0.0` as an explicit opt-in in `.env`), and the local-dev gateway binds via `GATEWAY_BIND_HOST` defaulting to `127.0.0.1`. The docs/implementation mismatch described here no longer exists. Closing this issue (see also PR [#4697](https://github.com/bytedance/deer-flow/pull/4697), closed for the same reason).
