### Problem summary

Concurrent parent runs can share, cancel, or remove each other's background subagent state when their provider-generated `tool_call_id` strings are equal.

### Affected area(s)

Agents / LangGraph (subagent execution)

### What happened?

`task_tool` passes the injected provider `tool_call_id` directly to `SubagentExecutor.execute_async()` as its `task_id`:

```python
# task_tool.py
task_id = executor.execute_async(prompt, task_id=tool_call_id)
```

`execute_async()` then uses that value as the only key in a process-global registry. A second concurrent run with the same ID silently replaces the first result holder:

```python
_background_tasks: dict[str, SubagentResult] = {}

with _background_tasks_lock:
    _background_tasks[task_id] = result
```

The scheduler closure later looks the holder up again by that global key instead of retaining the holder created for its own execution:

```python
with _background_tasks_lock:
    _background_tasks[task_id].status = SubagentStatus.RUNNING
    result_holder = _background_tasks[task_id]
```

As a result, if run A and run B both use `task_id="same-provider-tool-call-id"` before their scheduler closures start:

- B's registration overwrites A's registry entry.
- Both workers attach to B's `SubagentResult`.
- A can publish its result into B's holder.
- cancelling A by the returned ID signals B's `cancel_event`.
- cleanup performed by A can delete B's registry entry.
- either caller can observe the other run's status/result, or see `Task disappeared from background tasks`.

The lock prevents concurrent dictionary corruption, but it does not provide a namespace for the key.

This is not only theoretical provider behavior: [#3142](https://github.com/bytedance/deer-flow/issues/3142) established that OpenAI-compatible providers may reuse tool-call ID strings and that DeerFlow must not treat them as globally unique. Here the registry scope is the whole Python process, across unrelated threads/runs.

There is a second process-global map keyed only by `tool_call_id`, `_subagent_usage_cache`, which may need the same scope review, although the deterministic reproduction below focuses on `_background_tasks`.

### Expected behavior

Each background subagent execution has a server-generated internal identity that is unique within the process. Provider `tool_call_id` remains a correlation/display field and the original ID is still used for the returned `ToolMessage`, but it is not the ownership key for execution state.

Polling, cancellation, timeout handling, and cleanup for one parent run must never operate on another run's `SubagentResult`, even when their provider tool-call IDs are identical.

### Steps to reproduce

Revision tested:

```
17531d7c118d6111b863f945ff910a7889a235b0
```

1. Create two `SubagentExecutor` instances representing different parent runs/traces.
2. Replace `_scheduler_pool` with a deterministic queue so submitted closures do not start immediately.
3. Call both executors before releasing the queued closures:

```python
id_a = run_a.execute_async("alpha", task_id="same-provider-tool-call-id")
holder_a = executor_module._background_tasks[id_a]

id_b = run_b.execute_async("beta", task_id="same-provider-tool-call-id")
holder_b = executor_module._background_tasks[id_b]

assert holder_a is not holder_b
assert executor_module._background_tasks[id_a] is holder_b  # A was overwritten
```

4. Release run A's scheduler closure after B has registered.
5. Observe that run A resolves `result_holder` to `holder_b`.
6. Call `request_cancel_background_task(id_a)` and observe `holder_b.cancel_event.is_set()` while `holder_a.cancel_event` remains clear.
7. Complete run A and call `cleanup_background_task(id_a)`; B's registry entry is removed.

I ran a deterministic harness that AST-extracts the current upstream `execute_async`, `get_background_task_result`, `request_cancel_background_task`, and `cleanup_background_task` functions, replacing only external dependencies and the scheduler. It reproduces on every run.

### Suggested fix and regression coverage

- Generate a full server-side execution UUID for the registry key; do not pass `tool_call_id` as the internal `task_id`.
- Keep `tool_call_id` separately for trace/display and `ToolMessage` correlation.
- Have each scheduler closure retain its own `SubagentResult` rather than re-resolving ownership through a mutable global key.
- Add a regression test with two executors and the same provider ID, asserting independent result, cancel, timeout, and cleanup behavior.
- Review `_subagent_usage_cache` for the same cross-run key collision.

## Follow-up: reproduced through the real Gateway + frontend path

I ran a deterministic full-stack reproduction against both the baseline revision and the fix branch.

The test drives two concurrent parent runs through the real Gateway `/runs/stream` endpoint. Both model responses intentionally use the same provider tool-call ID:

```
call_reused_provider_id_4757
```

The subagent model returns distinguishable results:

```
run A -> A_RESULT
run B -> B_RESULT
```

### Baseline

Against:

```
17531d7c118d6111b863f945ff910a7889a235b0
```

The process-global registry uses the provider ID as its ownership key. After A and B register:

```
_background_tasks["call_reused_provider_id_4757"] = holder_B
```

Observed through real SSE and persisted thread history:

- A received `task_running` events containing both `A_RESULT` and `B_RESULT`.
- A eventually completed with `A_RESULT`.
- B received `Task disappeared from background tasks`.
- The DeerFlow frontend rendered B as a failed subtask.

Evidence:

- `baseline4-a.sse`: A's progress contains both `A_RESULT` and `B_RESULT`.
- `baseline4-b.sse`: B emits `task_failed` with `Task disappeared from background tasks`.
- The DeerFlow frontend rendered the same failure in the B thread.

### Fix branch

On the fix branch, the external provider ID remains unchanged for ToolMessage/SSE/frontend correlation, but execution ownership uses a server-generated `execution_id`.

Observed:

- A completed with `A_RESULT`.
- B completed with `B_RESULT`.
- Both frontend subtask cards displayed completed status.
- No cross-run result or cleanup contamination was observed.

This confirms the issue is not only a unit-level theoretical collision. It affects the real run lifecycle, SSE task events, persisted ToolMessages, and frontend task status.

The exact terminal result is race-dependent: one run may consume the other run's result, or one run may disappear during cleanup. The reproduction above captured the disappearance variant and cross-run progress contamination deterministically.

The local frontend screenshots and raw SSE captures are available from the reporter's reproduction workspace. The focused backend regression suite passed (`124 passed`), and the Next.js frontend build passed.
