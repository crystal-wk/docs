# RFC: Shared Sandbox Identity and Acquire Serialization

**Status:** Draft for feedback. 
**Scope:** Two behavior-preserving shared mechanisms used by remote sandbox 
providers. 
**Non-goals:** User quotas, admission, capacity policy, ownership changes, 
warm-pool unification, or a provider template-method hierarchy.

## 1\. Summary

AIO, E2B, BoxLite, and Tenki independently implement two mechanisms that now 
have four consumers:

1. deterministic sandbox-id derivation from `(user_id, thread_id)`;
2. in-process serialization of provider-selected lifecycle transitions.

This RFC extracts those mechanisms into small shared components without changing 
provider lifecycle, public tool behavior, capacity semantics, or remote resource 
identity. It is deliberately independent from the active-admission RFC.

## 2\. Motivation

### 2.1 Identity is a compatibility boundary

All four providers currently use the same expression:

```python
hashlib.sha256(f"{user_id}:{thread_id}".encode()).hexdigest()[:16]
```

The duplicate is small, but changing one copy and not the others can cause 
cross-provider inconsistency, tenant-isolation regressions, or orphaned warm 
resources after an upgrade. Centralizing the algorithm makes its compatibility 
status explicit.

### 2.2 Acquire serialization has already drifted

- AIO has cancellation-safe async acquisition using a dedicated executor.
- E2B serializes synchronously while its async entry point offloads the complete 
 acquire operation to a dedicated executor.
- BoxLite and Tenki lock by derived sandbox id.
- every implementation retains one lock for every historical thread until 
 provider shutdown.

The shared component should preserve each call path while standardizing 
cancellation safety and fixing unbounded lock-table growth.

## 3\. Design principles

- Composition, not a new provider base class.
- Pure functions for identity; one lifecycle-owning object for locks.
- Zero intended behavior change and no remote id migration.
- Provider-specific acquire, discover, ownership, reaper, and capacity logic 
 remain private.
- Each extraction is independently mergeable and revertable.

## 4\. Shared identity

New module: `deerflow.sandbox.identity`.

```python
SANDBOX_ID_VERSION = 1


def derive_sandbox_scope_token(user_id: str, thread_id: str) -> str:
    """Return the durable 16-lowercase-hex sandbox scope token."""


def is_sandbox_scope_token(value: str) -> bool: ...
```

`derive_sandbox_scope_token` must reproduce the current bytes exactly, including 
separator, default UTF-8 encoding, SHA-256, lowercase hex, and 16-character 
truncation. The function's docstring states that changing any of these is a 
breaking migration because existing containers and VMs would no longer be found.

There is intentionally no `parse_sandbox_scope_token`: a truncated hash is not 
reversible. `is_sandbox_scope_token` validates shape only.

Local keeps the readable `local:{user}:{thread}` id and its existing parser. It 
does not adopt the remote format. If local parsing is later shared, it should use 
a separately named `parse_local_sandbox_id` function.

The neutral name is deliberate: AIO, BoxLite, and Tenki use the token as their 
DeerFlow-side sandbox id, while E2B uses it as a warm-pool lookup seed and gets 
the actual remote id from the E2B API. Admission keys are not defined here; they 
belong to the admission RFC and use a separate compatibility domain.

### 4.1 Collision defense

The helper does not weaken existing collision checks. AIO and BoxLite retain 
their full `(user_id, thread_id)` identity maps and fail closed when a truncated 
id is associated with another scope. E2B retains its metadata filtering. Tenki 
continues to rely on the current 64-bit collision probability and does not gain a 
new full-identity map in this behavior-preserving RFC. Centralizing derivation is 
not a substitute for complete identity verification where it already exists.

## 5\. Acquire serializer

New module: `deerflow.sandbox.acquire_serialization`.

```python
class AcquireSerializer[KeyT: Hashable]:
    @contextmanager
    def hold(self, key: KeyT) -> Iterator[None]: ...

    @asynccontextmanager
    async def hold_async(
        self, key: KeyT
    ) -> AsyncIterator[None]: ...

    def close(self) -> None: ...
```

The context-manager API makes lock release unconditional and prevents callers 
from acquiring without a matching `finally`. Providers select the key that 
preserves their current collision and lifecycle semantics; the component does 
not reinterpret it.

Required behavior:

- calls using the same provider-selected key never overlap;
- different scopes may proceed concurrently;
- cancellation while waiting asynchronously never leaves the lock acquired;
- cancellation after acquisition releases on context exit;
- async waiting never blocks the event loop;
- the implementation does not consume the default executor;
- `close()` rejects new holders and releases executor resources without 
 invalidating a currently executing critical section;
- lock entries are removed when they have no holder and no waiters.

### 5.1 Lock-table lifecycle

Each entry contains a lock plus a holder/waiter reference count. Looking up an 
entry increments the count while holding the table lock. Both successful exit 
and cancelled wait decrement it. The entry is deleted only when the count 
reaches zero and the lock is not held.

This avoids the current one-lock-per-historical-thread growth without relying on 
`WeakValueDictionary`, whose collection timing would make reasoning about queued 
waiters harder.

### 5.2 Async execution

The component owns a bounded dedicated executor for blocking 
`threading.Lock.acquire`. It follows AIO's existing shield-and-release callback: 
if the coroutine is cancelled while the worker is waiting, completion releases 
the subsequently acquired lock and decrements the entry reference.

E2B may continue to offload its entire synchronous acquire function and use 
`hold()` inside that worker. It does not need to switch its remote SDK path to 
native async merely to consume this component.

## 6\. Provider integration

### AIO

- replace `_deterministic_sandbox_id` with `derive_sandbox_scope_token`;
- replace `_thread_locks` and module-level async lock helpers with one serializer;
- keep `(user_id, thread_id)` as the key and serialize acquire only, matching 
 current behavior;
- preserve flock, ownership, `_local_teardown`, `_acquire_epoch`, and async 
 readiness behavior.

### E2B

- replace `_stable_seed` with the shared identity helper — note that for E2B 
 the derived value is the warm-pool lookup _seed_, not the provider-issued 
 remote id (which comes from the E2B API); calling it a "sandbox id" in E2B 
 code is historical;
- replace `_thread_locks` with `AcquireSerializer.hold` around both acquire and 
 release transitions;
- keep `(user_id, thread_id)` as the serializer key;
- preserve its acquire executor, capacity condition, Redis ledger, reservation 
 tokens, reconciliation, tombstones, and overflow policies.

### BoxLite

- replace `_sandbox_id` and `_acquire_locks`;
- keep the derived sandbox id as the serializer key and serialize acquire only, 
 preserving current collision exclusion and release behavior;
- preserve the private event loop and warm-pool behavior.

### Tenki

- replace `_sandbox_id` and `_acquire_locks`;
- keep the derived sandbox id as the serializer key and serialize acquire only;
- preserve SDK, bootstrap, health check, and warm-pool behavior.

### Local

No change. Local creation is already serialized through its object-cache lock, 
and its readable id is intentionally different.

## 7\. What remains provider-private

| Mechanism | Provider | Reason |
| --- | --- | --- |
| create/discover flock | AIO | backend-specific cross-process exclusion |
| teardown reservation and acquire epoch | AIO | tied to its reaper protocol |
| capacity condition, reservations, tombstones | E2B | physical remote-capacity correctness |
| private event loop | BoxLite | loop-affine handle correctness |
| warm-pool health checks/bootstrap | BoxLite/Tenki | SDK-specific behavior |

No template-method provider base class is introduced. The similar-looking 
acquire flows have materially different step contracts and failure recovery.

## 8\. Rollout plan

### Phase 1: identity

- add exhaustive golden-vector tests, including empty/non-ASCII values;
- switch one provider at a time;
- prove every provider still produces the exact previous id;
- document the algorithm as a compatibility contract.

### Phase 2: serializer contract

- add sync mutual-exclusion, cross-key concurrency, cancellation-before-acquire, 
 cancellation-after-acquire, close-race, and lock-entry reclamation tests;
- add a blocking-IO runtime anchor proving async waits stay off the event loop.

### Phase 3: provider migration

- migrate AIO first because it supplies the reference cancellation behavior;
- migrate E2B, BoxLite, and Tenki in separate commits;
- run each provider's existing concurrency, release-race, warm-reclaim, shutdown, 
 and identity-collision tests after its migration.

## 9\. Compatibility and rollback

- `SandboxProvider` and sandbox tool contracts are unchanged.
- Every provider's derived compatibility token is byte-for-byte unchanged; E2B's 
 provider-issued remote id remains untouched.
- Existing warm resources remain discoverable.
- No config keys or database schema are added.
- Each provider migration can be reverted independently.
- The shared serializer must be closed from provider shutdown/reset paths; tests 
 pin idempotent close behavior.

## 10\. Acceptance criteria

- Golden vectors match all four current identity implementations.
- No provider loses any existing identity-collision defense.
- Every transition currently protected by a provider lock remains protected by 
 the same effective key; this RFC does not newly serialize unprotected release 
 paths.
- A cancelled async waiter never leaks a lock or a lock-table entry.
- Lock-table size returns to zero after all distinct scopes finish.
- E2B capacity and reconciliation tests pass without ledger changes.
- AIO ownership/reaper race tests pass unchanged.
- BoxLite's private-loop and Tenki's warm-pool tests pass unchanged.
- No user-visible configuration or behavior changes.

## 11\. Relationship to active admission

Admission keys use a separate helper in `deerflow.sandbox.admission.identity`. 
This RFC does not import quota, Redis admission, user records, or admin APIs, and 
the admission RFC does not depend on this module. Either RFC can land first.

# RFC：共享 Sandbox Identity 与 Acquire Serialization

**状态：** 草案，等待反馈。 
**范围：** 四个远端 sandbox provider 共用的两项、保持行为不变的机制。 
**非目标：** 用户配额、admission、容量策略、ownership 改造、warm-pool 统一，或 
provider 模板方法继承层级。

## 1\. 摘要

AIO、E2B、BoxLite、Tenki 各自实现了两项已有四个消费者的机制：

1. 从 `(user_id, thread_id)` 派生确定性 sandbox id；
2. 对 provider 选定的生命周期状态转换做进程内串行化。

本 RFC 将其提取成小型共享组件，不改变 provider 生命周期、公开 tool 行为、容量 
语义或远端资源 identity。它与 active-admission RFC 完全独立。

## 2\. 动机

### 2.1 Identity 是兼容边界

四个 provider 当前使用相同表达式：

```python
hashlib.sha256(f"{user_id}:{thread_id}".encode()).hexdigest()[:16]
```

重复代码很小，但只修改其中一份可能造成跨 provider 不一致、tenant isolation 回归， 
或升级后遗留无法重新发现的 warm 资源。集中算法可以明确其兼容性地位。

### 2.2 Acquire serialization 已发生漂移

- AIO 使用专用 executor，支持取消安全的异步 acquire；
- E2B 同步串行化，async entry point 把整个 acquire 卸载到专用 executor；
- BoxLite、Tenki 按派生 sandbox id 加锁；
- 每份实现都会保留历史上每个 thread 的锁，直到 provider shutdown。

共享组件应保留各自调用路径，同时统一取消安全并解决 lock table 无界增长。

## 3\. 设计原则

- 使用组合，不新增 provider 基类；
- identity 使用纯函数，锁由一个拥有生命周期的对象管理；
- 目标是零行为变化，不迁移远端 id；
- provider 私有的 acquire、discover、ownership、reaper、capacity 逻辑保持私有；
- 两项提取均可独立合并和回滚。

## 4\. 共享 identity

新增模块：`deerflow.sandbox.identity`。

```python
SANDBOX_ID_VERSION = 1


def derive_sandbox_scope_token(user_id: str, thread_id: str) -> str:
    """返回持久兼容的 16 位小写十六进制 sandbox scope token。"""


def is_sandbox_scope_token(value: str) -> bool: ...
```

`derive_sandbox_scope_token` 必须逐字节复现当前结果，包括分隔符、默认 UTF-8 编码、 
SHA-256、小写 hex 与 16 字符截断。docstring 必须说明修改任一细节都是 breaking 
migration，因为现有容器与 VM 将无法重新发现。

刻意不提供 `parse_sandbox_scope_token`：截断 hash 不可逆。 
`is_sandbox_scope_token` 只校验格式。

Local 保留可读的 `local:{user}:{thread}` id 与现有 parser，不采用远端格式。如果未来 
共享 Local parser，应使用单独命名的 `parse_local_sandbox_id`。

中性命名是刻意的：AIO、BoxLite、Tenki 把 token 用作 DeerFlow 侧 sandbox id；E2B 
只把它用作 warm-pool 查找 seed，实际远端 id 由 E2B API 返回。admission key 不在 
本模块定义；它属于 admission RFC，并使用独立的兼容性 domain。

### 4.1 碰撞防御

helper 不削弱现有 collision check。AIO、BoxLite 保留完整 `(user_id, thread_id)` 
identity map，在截断 id 属于其他 scope 时 fail closed；E2B 保留 metadata filtering。 
Tenki 继续依赖当前 64-bit 碰撞概率，本次保持行为的 RFC 不为它新增完整 identity map。 
集中派生算法不能替代已经存在的完整身份校验。

## 5\. Acquire serializer

新增模块：`deerflow.sandbox.acquire_serialization`。

```python
class AcquireSerializer[KeyT: Hashable]:
    @contextmanager
    def hold(self, key: KeyT) -> Iterator[None]: ...

    @asynccontextmanager
    async def hold_async(self, key: KeyT) -> AsyncIterator[None]: ...

    def close(self) -> None: ...
```

context-manager API 保证 lock release 无条件执行，避免调用方 acquire 后忘记在 
`finally` 中释放。provider 选择能保持其现有碰撞与生命周期语义的 key；共享组件 
不重新解释它。

必须满足：

- 使用相同 provider-selected key 的调用不重叠；
- 不同 scope 可并发；
- 异步等待期间取消，不能留下已获取锁；
- 获取后取消，在 context exit 释放；
- async 等待不阻塞 event loop；
- 不占用 default executor；
- `close()` 拒绝新 holder，并释放 executor 资源，但不破坏正在执行的 critical section；
- 没有 holder 和 waiter 时删除 lock entry。

### 5.1 Lock-table 生命周期

每个 entry 包含 lock 与 holder/waiter 引用计数。在 table lock 下查找 entry 并增加 
计数；正常退出和取消等待都减少计数。只有计数为零且 lock 未持有时才删除 entry。

这消除了当前每个历史 thread 一把永久锁的增长问题，也不依赖 
`WeakValueDictionary` 的不确定回收时机。

### 5.2 异步执行

组件拥有一个有界专用 executor，用于阻塞的 `threading.Lock.acquire`。它复用 AIO 
现有的 shield + release callback 语义：若 coroutine 在 worker 等锁时取消，worker 
最终取得锁后必须立即释放，并减少 entry 引用。

E2B 可以继续卸载整个同步 acquire，并在 worker 内使用 `hold()`；不需要为了消费 
该组件而把远端 SDK 路径改成 native async。

## 6\. Provider 接入

### AIO

- 用 `derive_sandbox_scope_token` 替换 `_deterministic_sandbox_id`；
- 用 serializer 替换 `_thread_locks` 和模块级 async lock helper；
- 继续用 `(user_id, thread_id)` 作 key，并且只串行化 acquire，与当前行为一致；
- 保留 flock、ownership、`_local_teardown`、`_acquire_epoch` 与 async readiness。

### E2B

- 用共享 identity helper 替换 `_stable_seed`——注意对 E2B 而言派生值是 warm-pool 
 查找 _seed_，不是 provider 签发的远端 id（后者由 E2B API 返回）；在 E2B 代码里 
 称之为 "sandbox id" 是历史叫法；
- acquire 与 release 状态转换均改用 `AcquireSerializer.hold`；
- 继续用 `(user_id, thread_id)` 作 serializer key；
- 保留 acquire executor、capacity condition、Redis ledger、reservation token、 
 reconcile、tombstone 与 overflow policy。

### BoxLite

- 替换 `_sandbox_id` 与 `_acquire_locks`；
- 继续用派生 sandbox id 作 serializer key，并且只串行化 acquire，保留当前碰撞排除 
 与 release 行为；
- 保留私有 event loop 与 warm-pool 行为。

### Tenki

- 替换 `_sandbox_id` 与 `_acquire_locks`；
- 继续用派生 sandbox id 作 serializer key，并且只串行化 acquire；
- 保留 SDK、bootstrap、health check 与 warm-pool 行为。

### Local

不改。Local creation 已由 object-cache lock 串行化，其可读 id 也刻意不同。

## 7\. 保持 provider 私有的机制

| 机制 | Provider | 原因 |
| --- | --- | --- |
| create/discover flock | AIO | backend 特有的跨进程互斥 |
| teardown reservation 与 acquire epoch | AIO | 与其 reaper 协议绑定 |
| capacity condition、reservation、tombstone | E2B | 物理远端容量正确性 |
| 私有 event loop | BoxLite | loop-affine handle 正确性 |
| warm-pool health check/bootstrap | BoxLite/Tenki | SDK 特有行为 |

不引入 template-method provider 基类。看似相似的 acquire 流程具有本质不同的步骤 
契约与故障恢复。

## 8\. 落地阶段

### Phase 1：identity

- 增加完整 golden-vector 测试，包括空值与非 ASCII；
- 每次迁移一个 provider；
- 证明每个 provider 仍生成完全相同的 id；
- 将算法记录为兼容性契约。

### Phase 2：serializer 契约

- 增加同步互斥、不同 key 并发、获取前取消、获取后取消、close 竞态与 entry 回收测试；
- 增加 blocking-IO runtime anchor，证明 async 等待不在 event loop 上阻塞。

### Phase 3：provider 迁移

- 先迁移 AIO，因为它提供取消行为参考实现；
- E2B、BoxLite、Tenki 分别独立提交；
- 每次迁移后运行该 provider 的并发、release race、warm reclaim、shutdown、identity 
 collision 测试。

## 9\. 兼容与回滚

- `SandboxProvider` 与 sandbox tool 契约不变；
- 每个 provider 的派生兼容 token 逐字节不变；E2B 由 provider 签发的远端 id 不变；
- 现有 warm 资源仍可发现；
- 不新增配置或数据库 schema；
- 每个 provider 的迁移可独立回滚；
- provider shutdown/reset 必须关闭 serializer，测试固定 close 幂等行为。

## 10\. 验收条件

- golden vector 与四份当前 identity 实现一致；
- 不丢失任何 provider 已有的 identity collision 防御；
- 当前受 provider lock 保护的每个 transition 继续使用等效的同一 key；本 RFC 不会 
 新增对原本未串行化 release 路径的锁；
- 被取消的 async waiter 不泄漏锁或 lock-table entry；
- 所有 scope 完成后 lock table 大小回到零；
- E2B capacity 与 reconcile 测试在 ledger 不变的情况下通过；
- AIO ownership/reaper race 测试原样通过；
- BoxLite 私有 loop 与 Tenki warm-pool 测试原样通过；
- 不产生用户可见的配置或行为变化。

## 11\. 与 active admission 的关系

admission key 使用 `deerflow.sandbox.admission.identity` 中的独立 helper。本 RFC 
不导入 quota、Redis admission、用户记录或 admin API，admission RFC 也不依赖本 
模块。两者都可以先落地。
