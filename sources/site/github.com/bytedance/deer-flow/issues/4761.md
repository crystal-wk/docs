### Problem summary

WeComChannel.stop() cancels the WebSocket connection task but returns without waiting for the task to exit. It then clears the task reference, allowing an immediate restart to create a new connection while the old connection task is still performing cancellation cleanup.

### Affected area(s)

Backend API (gateway / endpoints / SSE)

### What happened?

WeComChannel.start() stores the SDK connection coroutine in \_ws\_task.

During shutdown, WeComChannel.stop():

1. calls \_ws\_task.cancel();
2. immediately sets \_ws\_task to None;
3. calls the SDK client's disconnect();
4. returns without yielding to or awaiting the cancelled task.

Cancellation is cooperative in asyncio. Calling Task.cancel() only requests cancellation; it does not guarantee that the task has processed CancelledError or completed its cleanup.

As a result, stop() can report that the channel is stopped while the old connection task is still alive. Because the task reference has already been cleared, an immediate start() creates and tracks a new connection task while the old task continues its cancellation cleanup.

This creates a deterministic shutdown/restart overlap and leaves the channel unable to track the old task.

### Expected behavior

Once WeComChannel.stop() returns, the connection task owned by that channel lifecycle should have finished cancellation and cleanup.

A subsequent start() should not overlap with an untracked connection task from the previous lifecycle.

class FakeClient:
    def __init__(self, name):
        self.name = name

    def on(self, *_args):
        pass

    def disconnect(self):
        pass

    async def connect(self):
        if self.name == "old":
            old_started.set()
            try:
                await asyncio.Future()
            except asyncio.CancelledError:
                old_cleanup_started.set()
                await release_old_cleanup.wait()
                raise

            new_started.set()
            await asyncio.Future()

    WSClientOptions=lambda **kwargs: SimpleNamespace(**kwargs),

channel = WeComChannel(

### Additional context

The reproduction uses controlled asyncio.Event barriers and requires no WeCom credentials or network access. It does not use arbitrary timing sleeps.

The intended scope is limited to the WeCom connection-task lifecycle:

- retain ownership of the connection task until cancellation cleanup completes;
- prevent stop() from returning while the old connection task is still active;
- prevent an immediate restart from overlapping the previous lifecycle;
- add a deterministic shutdown/restart regression test.

Normal connection setup, SDK reconnection behavior, message routing, streaming replies, configuration, and public APIs should remain unchanged.

I checked the current open and closed Issues and PRs. PR [#3526](https://github.com/bytedance/deer-flow/pull/3526) surfaces WeCom connection-task failures, but it does not await task cancellation during stop(). I found no existing implementation for this shutdown/restart overlap.
