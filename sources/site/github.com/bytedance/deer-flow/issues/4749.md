### Problem summary

TaskSnapshot accepts NaN and Infinity as poll\_after\_seconds values, causing next-poll scheduling to fail after a driver successfully returns a task status.

### Affected area(s)

MCP

### What happened?

`TaskSnapshot.poll_after_seconds` currently rejects only values that are less than or equal to zero.

As a result:

- `float("nan")` bypasses the comparison and is accepted.
- `float("inf")` is treated as a positive value and is accepted.

Both values fail later when `McpTaskService` calculates the next poll time:

```python
now + timedelta(seconds=interval)
```

The observed exceptions are:

```
ValueError: cannot convert float NaN to integer
OverflowError: cannot convert float infinity to integer
```

This means a driver can successfully return a remote task status, but the snapshot cannot be scheduled and persisted normally.

### Expected behavior

```
TaskSnapshot should reject poll_after_seconds unless it is both finite and strictly positive. Valid positive polling intervals should remain unchanged.
```

### Steps to reproduce

1. Check out `main@e16ef296`.
2. Enter the backend directory and set `PYTHONPATH=.`.
3. Run:

```powershell
uv run python -c "from datetime import UTC, datetime, timedelta; from deerflow.mcp.tasks import TaskSnapshot, TaskStatus; s=TaskSnapshot(status=TaskStatus.WORKING, poll_after_seconds=float('nan')); print('accepted:', s.poll_after_seconds); print(datetime.now(UTC) + timedelta(seconds=s.poll_after_seconds))"
```

4. Observe that `nan` is accepted before `timedelta` raises `ValueError`.
5. Repeat with positive infinity:

```
uv run python -c "from datetime import UTC, datetime, timedelta; from deerflow.mcp.tasks import TaskSnapshot, TaskStatus; s=TaskSnapshot(status=TaskStatus.WORKING, poll_after_seconds=float('inf')); print('accepted:', s.poll_after_seconds); print(datetime.now(UTC) + timedelta(seconds=s.poll_after_seconds))"
```

6. Observe that `inf` is accepted before `timedelta` raises `OverflowError`.

### Additional context

The invariant belongs at the protocol-neutral `TaskSnapshot` boundary rather than in one concrete driver, so all current and future MCP task drivers receive the same validation.

The intended minimal fix is to require `poll_after_seconds` to be finite and strictly positive, with deterministic regression tests for `NaN` and positive infinity.

Related foundation PR: [#4665](https://github.com/bytedance/deer-flow/pull/4665).

I also checked the open ordinary-driver PR [#4690](https://github.com/bytedance/deer-flow/pull/4690). It extends `TaskSnapshot`, but its current diff does not add finite-value validation for `poll_after_seconds`.
