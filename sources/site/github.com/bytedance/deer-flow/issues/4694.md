## Problem

`ScheduledTaskService.start()` runs two startup sweeps — `mark_stale_active_runs()` and `cancel_stuck_once_tasks()` — that mark **every** `queued`/`running` row in `scheduled_task_runs` as terminal, with no owner/lease/time filter. The repository's own docstring flags the assumption: _"Only valid under the MVP's single-scheduler-instance assumption."_

Under `GATEWAY_WORKERS > 1` or multi-pod Kubernetes, every worker/pod runs the lifespan and therefore runs the sweep. A worker that starts (or restarts) while a peer's scheduled run is legitimately executing will:

1. Mark the peer's live run row `interrupted` — the run keeps executing in the peer process, but its durable record now says it stopped.
2. Release the `uq_scheduled_task_run_active` partial-unique slot (`WHERE status IN ('queued','running')`), so the **next cron tick launches a second execution while the first is still running** — `overlap_policy=skip` is defeated from a new path (the same duplicate-execution class as [fix(scheduler): close dispatch race that can launch two runs for one task #4105](https://github.com/bytedance/deer-flow/pull/4105), reopened through the startup sweep).
3. For `once` tasks, `cancel_stuck_once_tasks()` additionally marks the _task_ itself `cancelled` mid-execution.

A rolling restart of a multi-pod deployment reproduces this deterministically whenever a cron run is in flight.

Single-worker / single-pod deployments (the current default and the documented safe configuration) are unaffected.

## Root cause

- `backend/app/scheduler/service.py` — `start()` calls the sweeps unconditionally on every worker's lifespan.
- `backend/packages/harness/deerflow/persistence/scheduled_task_runs/sql.py` — `mark_stale_active_runs()` has no owner/lease/time predicate.
- `backend/app/gateway/deps.py` — `_validate_multi_worker` gates other multi-worker-unsafe features (`run_ownership` heartbeat, browser sessions) but not `scheduler.enabled`.

## Candidate directions

(a) **Startup gate**: extend `_validate_multi_worker` to reject `scheduler.enabled: true` when `GATEWAY_WORKERS > 1` (and document that multi-pod requires an external leader-election/Postgres advisory lock around the scheduler poller). Smallest change, fail-loud, matches how other multi-worker-unsafe features are handled today.

(b) **Owner-aware sweep**: give `mark_stale_active_runs` / `cancel_stuck_once_tasks` a lease/time predicate (only sweep rows whose `lease_expires_at` is well past, or that predate this process start), so a peer's live rows survive. More work, but multi-pod-capable.

I lean toward (a) now + documenting (b) as a follow-up, mirroring the run-ownership gating pattern — but happy to implement whichever direction maintainers prefer.

## Repro sketch

Two `ScheduledTaskService` instances sharing one SQLite/Postgres repo: service A dispatches a run (row `running`), then service B runs `start()` — A's row is marked `interrupted` while A's run is still executing.

Happy to send a PR with tests once the direction is confirmed.
