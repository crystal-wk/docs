DeerFlow supports user-owned IM channel connections for Telegram, Slack, Discord, Feishu/Lark, DingTalk, WeChat, WeCom, and Buzz. No public IP, OAuth callback URL, or provider webhook is required — DeerFlow uses outbound long-polling and Socket Mode connections, so you can connect from any private or local deployment.

## Configure config.yaml

Add the `channels` and `channel_connections` blocks to your `config.yaml`. Replace each placeholder with the corresponding environment variable or literal value for your deployment.

```yaml
channels:
  telegram:
    enabled: true
    bot_token: $TELEGRAM_BOT_TOKEN
  slack:
    enabled: true
    bot_token: $SLACK_BOT_TOKEN
    app_token: $SLACK_APP_TOKEN
  discord:
    enabled: true
    bot_token: $DISCORD_BOT_TOKEN
  feishu:
    enabled: true
    app_id: $FEISHU_APP_ID
    app_secret: $FEISHU_APP_SECRET
  dingtalk:
    enabled: true
    client_id: $DINGTALK_CLIENT_ID
    client_secret: $DINGTALK_CLIENT_SECRET
  wechat:
    enabled: true
    bot_token: $WECHAT_BOT_TOKEN
  wecom:
    enabled: true
    bot_id: $WECOM_BOT_ID
    bot_secret: $WECOM_BOT_SECRET
  buzz:
    enabled: true
    relay_url: wss://buzz.example.com
    private_key: $BUZZ_PRIVATE_KEY   # hex or nsec1…

channel_connections:
  enabled: true
  require_bound_identity: true

  telegram:
    enabled: true
    bot_username: $TELEGRAM_BOT_USERNAME

  slack:
    enabled: true

  discord:
    enabled: true

  feishu:
    enabled: true

  dingtalk:
    enabled: true

  wechat:
    enabled: true

  wecom:
    enabled: true

  buzz:
    enabled: true
```

<Warning>
  `require_bound_identity: true` is the default. With this setting, DeerFlow rejects ordinary IM messages from users who have not yet completed the identity bind flow. Set it to `false` only for legacy open-bot deployments that intentionally route unbound platform users to shared buckets.
</Warning>

## Connect Your Identity

Each DeerFlow user must complete a one-time identity bind before sending messages through an IM channel. The bind uses a short-lived one-time code generated by the DeerFlow web UI.

<Steps>
  <Step title="Open Settings">
    Navigate to **Settings → Channels** in the DeerFlow web UI.
  </Step>
  <Step title="Select your provider">
    Choose the messaging provider you want to connect (for example, Telegram or Slack).
  </Step>
  <Step title="Generate a connect code">
    Click **Connect**. DeerFlow generates a one-time code with a 10-minute TTL. For Telegram, the UI also produces a deep-link URL you can click directly.
  </Step>
  <Step title="Send the code to the bot">
    Send `/connect <code>` to the DeerFlow bot for your provider. See the provider-specific instructions below for exact steps.
  </Step>
  <Step title="Confirm the bind">
    DeerFlow binds your IM identity to your DeerFlow account. Future messages from that IM identity run under your user bucket (memory, uploads, outputs).
  </Step>
</Steps>

## Provider-Specific Instructions

<AccordionGroup>
  <Accordion title="Telegram">
    Click the deep-link URL displayed in the Connect dialog, or open `https://t.me/<your_bot_username>?start=<code>` directly in Telegram. Your Telegram client sends `/start <code>` to the bot automatically, completing the bind.
  </Accordion>
  <Accordion title="Slack">
    Find the DeerFlow Slack bot in your workspace and send it the message:

    ```text
    /connect <code>
    ```

    The Slack Socket Mode worker receives the message and binds your Slack user and team to your DeerFlow account.
  </Accordion>
  <Accordion title="Discord">
    Open a DM with the DeerFlow Discord bot and send:

    ```text
    /connect <code>
    ```

    The Discord Gateway worker receives the message and binds your Discord user and guild to your DeerFlow account.
  </Accordion>
  <Accordion title="Feishu / Lark">
    Open a direct message with the DeerFlow Feishu bot and send:

    ```text
    /connect <code>
    ```

    The long-connection worker receives the message and binds your Feishu user identity to your DeerFlow account.
  </Accordion>
  <Accordion title="DingTalk">
    Open a direct message with the DeerFlow DingTalk bot and send:

    ```text
    /connect <code>
    ```

    The polling worker receives the message and binds your DingTalk user identity to your DeerFlow account.
  </Accordion>
  <Accordion title="WeCom">
    Open a conversation with the DeerFlow WeCom bot and send:

    ```text
    /connect <code>
    ```

    The long-connection worker binds your WeCom identity to your DeerFlow account.
  </Accordion>
  <Accordion title="WeChat">
    Open a conversation with the DeerFlow WeChat bot and send:

    ```text
    /connect <code>
    ```

    The polling worker binds your WeChat identity to your DeerFlow account.
  </Accordion>
  <Accordion title="Buzz (Nostr)">
    Send `/connect <code>` as a direct message or @-mention to the DeerFlow Buzz bot on your relay. The relay-loop worker receives the message and binds your Nostr pubkey (scoped to the relay host) to your DeerFlow account.

    Before connecting, make sure the DeerFlow bot pubkey has been:
    1. Registered as a relay member: `buzz-admin add-member --pubkey <hex>`
    2. Added to each channel: `buzz channels add-member --channel <uuid> --pubkey <hex> --role bot`

    The `buzz` dependency extra is required: `uv sync --extra buzz`.
  </Accordion>
</AccordionGroup>

## Sync vs. Streaming Modes

Different providers deliver agent replies in different ways depending on their platform capabilities.

| Mode | Channels |
|---|---|
| Streaming (real-time, incremental updates) | Feishu, Telegram, WeCom |
| Sync (wait for completion, single reply) | Slack, Discord, DingTalk |

Streaming channels show progressive updates as the agent works — Telegram edits the placeholder message in-place, Feishu patches a running card, and WeCom uses the AI card streaming API. Sync channels send one reply after the agent run completes.

## File Attachments

You can send files (images, documents) directly in your IM conversation and the agent receives them in your uploads directory. DeerFlow downloads and stages each attachment into your thread's `/mnt/user-data/uploads/` path, then injects a `<current_uploads>` block so the agent sees the files for the current message. Use `list_uploaded_files` to reference uploads from earlier turns.

## Security Notes

<Note>
  Connect codes use 128 bits of randomness, expire after 10 minutes, and are single-use. Treat them like one-time passwords — do not forward or share them.
</Note>

- Connect codes are shown only in your browser during the bind flow and are never echoed back to the IM chat.
- Each external IM identity (`provider + account + workspace`) can have at most one active DeerFlow owner. A successful re-bind transfers ownership and revokes the previous owner's connection.
- Provider bot tokens remain in `channels.*` config and are never returned to the browser.
- For providers with an `allowed_users` allowlist (Telegram, Slack, DingTalk, WeChat), a valid `/connect <code>` is consumed **before** the allowlist is checked. This lets a not-yet-allowlisted user complete their first bind. After binding, `allowed_users` continues to gate ordinary messages.

<Warning>
  Setting `require_bound_identity: false` restores legacy open-bot behavior where unbound platform users can trigger DeerFlow runs. Use this only for intentional operator-owned deployments where you accept unauthenticated IM-to-agent routing.
</Warning>
